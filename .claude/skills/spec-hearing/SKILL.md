# spec-hearing

## 使う役
specification

## 読むもの
- `specs/<チケット>/hearing/brainstorm.md`（根拠にしてよいのはここと人の答えだけ）
- `specs/ticket-plan.yaml` の自分の行、変える領域と uses で指す領域の `specs/_current/<領域>/requirements.yaml`、`specs/_current/_intent/`、`specs/_current/_shared/`、`specs/_current/_tech/architecture.md` の「仕様の結果の写し方」
- `specs/_notes/` のうち、名前と「当てはまる」から関係しそうなもの
- チケットの範囲が `_tech` に当たる（デプロイ、技術の入れ替えなど）なら、foundation-hearing スキルの該当する節
- 流れのチケットなら、通す操作を確認した前のチケットのテスト（下の「流れのチケット」）

## 1. 自分の行と前提
- ticket-plan.yaml の自分の行の purpose と scope が、壁打ちのメモと合うかを確認し、合わなければ直す。行が無ければ（/aidd-new で足したチケット）足す。later から切り出したなら、later の行を消す。作ったものを公開して使う人が使い始めるチケット（公開のチケット。later の「デプロイ」を切り出したものなど）なら、行に `release: true` を付ける（公開の後でないと確認できない非機能要件が、このチケットの Gate 2 で人の判断に出る）
- AI が推測すると下書き全体が的外れになりうる前提の事実（誰が予約できるか、など）だけを先に問う。答えは `_intent/intent.yaml` の facts に足す

## 2. 要件と具体例
`specs/_current/<領域>/requirements.yaml` に、`.claude/aidd/templates/requirements.yaml` の形で書く。新しい領域なら purpose も書く。
- 仕様に書く具体例は、会社や人によって答えが変わりうるものだけ（「10:00〜11:00 の予約があるとき、11:00〜12:00 は予約できる」は間を空けたい会社もあるので書く）。業務の人が答えを持たないもの（人数の欄に「八」と入れたら断る、名前の前後の空白を除く）は書かない。テストか計画の決め事かライブラリの既定に任せる。例外は、下の具体例の無い画面の状態と、やり直しの具体例と、承認の後に見つかった具体例の無い場面（プロダクトリードが渡す。下の「承認の後に直すとき」）
- 扱うのは、使う人の業務で実際に起きる場合だけ。極端な場合は、壊れるとお金、データ、安全、既存の振る舞いに影響するときだけ書く
- 場合（要件の文や具体例）を足す前に、下の「レビューの指摘を直すとき」の 3 つ（1 か所に寄せる、確認する順を 1 つの決まりにする、細部を計画に回す）を考える。最初に書くときも同じに考える
- 人に並べる具体例は、結果（出る文の中身、残るデータ、次にできること）が業務の判断で変わりうるものと、種類ごとの代表 1 つにする。違いが操作の動詞だけのもの（予約で送るか、取り消しで送るか、など）は代表に畳み、テストで守る
- 具体例の結果は、architecture.md の「仕様の結果の写し方」の語でそろえる（断られる、ほかと重なるので断られる、見つからない など）。状態コード、パス、欄の名前、応答の形は書かない
- uses は、領域の外（ほかの領域、`_shared`、`_intent`）で、その要件と下の具体例が頼るものだけを書く。領域の中の要件どうしは書かない。言葉を指すのは、その意味が変わると要件が崩れるときだけ
- 共通の非機能要件のうち、確認の仕方が test と human のもので、この操作に当てはまるものは、要件の uses で指し、test の基準は具体例を置く。領域の非機能要件を足すとき、human のものには、人が確認する手順（どこを開いて何を見るか）を文に添え、公開の後でないと確認できないものには `after_release: true` を付ける（overall-hearing と同じ書き方）
- 共通の用語や要件が要り、まだ無ければ、`_shared` に足す（最初に使うチケットが足す。terms.yaml は `.claude/aidd/templates/shared-terms.yaml`、rules.yaml は `.claude/aidd/templates/shared-rules.yaml` の形）
- 共通の要件と代表の具体例：同じ種類の場面（返事が届かない、入れ忘れ、途中でやめる など）が 2 つ目の操作か 2 つ目の領域に出たら、`_shared/rules.yaml` に共通の要件を 1 つ書き、その下に代表の具体例を 1 つ置く（id は `AC-<共通の要件の名前>-<番号>`）。その種類の共通の要件が既にあれば（000 で書いたものも）、その下に代表の具体例を置き、新しく作らない。操作の要件は uses でその共通の要件を指し、同じ場面の具体例を操作ごとに書かない（テストは、指す操作ごとに代表の具体例の ID で書く）。前に人が答えた種類は、その答えに従う。最初に出た操作の具体例は、`spec-changes.yaml` の renames で代表の具体例に移す（結果が同じなら、今あるものへの影響の一覧に出ない）。振る舞いが同じものをまとめるだけなら問わない。領域ごとに振る舞いがそろっていない（前の答えが割れている）ときは、そろえ方を問いにする
- 画面のあるシステム（`specs/_current/_tech/design.yaml` がある）では、このチケットで足すか変える画面を、領域の `screens` に書く（`id` は `SCR-<英語の名前>`、`title` は業務の言葉の画面の名前）。画面の見た目（並び、色、文言）は書かない（Designer がモックで描く）。画面に出る振る舞い（項目、操作、メッセージ）は、要件と具体例で書く
- 具体例は、結果（then）が見える画面のある領域に置く（画面例は、その画面のある領域の具体例しか指せないため）。共通の要件の具体例は `_shared` に置き、画面例から指せる
- プロダクトリードが、Designer の挙げた具体例の無い画面の状態（`specs/<チケット>/screen-changes.yaml` の `unexampled`）を渡したら、1 件ずつ、利用者に何が見えるかを要件と具体例にする。答えが 1 つでも、画面に見える結果は、共通の要件で決まらないものだけ具体例にする（上の「業務の人が答えを持たないものは書かない」の例外。画面で何も起きないことを、利用者は誤りかどうか判別できないため。共通の要件で決まる状態は、その要件を uses で指す）。知らせ方など業務で答えが変わるものは、提案付きの問いを書く。起きないと判断したもの（選べない作りになっている、など）は足さず、報告に理由を書く。`unexampled` は書き換えない（Designer の書くもの）
- やり直しの具体例：入力や操作を断る具体例がある画面では、画面ごとに、断られた後に直してもう一度送ると受け付けられる具体例を 1 つ置く（例：写真の代わりに PDF を選んで断られた後、写真を選び直して登録すると、登録できる）。答えは 1 つに決まるが、断られた後に先へ進めないことは、書かないと作りでもテストでも確認されないため

## 3. 今ある振る舞いを変えるとき
- 今ある具体例を書き換え、消す具体例は消す。Gate 1 の承認のページには、機械が今と後の対を出す
- 名前を変えるときは、`specs/<チケット>/spec-changes.yaml`（`.claude/aidd/templates/spec-changes.yaml` の形）の renames に古い ID と新しい ID の対を書く。ID でつながらない影響は impacts に書く（今あるものへの影響の一覧に行として出て、Gate 1 の承認のページの冒頭に載る。note は ID を入れずに、何がどう変わるか（前と後）が分かる 1 文で書く）
- このチケットの範囲を超えて共通の要件などを変えたくなったら、変えずに問う（選択肢：このチケットに含める、別のチケットに分ける、変えない）。同じ種類の場面を共通の要件にまとめるとき、振る舞いが同じものをまとめるだけなら問わない。領域ごとに振る舞いがそろっていなければ、そろえ方を問う（2 の「共通の要件と代表の具体例」）
- ただし、プロダクトリードが、レビューの挙げた共通の文書（architecture.md の「仕様の結果の写し方」など）に足す候補を渡したら、承認の前後によらず、foundation-hearing のその文書の節に沿って足す。技術の細部なので問いにしない
- まだ始めていないほかのチケットの行（範囲、依存）は、要るなら変えてよい。進行中と main にマージ済みのチケットの行は変えない。マージ済みかは aidd-run の「マージ済みの決め方」のとおり、main の `specs/<チケット>/status.yaml` が受入済かで決める（作業ツリーにあるほかのチケットの status.yaml は、main から取り込んだマージ済みのもの）。例外は、流れのチケットを閉じるときに自分の行を消すこと（下の「流れのチケット」）

## 4. 技術の選択
ライブラリの追加、データの形など、後で変えにくい選択があれば、`_tech/tech.yaml` に足す（開いて見せる形。alternatives の effect は選ばなかった理由の一言にする）。足したものは Gate 1 の承認のページの「確認してほしいこと」に出る。

問いは、定義（specification.md）の「問いの書き方」のとおりに書く。

## 流れのチケット
自分の行が流れのチケット（複数の領域を通る操作を確認するチケット。000 で一覧に足す）なら、要件と具体例は流れの領域（`specs/_current/journeys/<流れ>/requirements.yaml`）に書き、具体例は次のとおりに選ぶ。前のチケットのテストが確認したことを、重ねて確認しないためである。
1. 通す操作を確認した前のチケットのテストを読む（テストの名前に具体例の ID `<領域>/AC-…` が入っているので、Grep で探す）。テストごとに、何を確認したかと、確認の前の場面をどう作ったか（準備のデータで直に入れたか、API で入れたか、画面で操作したか）を見る
2. つなぎ目（ある画面の操作の結果を、別の画面か別の使う人が受ける所。例：顧客の画面で頼んだ取り置きが、スタッフの一覧に出る）ごとに、前のチケットのテストが、結果を作る側も受ける側も画面で操作して通したかを見る。片側を準備のデータか API で入れたつなぎ目は、まだ通していない
3. まだ通していないつなぎ目だけを具体例にする。もう通したつなぎ目は具体例にしない
4. まだ通していないつなぎ目が残っていなければ、要件と具体例を書かずに、このチケットを閉じる案を問う（about は `TICKET/<自分のチケット>`。選択肢は「閉じる」（提案）と、確認を続けたいつなぎ目を書いてもらう「確認を続ける」。background には、どのつなぎ目を、前のどのチケットのテストが画面の操作で通したかを書く）
5. プロダクトリードが、人が閉じる方を選んだと伝えたら、ticket-plan.yaml の自分の行を消す（上の 3 の「進行中のチケットの行は変えない」の例外）。まだ始めていないほかのチケットの depends_on にこのチケットがあれば、外す。ほかのファイルは変えない（承認の段は無く、プロダクトリードがコードの無いまま閉じる）

## レビューの指摘を直すとき
承認の前でも後でも、次のとおりに直す。
- 場合を足す前に、次の 3 つを考える（場合ごとに足すと、足した決まりから次の場合が見つかり、往復が続くため）
  - (a) 1 か所に寄せる：1 つの事柄は 1 か所に書き、ほかはそこを指す
  - (b) 確認する順を 1 つの決まりにする：種類（`kind`）の付いた指摘は、挙がった場合ごとに決まりを足さず、その種類を 1 つの決まり（要件の文）で扱う。状態で答えが変わる操作は、受け付けの順を 1 つの決まりで書き、場面ごとの文を足さない
  - (c) 細部を計画に回す：業務の判断が要らない細部は、要件の文に足さず、計画の決め事に任せる
- 種類の付いた指摘か一歩引いた見直しを直すときは、ほかの値や画面にも同じ形を探し、同じ回に直す
- 狭める問い：振る舞いを狭めれば（例：頼めたか分からない間は、日の切り替えも別の日の分を頼むこともできなくする）、その種類の場合がまるごと要らなくなるなら、狭める案を問いにする。狭めると利用者にできることが減るので、決めるのは人である。選択肢は、狭める案と、狭めずに 1 つの決まりで場合を扱う案（扱い方の答えが 1 つに決まらなければ、扱い方ごとに）。effect には、狭めるとできなくなることと、狭めないと扱う場合を書く。about には、狭めると消えるか変わる具体例の ID も入れる。同じ要件で 2 つ目の穴が出たら、狭める案を提案にする。狭めると人が話したことができなくなるときだけ、狭めない方を提案にし、reason に、人が話したどのことができなくなるかを書く

## 承認の後に直すとき
計画、テスト、実装の段で仕様の漏れや誤りが見つかって戻ったら、要件と具体例を直す。
- 問いにするのは、業務で答えが変わりうる点と、プロダクトリードが問いにするよう伝えた点（見つけた役が、今の要件からは答えが 1 つに決まらないとしたもの。自分では決まると思っても問う）。ほかは問わずに具体例を足す（Gate 2 で「承認の後に変わった具体例」として見せる）
- プロダクトリードが、同じ要件で 2 つ目の穴として狭める問いを伝えたら、上の「狭める問い」で書く（場合を 1 つ足す問いにはしない。提案の選び方も「狭める問い」のとおり）。どう狭めても場合が残るか、その要件の狭める問いに人がもう答えていれば（狭めない方を選んだ）、狭める問いは書かずにふつうに直し、報告に理由を書く
- 問いにする穴の場面が、人が壁打ちでも答えでも話していない所なら、選択肢に「この場面はこのチケットでは扱わず、後で切り出す範囲に回す」も入れる（選ばれたら、ticket-plan.yaml の later に足し、このチケットでは具体例を足さない）
- 問いの about には、要件の ID に加えて、答えで足すか変える具体例の ID を、領域を付けた形（`<領域>/AC-…`）で 1 つずつ入れる。Gate 2 は、承認の後に足すか変えた具体例のうち、承認の後に答えた問い（承認のコミットで答えが無く、今は答えのある問い）の about に ID の無いものを、問わずに決めた振る舞いとして「あなたが見て判断すること」に出す。要件の ID だけでは、その具体例を問うたことにならない。答えを反映して具体例の ID が変わったら、about も合わせる

## main の取り込みで仕様の YAML がぶつかったとき
両側の変更を残して解く。main の側で足された要件を落とさない。両側が同じ要件を変えていたら、どちらにするかを問いにする。

## しないこと
- 根拠の無い要件を、問いを書かずに足すこと
- 具体例と同じことを、要件の文や別の欄に重ねて書くこと

## 終わったとき
報告に、変えた領域と、書いた問いの数を書く。最初の下書きの回は、問いにせず自分で決めた、利用者に見えること（壁打ちのメモにも人の答えにも無く、答えが 1 つに決まるので問わなかったこと）の件数と、主なもの 3 つほども書く（プロダクトリードが、問いの前に人に伝える）。
