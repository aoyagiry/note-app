# test-generation

## 使う役
test-writer

## 読むもの
- 変える領域の `specs/_current/<領域>/requirements.yaml`（承認した具体例）、`specs/<チケット>/plan/implementation-plan.md`（テストが呼ぶ形と、作る順番のこの役の分担）、`plan/details.yaml`
- `specs/_current/_tech/`（architecture.md のテストの決まりと「仕様の結果の写し方」、toolchain.yaml）、今のテスト
- プロダクトリードが伝える、テストを書く具体例（`results/spec-diff.json` の足した、変えた具体例。不具合の修正では、壁打ちで確認した壊れている具体例）

## 書くもの
- テストのファイル。テストの名前に、領域を付けた具体例の ID（`rooms/AC-register-1`）か、番号を付けた決め事の ID（`003/PD-001`）を入れる
- `specs/<チケット>/results/red-result.md`（`.claude/aidd/templates/red-result.md` の見出しのまま）：テストごとに、なぜ今は落ちるか。最初から通るテストとその理由
- テストの設定とテストの支え（playwright.config.ts、vitest.config.ts、準備の関数、時刻の表など）のうち、計画の分担でこの役に入っているもの（Red の前に要るものと、作りに合わせた設定の直し）。作る役はこれらを変えられない

## 手順
1. 具体例ごとにテストを書く。期待する結果は、具体例の then と、仕様の結果の写し方（architecture.md。「断られる」を何として確認するか）と、計画の決め事だけから作る。具体例に無い期待する結果を足さない
   uses で共通の要件（`specs/_current/_shared/rules.yaml`）を指す操作（要件）ごとに、その共通の要件の代表の具体例の ID（`_shared/AC-…`）でテストを書く（同じ ID のテストが操作の数だけできる）。プロダクトリードが、前の領域の具体例を共通の要件の代表に移した（spec-changes.yaml の renames）と伝えたら、前の領域のテストの名前の ID を新しい ID に書き換え、e2e のスクリーンショットの名前も一緒に直す。期待する結果は変えない
   操作の前に、具体例の前提（given の数や状態。例：枠 10 人で 9 人を受けた日）をテストの中で確認する。確認はテストの準備の関数（データの読み書きの関数）で行い、まだ作っていない画面や API に頼らない（準備の誤りが、誤った理由の Red として出るように）
   場面を作る準備（通信を止める、時刻を止める、同時に押す）は、効いたことをテストの中で確認する（止めた要求の数、画面の今の時刻など）。Red では先に「未実装」で落ちるので、準備が効いていない不備は、作った後まで見えないため。同時の場面は、具体例が同時を求める操作だけを同時にする（画面を開く所から同時にしない）
   返事が届かなかった場面（前の分は届いていた）は、要求を本物のサーバーに届けて処理させてから、画面への返事だけを落として作る。通信を切るだけの作り方は、要求がサーバーに届かず「前の分は届いていた」を作れないので使わない。画面の読み込みそのものが届かない場面は、要求を届けずに落とす
2. テストは計画の約束（テストが呼ぶ形）で呼ぶ。API のテストは、まだ無いパスを呼ぶと 404 で落ちるので、受け口は要らない。関数を直接呼ぶテストでは、約束に沿って受け口だけを置く（中身は作らない）
3. 「見つからない」「ログインしていない」を期待する否定の具体例は、実装が無くてもフレームワークの既定の応答で通りうる。そうした具体例があれば、受け口だけを置く（501 などを返す）
4. test: true の計画の決め事にもテストを書く。画面のあるチケットでは、計画で決めたスクリーンショットのテストを書き、計画が決めた名前（`e2e-screenshots/<領域>--<SCR の ID>[--<AC の ID>][--<幅の名前>].png`）と幅で残す（モックだけの画面（screen-changes.yaml の `variant`）と `also` の具体例は撮らない）。画面の下に固定した部品（bottom を指定した sticky と、下に近い fixed）があり、ページが画面より高い画面は、`.claude/aidd/lib/pin-fixed.mjs` の関数で部品をページの下端に置いてから全体を撮って戻し、画面の元はその前に最初の 1 画面を、名前の末尾に `--top` を付けて撮る（architecture.md のテストの節。001 で撮る支えの関数を書くときに、この関数を読む。型は隣の `pin-fixed.d.mts`）。撮る前に、画面の元はその画面の主な要素（見出しなど。今ある画面を変えるときは、変える要素）が、画面例はその具体例の then（知らせ、一覧の変化）が見えることを確認する（まだ作っていない画面を撮って通らないように）。画面例が具体例の途中の場面（1 回目に断られた所、返事が届かなかった所など。領域の `mock/project/canvas.json` の boards の title の要約に、どの段の後の場面かが書いてある）を描いているときは、その場面を確認した直後に撮り、続きの操作はその後で行う。具体例の when が 2 段あるときは、モックが描いた方の段の後に撮る（終わりの場面で撮ると、モックと違う場面の画像になり、モックとの比較で違いとして出るため）。前のチケットの画面例を描き直しただけ（screen-changes.yaml で modified）なら、その具体例の撮るテストは then が変わらない限り変えない。今ある画面を変えるときは、前のチケットの同じ画面の撮るテストを書き換え、同じ名前に撮るテストを 2 つにしない
   動きのある画面（計画の約束に動きの作り方がある）は、動きを減らす設定を外した e2e を 1 本書く。CSS で作る動きは、操作の後に `document.getAnimations()` で長さを読み、`_tech/design.yaml` の motion の値と比較する。JS で作る動きは、Playwright の時計を止めて操作し、長さの半分だけ進めて途中の位置にいること、残りを進めて終わりの位置にいることを確認する（スクリーンショットは撮らない）。約束の作り方では確認できなければ、計画への異議で止まる
   画面の文を確認するときは、文をテストに直に書かず、画面文の一覧（texts.yaml）から ID で取る。値の入る所（`{名前}`）は、具体例の値で埋めてから比較する（Designer や人が文を直しても、テストを書き換えずに済むように）。具体例の then には文の意味が書かれ、文そのものは画面文の一覧にある。作る役が足す文（具体例もモックの画面例も無い場面の文で、画面文の一覧にまだ無いもの）は、画面文の一覧から ID で引いて確認しない（足す文は言い回しで、業務の振る舞いではないため）。モックに書かれた文は、上のとおり画面文の一覧から ID で取って確認する
5. テストを流し、正しい理由で落ちることを確認して red-result.md に書く。流すときは Red の印（環境変数 `AIDD_RED=1`）を付ける（6 の run-capture.mjs も付ける。e2e の操作と expect の待ちが短くなり、パソコンの幅の project だけが流れる。architecture.md のテストの節）。正しい Red は、期待する結果の不一致と、受け口が無いための 404 など、まだ無い画面の要素を待つ e2e の期限切れ（要素の待ちや操作の待ちの上限で、要素が見つからない）だけ。import のエラー、テスト 1 件の待ちの上限での失敗、環境のエラーは直す。前からある e2e が Red の印で操作か expect の待ちの上限で落ちたら、そのファイルだけを Red の印なしで流し直して通ることを確認し、red-result.md の「今は落ちるテスト」に、待ちの短さで落ちたことと、流し直して通ったことを書く（誤った Red ではない）
6. 最後に、toolchain.yaml の commands のうち名前が `test` で始まるものを、`node .claude/aidd/bin/run-capture.mjs specs/<チケット>/results/red-run.json "<コマンド>" ...` で流す（Red の根拠）。流した後にテスト、ヘルパー、テストの設定、受け口のどれかを直したら、流し直す（コミットの検査が、red-run.json がほかのファイルより後に書かれたかを確認する。説明の red-result.md は比較しないので、流した後に書いてよい）。テスト作成中のときだけ流す。実装中にテストの設定を直すとき（下の「実装中にテストの設定を直すとき」）、検証中にテストを直すときや、実装中に失敗の判断が test とした直しのときは流さない（Red の根拠を、作りかけか通った後の出力で上書きしないため）
7. 返す前に `node .claude/aidd/bin/traceability-check.mjs <チケット> --stage tests` を流し、違反を直してから返す（テストを直したら、6 も流し直す）

## 実装中にテストの設定を直すとき
プロダクトリードが、作る役が作ったものに合わせてテストの設定だけを直すよう伝えたとき（webServer の起動のコマンドとポート、カバレッジから外すファイルなど）。伝えられた設定のファイルだけを、作業ツリーにある作りかけのコード（起動のコマンド、ポート、ファイルの置き場所）に合わせて直す。テストのファイル、テストの支え、テストが呼ぶ形は変えない。待ちの上限を延ばして落ちるテストを通す、振る舞いを持つコードをカバレッジから外すなど、テストが確認することを減らす直しはしない。red-run.json は流さない。検証（verify.mjs）も流さない（作る役が後で流す）。直した後にテストを流して、設定の誤りによる失敗（サーバーが起動しない、ポートが違う）が消えたことを確認する（作りかけなので、まだ作っていない所のテストは落ちてよい）。伝えられた直しが、テストのファイルかテストの支えにも及ぶなら、直さずに止まる（計画への異議）。
実装中に、失敗の判断が test とした直しを伝えられたときも、red-run.json、red-result.md、検証（verify.mjs）を流さず、書き換えない（直すのはテストのファイルとテストの支えでよい）

## 検証中にテストを直すとき
プロダクトリードが、検証中の直し（スクリーンショットのテストの直し、検証中に失敗の判断が test とした直し、コードレビューの target: test の指摘の直し）か、テストが最初から通って実装中を飛ばしたので検証を流すだけであることを伝えたとき。直した後に（流すだけなら何も直さずに）、最後に `node .claude/aidd/bin/verify.mjs <チケット>` を流し（e2e を含めて長いので、裏に回ることが多い。CLAUDE.md の「サブエージェントの決まり」の長く流れるコマンド）、出力（`results/verify.json`、`results/examples.json`、`results/visual/`、差し替えた見た目の基準 `specs/_current/<領域>/screenshots/`）を成果物に含める（implementation の 6 と同じ）。検証中の直しでは `--measure` を付けない（計測は作る役が流す）。検証を流すだけのときは、作る役を起動しないので、verify.mjs が通ったら、続けて `node .claude/aidd/bin/verify.mjs <チケット> --measure` を 1 回流す（implementation の 8 と同じ）。流した後にテストかテストの支えを直したら、流し直す（コミットの検査が、verify.json がほかのファイルより後に書かれたかを確認する）。テストの不備でない失敗が残ったら、コードを直さずに、その出力を報告に書いて返す（作る役が直す）。red-run.json は流さない

## 既存のテストの変え方
既存のテストの期待する結果を変えてよいのは、そのテストが確認する具体例、仕様の結果の写し方、計画の決め事のどれかが変わったときだけ。それ以外の変更（ファイルの移動、書き方の変更、準備のデータの直し）は、確認することを変えない形でだけ行う。消えた具体例のテストは消す。

## 最初から通ってよいテスト
次だけ。red-result.md の「最初から通ってよいテスト」に理由を書く。
- 流れの領域（journeys）の具体例のうち、前のチケットで作った機能の組み合わせで満たされるもの
- 確認することを変えずに移したり書き換えたりした既存のテスト
- 変えた後の期待する結果を、今の実装がすでに満たすもの
- 基盤の受入条件の write-scopes の検査（コアの仕組みで成り立つため）

## 基盤づくりのとき
基盤の受入条件（`_tech/acceptance.yaml` の checked_by: test）を確認する検査を `specs/_current/_tech/checks/` に書く。検査の名前に `_tech/AC-<観点>-<番号>` を入れ、結果を JUnit XML で出す。
- テストの道具を確認する検査は、見本のテスト（必ず通るものと必ず落ちるもの）をその場で置き、toolchain.yaml のテストのコマンドにそのファイルだけを渡して流す。プロジェクトの本物のテスト全体は流さない（基盤の検査は検証、Red、CI のたびに流れる）。検証のコマンドが全部通るかを確認する検査は書かない（チケットごとの検証が同じコマンドを流す）
- 見本のテストは、実行のたびに作って消す。実行の前後で作業ツリーを変えない。test_reports の JUnit XML と `e2e-screenshots/` にある本物のテストの結果を、見本の結果で上書きしない（同じ場所に出るなら、流す前に退かして、終わったら戻す。検証は、すべてのコマンドを流した後に test_reports を読む）
- テストの設定とテストの支え（architecture.md のテストの節のとおり）も、この役が書く。作る役は書けない。画面のあるシステムでは、playwright.config.ts を、Red の印（`AIDD_RED=1`）があるときだけ操作の待ちと expect の待ちを 1.5 秒にし（移動の待ちは 5 秒のまま）、project をパソコンの幅のものだけにする形で書く。パソコンの幅の project は、すべての e2e のファイルを流す
- 見本のテストを流す子のプロセスの環境からは、Red の印（`AIDD_RED`）を除く（除かないと、Red の記録の回に見本の e2e がパソコンの幅だけで流れ、基盤の検査が落ちる）
- これから作る雛形のファイルが無いことは、正しい Red である
- write-scopes の検査は、`.claude/aidd/lib/scopes.mjs` の `loadScopes(<リポジトリのルート>, "999-check")` と `canWrite(<その戻り値>, "implementer", <テストのファイルかテストの設定のパス>)` を node で直接呼び、ok が false になることを確認する（テストを置く場所と、テストの設定のファイルごとに 1 つ）。案件の `_tech/write-scopes.json` が正しいことを確認するのが目的である

## 止まるとき
- 約束の形では具体例を確認できない（計画への異議。どの具体例が、なぜ確認できないか）
- 具体例どうしが両立しない、具体例が足りない（仕様の問題）。報告には、かかわる要件の ID（領域を付ける）と、今の要件から答えが 1 つに決まるか（決まらないなら答えの候補）を書く（決まらないとした穴は、必ず人に問われる）
- 開発環境の準備が要る。基盤づくりで、これから作る雛形やアプリの依存（package.json など）がまだ無いことは、これに当たらない（正しい Red である）。止まるのは、雛形とは別に、人かプロダクトリードの準備（setup.command など）が要るときだけ

## しないこと
- テストを skip すること
