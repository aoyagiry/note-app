# screen-mock

## 使う役
designer

## 読むもの
- `specs/<チケット>/results/spec-diff.json`（このチケットで変わった要件と具体例）
- 変える領域の `specs/_current/<領域>/requirements.yaml`（`screens`、要件と具体例）と `specs/_current/_shared/rules.yaml`（共通の要件の代表の具体例。その画面例は、それを最初に指す操作の画面に描く）、`specs/_current/_tech/design.yaml`（デザインシステムの URL と値）、`specs/_current/_tech/ds/<フォルダ>/base.css`（デザインシステムの土台の CSS。日本語の折り返し、操作の応答と動き、入力の部品の形）
- 変える領域の `specs/_current/<領域>/mock/`（`canvas.yaml` のキャンバスの URL と、`project/` の写し）
- `specs/_current/_tech/design.yaml` の breakpoint（画面の幅の名前と大きさ）と `specs/_current/_tech/architecture.md`
- `specs/<チケット>/hearing/brainstorm.md`（「デザイン」に見た目の壁打ちの言い直しがあれば、それに沿って描く）、`specs/_current/_intent/intent.yaml`（使う人。顧客向けの画面かを判断する）
- `_tech/design.yaml` の `decisions`（人の直しから決めたこと。次の画面から従う）と `text_rules`
- お手本の画像（`git rev-parse --git-common-dir` の下の `aidd/references/design/`。あれば）
- プロダクトリードが伝える回（作る、直す、写しを取る、動く試作）と、直すときはキャンバスのコメント、人の答え、画面のレビューの指摘（`specs/<チケット>/reviews/screen/` の指摘と直す範囲（`fix_scope`）か、計画のレビューの target: mock の指摘）の中身

## 置き場所
| 場所 | 中身 |
| --- | --- |
| Design のキャンバス（領域ごとに 1 つ） | 領域の今の画面。正。チケットをまたいで使い続け、人も直接直せる |
| `specs/_current/<領域>/mock/canvas.yaml` | キャンバスの URL（`url`）と、画面ごとの撮る幅（`screens` に `id` と `widths`。breakpoint の名前の並び）。書かない画面は breakpoint の最初の幅だけで撮る。チケットをまたいで残るので、後のチケットでその画面を描かなくても、撮り直しと幅が読める |
| `specs/_current/<領域>/mock/project/` | キャンバスの中身の写し。`canvas.json` と、画面ごとの画面の元 `<SCR の ID>.dc.html`（例：`SCR-list.dc.html`）、画面例 `<SCR の ID>--<AC の ID>.dc.html`（例：`SCR-list--AC-register-1.dc.html`）、画面の CSS `<SCR の ID>.css`（画面の元と画面例が読む）、共通部品 `<共通部品の名前>.dc.html` と `<共通部品の名前>.css`（下の「共通部品」）、デザインシステムの変数 `ds/<フォルダ>/tokens.css` と土台の CSS `ds/<フォルダ>/base.css`（mock-render が `specs/_current/_tech/ds/<フォルダ>/` の正本から毎回写す。直さない） |
| `<git の共通の場所>/aidd/runtime/<キャンバスの id>.js` | キャンバスの Design のランタイムの写し。mock-render がキャンバスと同じ描かれ方で撮るために使う。コミットしない |
| `specs/_current/<領域>/texts.yaml` | 画面文の一覧。画面の文を 1 行ずつ（`id` は `<SCR の ID か部品の名前>.<どこ>`、`screen`、`where`、`text`）。文の中には改行と強調（`**…**`）だけを使ってよい。値の入る文（「残り 3 席」）は、値の所を `{名前}` にして「残り {seats} 席」と書き、モックには具体例の値を描く（texts-sync は、`{名前}` にどんな値が入っても合うとみなす）。領域をまたぐ文（ナビゲーション、共通の知らせ）は `specs/_current/_tech/texts.yaml` に置く。流れの領域（journeys）には置かない |
| `specs/<チケット>/screen-changes.yaml` | このチケットで足すか変えた画面の一覧（`area`、`id`、`change` は added か modified、画面の元を描き直さなければ unchanged）と、その画面の画面例（`examples` に `ac` と `change`。同じ見た目にまとめた具体例は `also` に並べる）。このチケットで足すか変えた共通部品（`parts` に、領域ごとに `area`、`name`、`change` は added か modified）。描いていて気づいた具体例の無い画面の状態（`unexampled` に `area`、`screen`、`action`、`scene`） |

公開は、`root` を `specs/_current/<領域>/mock` にし、`files` に `project/canvas.json` と、変えた artboard の `.dc.html`、変えた画面の CSS と共通部品のファイルを挙げて、リポジトリから直接行う。artboard を消すときは、`files` にその `project/<名前>.dc.html` を null で挙げ、`canvas.json` の boards と order からも外す。

## 0. どの回でも最初に：ランタイムの写し
このチケットの screen-changes.yaml の screens と parts に載る領域（作る回では、これから描く領域も）のキャンバスごとに、`<git の共通の場所>/aidd/runtime/<キャンバスの id>.js` があるかを確認する。git の共通の場所は `git rev-parse --git-common-dir`、キャンバスの id は `mock/canvas.yaml` の URL の最後の区切り。無ければ、キャンバスを Artifact の `read`（path は `artifact-type/dc-runtime.js`）で scratchpad に保存し、Bash でそこへ写す。キャンバスは作ったときの型の版で描かれるので、ほかのキャンバスのものを使い回さない。キャンバスを新しく作ったときは、作った後に写す。

## 1. 作る、直す
1. 描く artboard を決める
   - 画面の元：足す画面は、変える領域の `screens` にあり、`project/<SCR の ID>.dc.html` がまだ無いもの。変える画面は、spec-diff.json の変わった要件と具体例が、今の画面の元に出ているもの
   - 画面例：変える画面の具体例のうち、then が画面に見えるもの（知らせ、一覧の変化、ダイアログ）。このチケットで足すか変えた具体例は描く（足すなら added、描き直すなら modified）。前のチケットの画面例は、このチケットの変更（足した列、変えた文言）が見えるものだけを描き直す（modified）。画面の CSS を変えて見た目が変わる前のチケットの画面例は、ファイルは描き直さずに modified で載せる（e2e のスクリーンショットとの見比べを、今までと同じに保つため）。共通部品を変えたときは、それを読む画面と画面例を載せず、共通部品を parts に載せる（下の「共通部品」）。then が画面に見えない具体例は描かない。1 つの具体例が 2 つの画面にかかわるとき（予約の画面で予約し、一覧に出る）は、then が見える方の画面に描く。流れの領域（journeys）の具体例は描かない
   - まとめる：このチケットで足すか変えた具体例のうち、then で画面に見える状態が同じで、違いが値（日付、名前、金額）だけのもの（値の長さも近いもの）は、代表の 1 枚だけ描き、ほかの具体例の ID を代表の `also` に並べる。出る部品、並び、色が違うか、代表の画面に出ていない文が 1 つでもあれば（知らせの文が違う、など）、別の画面例にする（どのキャンバスにも描かれない文は、人がキャンバスで直せないため。値の入る所（`{名前}`）だけが違う文は、同じ文とみなす）。動きの具体例（押すと動く、指で動かす）は、動いた後に見える画面で比較する（動きは静止画に出ないため）。前のチケットの画面例の `also` には入れない（同じ見た目でも、このチケットで 1 枚描く）
   - 消すもの：具体例が消えたか名前が変わったら（承認の前でも後でも）、その画面例をキャンバスと `project/` から消し、screen-changes.yaml からも外す
   - 付け替える：プロダクトリードが、前の領域の具体例を共通の要件の代表（`_shared`）に移したと伝えたら、その画面例は消さずに、artboard の名前を新しい具体例の ID に付け替え（`<SCR の ID>--<新しい AC の ID>`。canvas.json の boards と order も）、その領域の画面を screen-changes.yaml に載せる（画面例の change は modified）
   - プロダクトリードが前に描いた時点からの仕様の差分を渡したら（このチケットの 2 回目以降）、それで古くなった artboard を決める。代表の具体例が消えたか、`also` の具体例が変わったら、代表の artboard も古くなったとみなす（`also` の 1 つを代表にするか、見た目が分かれたら分ける）
   - 描く artboard が無ければ何も書かず、「状態：変える画面なし」で返す
2. 描く前に、要件と具体例だけで描けるかを確認する。具体例があるのに描けなければ、描かず公開もせずに「状態：停止（仕様の不足）」で返す（途中の画面をキャンバスに残さないため）
3. キャンバスがあれば、先に `read` でキャンバスの今の中身を読み、`project/` と比較する。違えば人が直接直したので、今の中身を `project/` に書き写し、続けて `node .claude/aidd/bin/texts-sync.mjs <領域>` を流して人が直した文を画面文の一覧に戻してから（変わった texts.yaml も成果物に含める。texts-sync の知らせの扱いは「3. 写しを取る」のとおり）直す（人の直しを消さない）。見た目だけでない直し（項目、操作、メッセージの足し引き）なら、報告に書く
4. artboard を描く。画面例は、下の「写して描く」のとおり、写してから違う所だけを直す。`canvas.json` の boards の title は、画面の元は「<SCR の ID> <画面の名前>（<チケットの番号> で追加）」、画面例は「<画面の名前>：<具体例の結果の要約>（<チケットの番号> で追加）」にする。このチケットで足した artboard は「で追加」、前からある artboard を描き直したものは「で変更」にする（前のチケットの印は外す）。要約は、その具体例の then で画面に見えることを 20 字ほどで書き、ID は出さない。具体例の途中の場面（1 回目に断られた所、返事が届かなかった所など）を描いた画面例は、要約に、どの段の後の場面かを書く（e2e はそれを見て撮る時点を決める）。artboard の大きさ（boards の w）は、その画面の最初の幅（canvas.yaml の widths の先頭。無ければ breakpoint の最初の幅）にそろえる。widths に 2 つ以上の幅がある画面は、画面の元と画面例のそれぞれについて、2 つ目からの幅ごとに、元を読み込むだけの artboard（画面の元は `<SCR の ID>--<幅の名前>.dc.html`、画面例は `<SCR の ID>--<AC の ID>--<幅の名前>.dc.html`）を元の右に並べる（人がキャンバスで幅違いの見え方を見て、その幅の画面にコメントを残せるように）。中身は、`<head>` に元と同じ tokens.css と base.css の読み込み、本文に幅を固定した枠と `<dc-import name="<元の名前>" hint-size="<幅>px,<高さ>px"></dc-import>` だけを書き、boards の w と h はその幅の大きさ、title は元の title の後ろに「（<幅の名前>）」を付ける。人がこの artboard で直そうとすると、キャンバスは元の artboard を直すよう案内するので、直しは元に入る。描くのは元の 1 枚だけで、ほかの幅は読み込むだけ（PNG は mock-render が幅ごとに撮る）。画面の元の下に、その画面の画面例を並べる
5. 描いていて気づいた、具体例の無い利用者の操作（必須の欄を空のまま押す、ダイアログでやめる、選べない組み合わせを選ぶ）を、screen-changes.yaml の `unexampled` に書き足す。顧客向けの画面では、具体例が無くても、一覧が空のとき、送れなかったとき、初めて使うときを必ず検討する（読み込み中は具体例にならないので、下の「モックだけの画面」で描く）。業務のどんな場面で起きるか（`scene`）を書けないものと、`unexampled` にすでにあるものと、共通の要件（`_shared/rules.yaml`。要件が uses で指す）で決まる状態は挙げない。描かずに書くだけにする（仕様担当が具体例にしたら、次の回で描く）
6. キャンバスが無ければ、Artifact の `quickstart`（intent: design）で Design の型を見つけ、その `type_url` から作り（title は「<領域> の画面」）、デザインシステム（`_tech/design.yaml` の URL）をキャンバスに入れる（型の決まりどおり、サーバーの中で `project/ds/<フォルダ>/` にコピーする。tokens.json、tokens.css、base.css を含める）。URL を `mock/canvas.yaml` に書く。キャンバスに入ったフォルダの名前が `specs/_current/_tech/ds/` のフォルダと違えば、モックのある領域がまだ無いときだけ、`_tech/ds/` のフォルダの名前をキャンバスに合わせる（ほかの領域があれば合わせず、報告に書く）（リポジトリの `project/ds/` は mock-render が写す）
7. 描いた画面の文を、画面文の一覧（texts.yaml）に足すか直す。モックの文の要素には `data-text="<行の id>"` を付け、要素の文と一覧の text を同じにする。同じ文を別の画面にも出すときは、同じ id を使う。値の入る文（一覧で `{名前}` にした所）は、モックでも、入れた具体例の値（名前など）を `<span data-value>` で包む（土台の CSS がこの印の値を行の途中で割らないので、モックと作ったものの折り返しがそろう）
8. 公開し、`specs/<チケット>/screen-changes.yaml` の一覧に、描いた画面と画面例と、足すか変えた共通部品（`parts`）を足すか更新する。前の回までの分と `unexampled` は残す（消すのは 1 の「消すもの」だけ）。このチケットで最初に足した artboard と共通部品は、描き直しても added のまま
9. 自分で確認する（下の「描いた画面を確認する」）

## モックだけの画面
顧客向けの画面では画面ごとに次の 2 枚を描く。業務の画面では、長い値の画面をすべての画面に、読み込み中の画面を領域ごとに代表の 1 枚だけ描く。screen-changes.yaml の画面例の行に `ac` の代わりに `variant` を書き（`{ variant: loading, change: added }`）、ファイルの名前は `<SCR の ID>--<variant>.dc.html` にする。仕様の具体例を持たず、e2e では撮らない（Gate 1 の承認のページと画面のレビューにだけ出る）。
- `loading`：読み込み中の画面
- `long`：現実にありうる長い値（長い名前、区切りの無いメールアドレス、桁の多い数、1 件だけの一覧）を散らした画面。mock-render の文字の測りで、収まるかを確認する。アイコンや丸い写真は縮ませず、文字の列は縮められるようにし、ラベル（状態のタグ）は折り返さない

## 顧客向けの画面か
顧客向けの画面にだけ当てる決まり（上の 1 の 5、モックだけの画面の数、下の「顧客向けの領域の最初の画面と、紹介のページだけ」、押せる所の 44px）は、`_intent/intent.yaml` の使う人と、その画面を使う人から、描くときにその場で判断する（顧客、初めて使う人、社外の人が使う画面か）。画面に印は付けない。判断に迷ったら、報告に書く。

## 描き方
- 振る舞い（項目、操作、メッセージ、要件）は要件と具体例のとおりに描く。要件と具体例に無い振る舞いは描かない（具体例の無い状態は 1 の 5 で挙げる）。見た目（並び、文言、値）は自分で決めてよい
- 画面の文は、要件の文の言い回しを写さず、使う人の言葉で書く（要件の文は業務の決まりを書くための文で、画面に出すと硬く不自然になる）。`_tech/design.yaml` の言葉づかいの決まり（`text_rules`）に従う
- 画面例は、その具体例の given の状態から when の操作をした後に、利用者に見える画面を描く。一覧の行や入力の値は、具体例に出てくる値で書く（e2e も同じ値で撮る）
- 静的に描く。キャンバスの差し込み（`{{…}}`）、繰り返し（`sc-for`）、条件（`sc-if`）、子部品（`dc-import`）を使わない（例外は、「1. 作る、直す」の 4 のほかの幅で見せる artboard と、下の「共通部品」）。一覧の行は、具体例に出てくる値で文字として書く（レビューと作る役が、具体例の値をファイルのとおりに読めるように）
- artboard は `<head>` で `<link rel="stylesheet" href="ds/<フォルダ>/tokens.css">` と `<link rel="stylesheet" href="ds/<フォルダ>/base.css">` をこの順に読み、色、文字、間隔、角の丸みを `var(--…)` で書く。値を直接書かない（デザインシステムの値を変えたとき、写しを入れ直すだけで画面がそろうように）。今ある値で画面の意図が描けなければ、下の「デザインシステムの値を変える」
- 日本語の行の折り返し、操作の応答と動き（押した、上に乗った、フォーカス、送っている間、知らせの出入り）、入力の部品の形（プルダウン、日付と時刻、ファイルを選ぶ、チェック）は、土台の CSS（base.css）に任せ、画面の CSS で書き直さない（作るものも同じ base.css を写すので、モックと作ったものがそろう）。1 行で切る欄（`text-overflow: ellipsis`）は、画面の CSS で書かずに、土台の CSS の印 `data-truncate` を要素に付ける（その中では値を包む span を inline に戻すので、値が丸ごと「…」にならない）。土台で描けなければ、下の「デザインシステムの値を変える」で土台を直す
- 画面の CSS：画面の見た目の規則（クラスの規則）は、画面ごとに 1 つのファイル `project/<SCR の ID>.css` に書き、画面の元と画面例は `<helmet>` の中で `<link rel="stylesheet" href="<SCR の ID>.css">` として読む（`<head>` に置くと、ほかの幅で見せる artboard の中で効かない）。画面例にだけ要る規則は、その画面例の `<helmet>` の `<style>` に、読む行の後ろに書く（画面の CSS を上書きするため）。画面例ごとに CSS を写さない（書く量が増え、写しがずれるため）。人がキャンバスで見た目を直すと、直しはその要素の `style` に入り、画面の CSS は変わらない
- 画面の幅：1 つの `.dc.html` をどの幅でも使う。いちばん外の要素に `container-type: inline-size` を付け、幅による切り替えは `@container` と `cqi` で書く（キャンバスでは `vw` と `@media` が artboard の幅で効かないため）。顧客向けの画面は、canvas.yaml の widths に phone を先頭にして phone と desktop の両方（breakpoint の名前）を書く。widths の先頭の幅が主の幅で、artboard の大きさと、画面のレビューがすべての画面例を見る幅になる（顧客の多くはスマホで開くため）。業務の画面は、書かなければ最初の幅だけ
- 画面の要素には、ラベルと役割（見出し、ボタン、表、入力欄）が分かる要素を使う（e2e のテストがラベルと役割で見つけるため）
- 業務の画面の細部（taste-skill の references/app-screens.md、MIT、をもとにした）：
  - 表の、何の行かを示す列は、いちばん広く取り、画面の幅で切らない
  - 数字と時刻は、右寄せか桁のそろう書体にして、列の中で桁をそろえる
  - 画面の中の左端と右端を 1 本ずつにそろえ、まとまりの間隔は 1 つの値にする
  - 横の帯は、ラベルを帯の中に置く。ラベルが入らない短い帯は、ラベルを帯の後ろに出すか短い印にし、帯の前の枠には重ねない
  - ゼロは 0 と書き、無い値は灰色の短い線にし、空のまとまりは枠と見出しを残して 1 文を置く
  - ラベル（状態のタグ）は縮めず、1 行に収める
- 見た目（どの画面にも当てる）：
  - 文で補う前に、配置で直せないかを考える。説明の文や補助のラベルは、配置で直せないときだけ足す
  - 最初の 2 秒：画面を開いて最初に目が行く所が、その画面でいちばん大事なものか。画面の目的がすぐ分かるか
  - 押せる所が押せると分かるか。強調は色より大きさと太さと余白で作り、灰色の文字を色の地に置かない
  - 余白は、迷ったら多めにしてから減らす。近いものはまとめ、関係の無いものは離し、揃えの線を減らす
  - 枠、罫線、番号、区切りは、情報を表すときだけ使う。番号は中身に順番があるときだけ
  - 道しるべ：今どこにいるか、どこへ行けるか、どう戻るかが分かるようにする
  - すりガラスを使うなら、半透明を重ねず、ぼかしの上の文字は太めにしてコントラストを上げる。グラデーションを使うなら、色の止まる位置を増やして段差を出さない
  - 品質の下限：スマホの幅まで崩れない、フォーカスが見える、本文のコントラストは 4.5:1 以上。押せる所は、顧客向けの画面とスマホの幅では 44px、業務の画面では 24px を目安にする
- 顧客向けの領域の最初の画面と、紹介のページだけ：見出しや大きな見た目（ヒーロー）、尖った見た目を最初から外さない（だめかどうかは人が決める）。大胆さは 1 か所に使い、ほかは静かにする。描き終えたら、飾りを 1 つ外す（手続きの画面には当てない）
- お手本の画像があれば、構成の水準（最初の画面の強さ、区切り方、余白）を比較する。お手本の製品の形、絵、文、色の組み合わせは写さない
- 人の直しから決めたこと（`_tech/design.yaml` の `decisions`）に従う

## 共通部品
領域の画面に共通で、具体例の値を持たない所（ヘッダー、ナビゲーション）は、共通部品にして読む。具体例の値を持つ所（一覧の行、知らせ、入力の値）は共通部品にしない（レビューと作る役が、画面例のファイルで値を読めるように）。
- 共通部品は `project/<共通部品の名前>.dc.html`（例：`staff-header.dc.html`）に書き、見た目の規則は `project/<共通部品の名前>.css` に書く。共通部品の `<head>` は画面の元と同じ（`support.js`、tokens.css、base.css）にし、共通部品の `<helmet>` で書体と共通部品の CSS を読む
- 画面の元と画面例は、共通部品の所を `<dc-import name="<共通部品の名前>" hint-size="<幅>px,<高さ>px"></dc-import>` の 1 行にし、`<helmet>` で共通部品の CSS も読む
- 画面ごとに違う所（今いる画面の印）は、読む側が属性で値を渡し（`<dc-import name="staff-header" breads="page">`）、共通部品の中では差し込みでその値を受ける（`aria-current="{{breads}}"`。渡さない画面では付かない）。共通部品の中の差し込みは、この値を受けるためだけに使う
- 共通部品の文にも `data-text` を付け、画面文の一覧に載せる（texts-sync は共通部品のファイルからも文を戻す）。前からある文を共通部品に移すときは、画面文の一覧の行の id を変えない（作る役のコードが id で文を取っているため）
- 共通部品は、`canvas.json` の boards に、title を「共通部品：<何の部品か>」、大きさを共通部品の大きさにして載せる。人が画面例の上で共通部品を選ぶと、キャンバスはこの artboard を開くよう案内し、直しは共通部品のファイルに入る
- 共通部品を足すか変えたら、screen-changes.yaml の `parts` に領域ごとに載せる（`{ area, name, change }`。name は `.dc.html` を除いたファイルの名前）。それを読む画面の元と画面例は、そのために screens に載せない（読む画面の数だけ同じ変化を見せないため）。mock-render が、共通部品の artboard と、それを読む代表の画面の元を撮る（代表は、その領域の screens に載る画面のうち読むものの先頭、無ければ requirements.yaml の screens の順で最初に読む画面）。プロダクトリードが、この 2 枚を画面のレビューと人に見せ、読む画面の変化は、作った後に検証とコードレビューが「共通部品で変わった画面」としてまとめて見る
- 共通部品は領域のキャンバスごとに置く（ほかの領域のキャンバスの共通部品は読めない）。領域をまたぐもの（スタッフの画面のナビゲーション）は、領域ごとに同じ名前と同じ中身で置き、文は `_tech/texts.yaml` の同じ行を使う
- 名前：同じ名前の共通部品は、どの領域でも同じ中身の同じ部品とみなす（mock-render が中身をそろえて確認し、承認のページと Gate 2 は名前ごとに 1 回だけ見せる）。中身の違う共通部品には、領域をまたいで違う名前を付ける（例：顧客の画面のヘッダーは `site-header`、スタッフの画面のヘッダーは `staff-header`）
- 領域をまたぐ共通部品を変えたら、同じ回に、それを置くすべての領域の写しを同じ中身に直して公開し、`parts` に領域ごとに載せる（前のチケットの領域の画面が、古い共通部品のまま残らないように）。その領域でも 0 を行う。同じ名前の共通部品の中身が領域で違うと、mock-render が止まる

## 写して描く
- 画面例は、画面の元か近い画面例を写し、その具体例で違う行（知らせの文、一覧の行、入力の値、題名）だけを置き換えて作る。写すのと置き換えるのを 1 つのスクリプト（Python など）でまとめて行い、画面例ごとに置き換える行の組を並べる（写したファイルを 1 枚ずつ Read と Edit で直さない）。画面例を初めから書かない
- 同じ直しを何枚にも入れるとき（列を足す、文をそろえる）も、スクリプトで一度に入れ、1 枚ずつ Edit しない
- スクリプトは scratchpad に置く（リポジトリに置くと、書き込み範囲の外になるか、成果物としてコミットされる）
- Design の型の「ファイルは 1 つずつ書いて送り、スクリプトで作らない」決まりより、このスキルを先にする

## 動き
動きのある画面を描くときだけ当てる。描く前に、このスキルのフォルダの `motion.md`（`.claude/skills/screen-mock/motion.md`）を読む。

## 描いた画面を確認する
作る回と直す回（2 を含む）で、公開と screen-changes.yaml の更新の後に、`node .claude/aidd/bin/mock-render.mjs <チケット> --out <scratchpad>/mock-check --only <その回に描いた artboard>` を流す（リポジトリの `results/` には書かない）。`--only` には、その回に描いたか直した artboard のファイルの名前（`.dc.html` を除く。例：`SCR-list--AC-register-1`）か、画面の ID（例：`SCR-list`。その画面の、このチケットに載っている artboard をすべて撮る）をカンマで区切って渡す。画面の CSS を変えた回は、その画面の ID を渡す。共通部品を変えた回は、その共通部品の名前（例：`staff-header`）も渡す（共通部品の artboard と代表の画面の元を撮る）。

- `mock-check.json` に、文字が枠に収まっていない所（はみ出し、切れ）が画面ごとに出る。`text-overflow: ellipsis` でわざと省いたもので、省いても具体例の結果が読み取れるものは直さなくてよい
- その回に描いた artboard の PNG を Read で見て、はみ出し、切れ、`var(--…)` でない色や間隔、上の「業務の画面の細部」に反する所を探す
- 見つけたら直して公開し直し、もう一度流す。直すのは多くて 2 回までにし、残ったものは報告に書く
- mock-render が止まったら（ランタイムの写しが無い、など）、0 をやり直してから流す。コマンドが止められたら、報告に書いて返す（プロダクトリードが代わりに流す）
- 人が求めない限り撮って確認しない、という Design の型の決まりより、このスキルを先にする

## デザインシステムの値を変える
今ある値か土台の CSS で画面の意図が描けないとき（画面のレビューの指摘か人のコメントで求められたときも。画面のレビューの直す範囲が all のときを含む）、デザインシステムの値か土台の CSS（base.css）を足すか変えてよい。変える前に、このスキルのフォルダの `ds-change.md` を読み、その手順で行う。

## 2. コメント、人の答え、レビューの指摘の直し
プロダクトリードが渡した直しを、1 と同じ手順（先に読む、描く、公開する、確認する）で入れる。人が頼んだ見た目の直し（Gate 1 と Gate 2 のコメントと答え）と、1 の 3 と「3. 写しを取る」で見つけた人のキャンバスの見た目の直しは、ほかの画面にも効く決めごとなら、`_tech/design.yaml` の `decisions` に 1 行ずつ書く（何をどうするかと、きっかけ。例：「一覧の行の高さは詰めない（Gate 1 で人が直した）」）。次の画面から従う。要件にかかわる直し（項目、操作、メッセージを変える）は描かずに、報告に「要件にかかわる」と書いて返す（仕様担当が要件に入れてから、もう一度呼ばれる）。デザインシステムの値が原因の指摘は、今ある値で直せるなら直し、直せなければ「デザインシステムの値を変える」。

画面のレビューの指摘は、直す範囲（`fix_scope`）に合わせて、直す所を選ぶ。直す範囲より狭い所で直さない（同じ崩れが、次に描く画面例に残るため）。
- example（この画面例だけ）：その画面例のファイル（`<helmet>` の `<style>` か要素）
- screen（この画面のすべての画面例）：画面の CSS（`<SCR の ID>.css`）。その画面のすべての画面例にそろって効く
- part（この共通部品を読むすべての画面）：共通部品のファイルか共通部品の CSS（「共通部品」のとおり parts に載せる）
- all（すべての画面）：デザインシステムの土台の CSS か値（「デザインシステムの値を変える」）
画面のレビューの指摘は `decisions` に書かない（次の画面でも同じにすることは、画面の CSS か土台の CSS に入る。`decisions` は、人の好みのように AI が推し量れないことの記録にする）。

## 3. 写しを取る（段 2 の人の番と相談の終わり、Gate 2 で伝えられたとき）
変える領域（このチケットの screen-changes.yaml の screens と parts に載る領域。共通部品だけを変える領域も入る）のキャンバスを `read` で読み、`project/` に書き写す（画面の元、画面例、共通部品の `.dc.html` と、画面の CSS と共通部品の CSS）。続けて `node .claude/aidd/bin/texts-sync.mjs <領域>` を流し、人がキャンバスで直した文を画面文の一覧に戻す（写しの前のモックと比較して、今回変わった文だけを戻す。変わった texts.yaml も成果物に含める）。同じ文を使うほかの artboard が古い文のままと出たら、その artboard の文をそろえて公開し直し、`project/` にも写す。一覧に無い文が出たら、行を足す。2 通りに直された文は、報告に書く（どちらにするかは人が決める）。値の入る所（`{名前}`）の形に合わない直しは、値の入る所を残して一覧の文を直し、報告に書く。`proto-` で始まるファイルは写さない。サーバーが写したデザインシステムのファイル（`project/ds/`）は写さない（リポジトリの写しは mock-render が `_tech/ds/` の正本から写す）。git は使わず、読んだ中身と `project/` の今のファイルを比較して、人の直しを見つける。見た目だけでない直しがあれば、報告に書く。人がキャンバスで選んだ値は、写しの形のまま正とする（デザインシステムの色を選べば `var(--…)`、自由に選べば値で書かれる）。

## 4. 動く試作
人が求めたときだけ作る（プロダクトリードが動く試作の回と伝える）。作る前に、このスキルのフォルダの `prototype.md` を読む。

## 公開が断られたとき
「新しい版を読んでいない」で断られたら、人がキャンバスを直接直した。`read` で読み直し、人の直しを `project/` に書き写し、続けて `node .claude/aidd/bin/texts-sync.mjs <領域>` を流して人が直した文を画面文の一覧に戻してから（変わった texts.yaml も成果物に含める）、自分の直しを重ねて公開し直す（公開したファイルだけが置き換わる）。

## 終わったとき
報告に、キャンバスの URL、描いた artboard、消した artboard、足すか変えた共通部品（領域ごと）と画面の CSS、画面のレビューの指摘ごとに直した所（画面例、画面の CSS、共通部品、土台の CSS のどれか）、画面文の一覧に足した文と変えた文、texts-sync で戻した文、書き足した具体例の無い画面の状態、見つけた人の直し（あれば。見た目だけか、見た目だけでないか）、自分での確認で直した所と残った所、デザインシステムの値を変えたとき（`ds-change.md` の 4 のとおり）を書く。
