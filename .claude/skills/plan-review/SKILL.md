# plan-review

## 使う役
reviewer

## 読むもの
- `specs/<チケット>/plan/implementation-plan.md`、`plan/details.yaml`
- 承認した仕様の差分（`specs/<チケット>/results/spec-diff.json`）と、変える領域の `specs/_current/<領域>/requirements.yaml`
- 仕様の差分が無いチケット（不具合の修正、依存の版の更新）では、壁打ちのメモ（`hearing/brainstorm.md`）の直し方と壊れている具体例
- `specs/_current/_tech/`（architecture.md、write-scopes.json）、`specs/_notes/`、今のコード
- 前のチケットの `plan/details.yaml` のうち、このチケットで変える領域にかかわる決め事
- 画面のあるシステムでは、計画が触る画面のキャンバスの写し（`specs/_current/<領域>/mock/project/`）
- 計画を書き足した後の確認でも計画の全体を見る。プロダクトリードが伝える書き足しの前のコミットからの差分は、まず見る所の手がかりにする

## 見るもの
- テストが呼ぶ形が、仕様の結果の写し方と基盤の構成（architecture.md）に沿っているか。どの具体例も、その形で確認できるか
- 計画の決め事に理由があり、仕様の結果の写し方やライブラリの既定から外れる理由が成り立つか。plain が何を決めたかを CLAUDE.md の「守ること」の 10 のとおりに伝えているか。前のチケットと同じ決め事を same_as で指していて、architecture.md の「仕様の結果の写し方」にまだ無ければ、そこに足す候補として指摘する（small）
- 変え方の方針が成り立つか
- 前のチケットの決め事と食い違う（前の決め事を変える）のに、replaces でその決め事を指していない決め事は、書き漏れとして指摘する（仕様の全体のページで、変えられた古い決め事が今のもののように並ぶため）
- 作る順番の分担で、各ファイルが書く役の書き込み範囲（`_tech/write-scopes.json` と、コアが決める置き場所（`.claude/aidd/lib/scopes.mjs` の CORE）の和）に入っているか。Red の前に要るものと、作りに合わせて変わるテストの設定の直しが、テストを書く役の分担に入っているか（作る役はテストの設定とテストの支えを変えられない）
- 過剰（要らない一般化、使われない作り込み）
- 画面のあるチケット（`specs/<チケット>/screen-changes.yaml` がある）では、足すか変える画面ごとに、画面の道（`plan/details.yaml` の `screen_paths`）と、撮るテスト（名前と撮る幅。implementation-planning の「撮るテスト」）が決めてあるか
- 決まった手順のある処理、標準の仕様、セキュリティにかかわるものを自前で作るなら、参照した実装と選んだ理由が計画の決め事にあるか。技術の選択に無い新しいライブラリを計画が入れていないか（入れていたら target: spec。技術の選択は仕様担当が決めるので single_answer: true）
- 関係する `_notes` の事実を、方針に反映しているか（取りこぼしは large）。同じチケットの中で、最初の計画より後に書かれた `_notes` は除く（作る途中で分かって書かれたメモで、その場で直してあることが多い。計画を直す回でも同じ）
- 影響の一覧（status.yaml の affects）が空でないときは、変え方の方針に、一覧の各行への影響が書かれているか
- 画面のあるシステムで、計画の決め事が画面の見た目（列の幅、並び、部品の形）をモックと違えるなら、target: mock、medium 以上で指摘する（キャンバスが画面の見た目の正なので、差が小さくても Designer に描き直させる）
- 仕様の穴（具体例どうしが両立しない、業務で答えが変わりうる場面の具体例が無い）に気づいたら、計画が決め事で埋めていても target: spec で指摘する。`where` の要件の ID と `single_answer` は、定義（reviewer.md）の「重大度と直す先」のとおりに書く

重大度と直す先は、定義（reviewer.md）の「重大度と直す先」のとおり。

## 書くもの
`specs/<チケット>/reviews/plan/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形、指摘の ID は、定義（reviewer.md）の「役割」のとおり）。
