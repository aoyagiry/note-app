# review-step-back

## 使う役
reviewer

## 読むもの
- 同じ連なりの前の回のレビューの結果（プロダクトリードがファイルを伝える）
- 各回の直しの差分（プロダクトリードが伝えるコミットの範囲を git で見る）
- レビューの対象の今の中身と、その種類のレビューのスキル（spec-review、plan-review、test-review、code-review、screen-review のどれか。観点と直す先の決まりはそれに従う）

## 見るもの
指摘に 1 件ずつ答えず、往復の全体を見る。
- 同じ種類の指摘が、場所を変えて出ていないか
- 前の回の直しから、新しい指摘が出ていないか（指摘ごとに、元からの問題か、前の回の直しから生じたものかを分ける）
- 直すたびに、決まり、分岐、例外、説明が足され、消すものより多くないか
- 確認していない前提（ツールの細かい振る舞い、読み手や使われ方の推測）に頼っていないか。確認できるものは、ファイル、記録、git で確認する

そのうえで、対象が何のためのものかから見て、指摘を「目的が崩れるもの」と「不便なだけのもの」に分ける。

## 書くもの
`specs/<チケット>/reviews/<種類>/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形は、定義（reviewer.md）の「役割」のとおり）。cycle と mode はプロダクトリードが伝えたとおりに書く（mode は step-back）。
- verdict に、根の原因を 1〜2 文で書く
- 根の原因の指摘は 1〜2 件にまとめる。fix には、根の原因を解く 1 つの直し方を書く。足すより、消す、まとめる、前提を確認する、を先に考える
- それとは別に、根の原因で解けない前の回の残りの指摘のうち、目的が崩れるものは、消さずにそのまま載せ直す。不便なだけのものは、仕様のレビューでは載せ直さず（重大度を付けないため）、ほかのレビューでは small で載せ直す
- 根の原因が人の判断（業務の要件）にあるなら target: spec にする。仕様のレビューなら、問いにさせる直し方を書く。ほかのレビューなら、`where` の要件の ID と `single_answer` を、定義（reviewer.md）の「重大度と直す先」のとおりに書く
- 根の原因が、ある種類の場合が回ごとに 1 つずつ見つかることなら、その種類に名前を付けて `kind` に書き、fix に、その種類を 1 つの決まりで扱う直し方を書く。振る舞いを狭めればその種類の場合がまるごと要らなくなるなら、その狭める案も fix に書き添える（狭めると利用者にできることが減るので、狭めるかは人が決める。spec-hearing の「狭める問い」にさせる）
