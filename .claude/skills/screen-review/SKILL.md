# screen-review

## 使う役
reviewer

## 読むもの
- プロダクトリードが渡す、見る PNG の一覧（`<git の共通の場所>/aidd/tmp/<チケット>/screen-review-list.json` の、渡された番号の組の `files` と `consistency`）。一覧の PNG（`specs/<チケット>/results/mock/` にある）を、すべて Read で画像として開く。1 回の応答で 5〜6 枚ずつ、Read を並べてまとめて開く（1 枚ずつ開くと、手数の上限に届いて結果を書けずに止まる）。ほかの読みもの（下の YAML、JSON、CSS、.dc.html）も、分かっているものはまとめて開く。一覧の外の PNG は、mock-check.json で文字が収まっていない所が出たものだけ、場所を確認するために開いてよい。PNG は、キャンバスと同じ Design のランタイムで描いて撮ったもの
- `specs/<チケット>/results/mock-check.json`（mock-render が、すべての幅の画面ごとに、文字の要素が枠に収まっていない所を測ったもの。kind ははみ出し、切れ、切れ（…で省略））
- `specs/<チケット>/screen-changes.yaml`（描いた画面と画面例と、変えた共通部品の一覧）
- `specs/_current/_tech/design.yaml`（デザインシステムの値）
- 変える領域の `specs/_current/<領域>/requirements.yaml`（具体例の文）
- 変える領域の `specs/_current/<領域>/texts.yaml` と `specs/_current/_tech/texts.yaml`（画面文の一覧）、`_tech/design.yaml` の `text_rules`（言葉づかいの決まり）
- `specs/_current/_intent/intent.yaml`（使う人。顧客向けの画面かを判断する）と、お手本の画像（`git rev-parse --git-common-dir` の下の `aidd/references/design/`。あれば）
- 一貫を見るために、同じ領域のキャンバスの写し（`specs/_current/<領域>/mock/project/` の .dc.html と、画面の CSS と共通部品の .css）と、デザインシステムの土台の CSS（`specs/_current/_tech/ds/<フォルダ>/base.css`）

## 見る範囲
すべての PNG は開かない。プロダクトリードが `screen-review-list.mjs` で一覧を作り、組の番号と一緒に渡す。主の幅は、領域の `mock/canvas.yaml` の widths の先頭（無ければ breakpoint の最初の幅）である。
- 1 回目：このチケットで足すか変える画面の元、画面例、モックだけの画面を、すべて主の幅で見る。もう一方の幅は、画面の元と長い値の画面（`variant: long`）だけを見る。変えた共通部品の artboard（`<領域>--<共通部品の名前>.png`）と、それを読む代表の画面の元も入る（共通部品は 1 回だけ見て、読む画面例ごとには見ない。領域をまたぐ共通部品は同じ中身なので、artboard は最初の領域の 1 枚だけで、代表の画面の元は領域ごとに入る）
- 2 回目から：前の回の指摘が指した画面例（直し方によらない）、直した画面例、画面の CSS を直した画面の画面例、直した共通部品の artboard と代表だけを、主の幅で見る
- 一覧が組に分かれたとき（見る PNG が 30 枚を超えた）：自分の組の画面を見る。組の `consistency`（ほかの組の画面の元の主の幅）も開き、画面をまたぐ一貫だけを見る。ほかの組の画面への指摘は、一貫の崩れだけにする
- 文字のはみ出しは、mock-check.json がすべての幅を測っている。一覧に無い幅で出たものも指摘する

## 見るもの
| 観点 | 見ること |
| --- | --- |
| 具体例の結果が読み取れる | 画面例で、then の結果（予約あり、知らせ、など）がひと目で分かるか。`also` にまとめた具体例が、本当に代表と同じ見た目になるか（知らせの文や部品が違わないか、値の長さが大きく違わないか） |
| 見た目の優先順位 | 最初の 2 秒で目が行く所が、その画面でいちばん大事なものか。画面の目的がすぐ分かるか。主な操作と結果が目立ち、読む順が自然か。押せる所が押せると分かるか。強調が色だけに頼らず、大きさと太さと余白で作られているか |
| 開いたときの見え方 | 画面の元に最初の 1 画面の画像（`<名前>--top.png`。画面の下に固定した部品があり、ページが画面より高い画面）が添えてあれば、それで開いたときの見え方を見る（全体の画像は、固定した部品をページの下端に置いて撮ってある） |
| まとまりと道しるべ | 近いものがまとまり、関係の無いものが離れているか。余白が足りずに詰まっていないか。枠、罫線、番号、区切りが、情報を表さずに飾りになっていないか。今どこにいるか、どこへ行けるか、どう戻るかが分かるか |
| 顧客向けの画面 | 顧客向けの画面か（使う人から判断する。印は無い）を決めてから見る。一覧が空のとき、送れなかったとき、初めて使うときが、具体例か `unexampled` にあるか。読み込み中と長い値のモックだけの画面（`variant`）があり、長い値で文字が収まっているか。お手本の画像があれば、構成の水準が届いているか、お手本に似すぎていないか（形、絵、文、色の組み合わせを写していないか） |
| 細部の整い | 揃え（画面の中の左端と右端が 1 本ずつか）、部品の内側の余白（記号や文字が枠に近すぎないか）、同じ並びの間隔、文字が枠に収まっているか（mock-check.json を根拠にし、PNG で場所を確認する）、表の何の行かを示す列が切れていないか、数字と時刻の桁がそろっているか、ラベル（状態のタグ）が縮んだり 2 行になったりしていないか。業務の画面でも、長い値のモックだけの画面（`variant: long`）で文字が収まっているか |
| 一貫 | 同じ部品が、画面どうしと同じ領域の前からある画面で、同じ見た目か。色、文字、間隔、角の丸みがデザインシステムの値か（.dc.html、画面の CSS、共通部品の CSS で `var(--…)` でない値は、デザインシステムの外の値として見る。ただし人がキャンバスで直した値と、ほかの幅で見せる artboard の枠の幅は除く）。折り返し、操作の応答、入力の部品の形を、土台の CSS（base.css）に任せずに画面の CSS で書き直していないか |
| 文 | 画面の文が、言葉づかいの決まり（`text_rules`）と仕様の言葉（同じものを同じ名前で呼ぶ）に合っているか。要件の文の言い回しがそのまま画面に漏れていないか（硬い、長い、業務の決まりの言い方）。ボタンが押すと何が起きるかを言っているか。失敗の知らせが何が起きたか、なぜか、どう直すかを言っているか |
| アクセシビリティ | 文字と地のコントラスト（デザインシステムの値から計算する。本文は 4.5:1 以上、大きい文字は 3:1 以上）、押せる所の大きさ（顧客向けの画面とスマホの幅では 44px、業務の画面では 24px を目安）、文字の大きさ、色だけで区別していないか |

見るのは、このチケットで描いた画面と変えた共通部品（screen-changes.yaml に挙がったもの）だけにする。キャンバスの写しの今の形は、前のチケットで承認されたか、人がキャンバスを直接直した、正の見た目である。一貫はそれにそろっているかで見て、写しの形を変えるよう指摘しない。

見ないもの：振る舞い、項目（仕様の要件と具体例が決める）、好みの問題、動き（フォーカス、キーボードの操作。静的な PNG では見えない）。

## 指摘の書き方
- 直し方の案は、配置、大きさ、色の強さ、デザインシステムのほかの値で書く。説明の文や補助のラベルを足す案は、配置で直せないときだけ出す
- 重大度の目安：具体例の結果が読み取れない、コントラストが足りない、押せる所が小さいは large。細部の整いと一貫の崩れは medium。好みに近いものは small。直す先は target: mock（Designer が直す）。デザインシステムの値が原因と見たもの（色の組み合わせのコントラストなど）も、同じ目安で target: mock にし、what に「デザインシステムの値が原因」と添える（Designer が、今ある値で直すか、値を変えるかを決める）
- 文字が枠に収まっていない所は、具体例の結果が読み取れなくなるなら large、そうでなければ medium。`text-overflow: ellipsis` でわざと省いたもので、省いても具体例の結果が読み取れるものは指摘しない
- 振る舞いにかかわるもの（具体例の then が画面に描けない、など）は target: spec にする
- 根拠（`where`）は、PNG の名前（例：`reservations--SCR-book--AC-no-overlap-1--desktop.png`）で始め、続けて画面の中の場所を書く（プロダクトリードが、次の回に見る PNG をこの名前から決める）
- target: mock の指摘には、直す範囲（`fix_scope`）を書く。この画面例だけ（example）、この画面のすべての画面例（screen）、この共通部品を読むすべての画面（part）、すべての画面（all）。同じ崩れがほかの画面例や画面にも出うるなら（同じ部品、同じ並び、同じ種類の入力の部品）、広い方にする。Designer は、これに合わせて、画面例の中、画面の CSS、共通部品、デザインシステムの土台の CSS のどこを直すかを選ぶ

## 書くもの
`specs/<チケット>/reviews/screen/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形は、定義（reviewer.md）の「役割」のとおり。組に分けたときも、組ごとに次の番号で書き、cycle は同じ）。指摘の ID は SC で、前の回とほかの組のファイルから通し番号にする。`opened` に、開いた PNG の名前をすべて書く（一覧の外で開いたものも。プロダクトリードが一覧と突き合わせ、開いていない PNG があれば、もう一度頼む）。
