# spec-review

## 使う役
reviewer

## 読むもの
- 仕様の全体（どの回も全体を見る）。2 回目からは、プロダクトリードが伝える前の回からの差分（`git diff <コミット> -- specs/`）を、まず見る所の手がかりにする
- `specs/<チケット>/hearing/brainstorm.md`、`hearing/questions.yaml`、`specs/_current/`、`specs/ticket-plan.yaml`
- `specs/<チケット>/results/spec-diff.json`（uses でたどった影響）と `specs/<チケット>/status.yaml` の affects（今あるものへの影響の一覧）

## 見るもの（5 つだけ）
1. **業務で実際に起きる場合の漏れ**：その場合が業務のどんな場面で起きるかを `scene` に書く。書けなければ指摘しない。細部や極端な場合（文字列の "8" を数として読むか、24 時間ちょうど）は指摘しない（計画とテストの段で扱う）。要件が共通の要件（`_shared/rules.yaml`）を uses で指していれば、その種類の場面（返事が届かない、入れ忘れ など）を、操作ごとの漏れとしない（共通の要件の代表の具体例とテストで扱う）。共通の非機能要件のうち確認の仕方が test と human のもので、この操作に当てはまるものを、要件が uses で指しているかも見る。画面のあるシステム（`_tech/design.yaml` がある）では、このチケットで足すか変える画面が、領域の `screens` に載っているかも見る（`mock/` は読まない。見た目は Designer の受け持ち）
2. **チケットの中の矛盾**：両立しない要件や具体例
3. **前の仕様とのぶつかり**：既存の振る舞いを変えるとき、テストの無い要件とぶつからないか、どちらを優先するかが人に問われているか。影響の一覧が空でないときは、一覧の各行について深く見る
4. **根拠の無い要件**：壁打ちのメモにも問いの答えにも根拠が無く、問いも書かれていない要件。AI が範囲を超えて共通の要件などを変えていないか（「ついでに」の広がり）。人が話していない操作、画面、データを足す範囲の広げが、問いの答えの前に仕様に書かれていたら指摘し、直し方は、仕様から外して問い（`widens: true`）の含める選択肢の effect に回す、と書く。同じ種類の場面を共通の要件にまとめるのは、領域ごとの振る舞いが同じなら根拠の無い要件としない。領域ごとに振る舞いがそろっていない（前の答えが割れている）のに、そろえ方を問わずにまとめていたら指摘する
5. **過剰**：答えが 1 つに決まる当たり前の具体例。テストか計画の決め事に移すよう指摘する。同じ種類の場面の具体例を操作ごとに書いていたら、過剰として、共通の要件と代表の具体例にまとめるよう指摘する（spec-hearing の 2）。共通の要件の代表の具体例は、過剰としない。ただし、Designer の挙げた具体例の無い画面の状態（`specs/<チケット>/screen-changes.yaml` の `unexampled`）から足した具体例は、画面に見える結果なので指摘しない。承認の後に見つかった具体例の無い場面（レビューの target: spec など）から足した具体例も、テストで守るために足したものなので指摘しない。断られた後に直してもう一度送ると受け付けられる具体例（spec-hearing の 2 の「やり直しの具体例」）も指摘しない

あわせて、仕様に作りの細部の言葉（状態コード、パス、欄の名前、応答の形）が混ざっていないか（決まった呼び名のある技術の言葉は CLAUDE.md の「守ること」の 10 のとおり指摘しない。言い換えで意味が変わった所は指摘する）、具体例の結果の語が仕様の結果の写し方（architecture.md）にそろっているかを見る。

## 種類で挙げる
指摘が、ある種類の場合の 1 つに当たるとき（例：「頼んだ時点で前提が変わっていたとき」の 1 つとして、頼んだ後に日が切り替わった）は、その種類に名前を付けて `kind` に書き、同じ回のうちに、その種類に入る場合をまとめて `kind.cases` に挙げる。場合ごとに指摘を分けず、1 件の指摘にする。挙げるのは、業務で実際に起きる場合（場面を書けるもの）だけにする。直す側は、場合ごとに決まりを足さず、その種類を 1 つの決まりで扱う（spec-hearing の「レビューの指摘を直すとき」）。

## 前の回の直しから生じた指摘
2 回目からの回では、指摘ごとに、元からの問題か、前の回の直し（プロダクトリードが渡す前の回からの差分）から生じたものかを分ける（review-step-back の「見るもの」の 2 つ目と同じ分け方）。前の回の直しから生じたと判断したら、その回のうちに、review-step-back の「書くもの」の書き方で書き、その回の結果に `from_previous_fix: true` を書く。verdict に根の原因を 1〜2 文で書き、根の原因の指摘を 1〜2 件にまとめ、fix には足さない直しを 1 つ書く（消す、まとめる、前提を確認する、を先に考える）。前の回の直しから生じていない元からの指摘は、ふつうに並べる。cycle はプロダクトリードが伝えたまま書き、mode は書かない（この回も往復の 1 回に数え、上限の 1 つ前の一歩引いた見直しは別に行う）。

## 流れのチケットのとき
自分のチケットが流れのチケット（ticket-plan.yaml の行が、複数の領域を通る操作を確認するもの。spec-hearing の「流れのチケット」）なら、前のチケットのテストが、結果を作る側も受ける側も画面で操作して通したつなぎ目を、漏れとして指摘しない（同じことを重ねて確認しないため）。要件と具体例を書かずに、チケットを閉じる案だけを問うている（`hearing/questions.yaml` に about が `TICKET/<チケット>` の問いがある）なら、上の 5 つは見ない。その問いの background の根拠（どのつなぎ目を、前のどのチケットのどのテストが画面の操作で通したか）が、テストのとおりかだけを見る（テストの名前の具体例の ID で Grep し、テストを開いて確認する）。根拠が合わないつなぎ目があれば、まだ通していないつなぎ目として、場面を書いて指摘する

## 000 のとき（後半の前から）
最初は `_intent` も含めた全体を見る。チケットどうしの範囲の重なり、どの目的も、どれかのチケットか later が担っているか、どの主な操作も、どれかのチケットか later か作らないものに入っているか。上の 5 つのうち当てはまるものは、範囲の境目（その操作を作るか、どのチケットに入れるか）の高さで見る。操作の中の細部（ある場合にどう振る舞うか、選べる範囲、知らせ方）の漏れは指摘しない（そのチケットのヒアリングで決める）。壁打ちのメモで人が話した細部が、どのチケットの範囲にも「このチケットのヒアリングで決める」として回されていないときだけ、回すよう指摘する。

## 001 のとき
- テスト駆動を回せるか（テストのレベルと道具、0 件でも成功、結果を JUnit XML で出す）
- 決める項目がそろっているか（foundation-hearing の確認の一覧）
- 非機能要件を、決めた技術で満たせ、確認できるか
- 作る役がテストとテストの設定を書けない範囲になっているか
- 書き方の決まりを道具で確認し、git の hook を使わないか
- 選んだ技術の妥当性（非機能要件を満たす見込み、ライブラリの保守とライセンス（出典を開いて確認する）、レイヤと依存の向き、セキュリティの構成）
- 目的に照らした選択：技術の土台（`_tech/tech.yaml` と `_tech/architecture.md`。構成とレイヤの切り方も含む）が、`_intent` の目的、使う人と量、`ticket-plan.yaml` の先のチケット、非機能要件に照らして、ほかに取りうる案（書かれていない案も含む）より良いか。指摘するのは、後から変えると作り直しが大きいか、目的や非機能要件に効く選択で、より良い案の名前と、どれに照らして良いかを書けるときだけにする。使う人と量、先のチケットに見合わない構成（重すぎても軽すぎても）と、選ばなかった理由が目的や非機能要件の言葉で書かれていないものも指摘する。直す側は、その案に選び直すか、選ばなかった案に足して理由を書く（畳んであった選択なら、開いて見せる）
- 開いて見せるべき選択が畳まれていないか、技術の言葉が CLAUDE.md の「守ること」の 10 のとおりか。指摘するのは、言い換えで意味が変わった所（例：アクセシビリティの検査を「見やすさの検査」と書いた。読み上げも調べるので見やすさより広い）と、決まった呼び名やライブラリの機能の名前だけで済ませ、何が起きるかを書いていない所。決まった呼び名をそのまま使った所は指摘しない

## 出典
外の事実に頼る要件と技術の選択は、出典を開いて確認する。ライブラリは Context7 を先に使う。

## 書くもの
`specs/<チケット>/reviews/spec/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形、指摘の ID は、定義（reviewer.md）の「役割」のとおり）。
直す先（target）は spec。直し方の案（fix）は決まりの単位で書き、場合の文を足す案を出さない（場合ごとに文を足すと、足した文から次の指摘が出るため）。

## しないこと
- 目指さないこと（わざと回り込む AI を防ぐこと、何人かで同時に使うときの重なりを先回りして防ぐこと、極端な場合への備え、監査に耐える記録）を求める指摘
