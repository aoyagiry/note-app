# overall-hearing

## 使う役
specification

## 読むもの
- `specs/000-overall/hearing/brainstorm.md`（人が確認した壁打ちの言い直し。根拠にしてよいのはここと人の答えだけ）
- `specs/_references/`（人が置いた参考資料。あれば）
- プロダクトリードが伝える回（前半か後半か）と、前の回の答え

## 前半：何を、なぜ、誰が、どこまで
`specs/_current/_intent/intent.yaml` を、`.claude/aidd/templates/system-intent.yaml` の形で書く。
- `goals`：システムの目的と実現の目安（success）。人が決められなければ unsure
- `users`：使う人
- `scope.includes`：使う人ごとの主な操作。`scope.excludes`：作らないもの
- `facts`：前提の事実（名前の ID）
ビジョンがはっきりしない人ほど壁打ちのメモに無い所が多い。メモに無い所は、選択肢で例を見せて問う。参考資料があるかも問いに入れる（メモで分かっていれば問わない）。この段の最後の確認（この内容で一覧を作ってよいか）はプロダクトリードが問うので、書かない。

## 後半：どう分けて、何を共通にするか
- `specs/ticket-plan.yaml`（`.claude/aidd/templates/ticket-plan.yaml` の形）：最初に作る範囲だけを具体的なチケットにし、残りは `later` に名前と理由だけを置く。行の欄は id（3 桁の番号と英語の名前。002 から）、title、purpose、scope（includes、excludes）、depends_on だけ（作ったものを公開して使い始めるチケットを一覧に入れるなら、その行に release: true も付ける）。000 と 001 は書かない。001 を depends_on に書かない
- チケットの分け方の粒度と依存は自分で決め、問わない。問うのは、最初に作る範囲と later の境目、流れのチケット（複数の領域を通る操作を確認するチケット）を足すか（足すなら一覧に入れ、その行を about にして問う）、画面のあるシステムなら層ごとか縦切りか（下の例の形で問う）
- 000 は、範囲の境目（その操作を作るか、どのチケットに入れるか）の高さで書き、問う。操作の中の細部（ある場合にどう振る舞うか、選べる範囲、知らせ方）は、壁打ちのメモにあってもレビューで挙がっても、該当するチケットの scope.includes の行に「（<細部>は、このチケットのヒアリングで決める）」と書き添えて回す
- `specs/_current/_shared/`（rules.yaml と nfr.yaml は、`.claude/aidd/templates/shared-rules.yaml` と `.claude/aidd/templates/nfr.yaml` の形）：001 の技術の選び方に効く非機能要件（速さ、セキュリティなど）と、チケットの分け方に効く少数の横断の要件だけを作る。言葉（terms）は作らない（最初に使う機能のチケットが足す）。当たり前の基準（エラーのとき内部の情報を返さない、など）は問わずに書く。答えが変わりうる基準（脆弱性をどの深刻度まで許すか、応答の速さ。「特に無い」も選べる）は問う
- 非機能要件の `check` は、test、tool、measurement、human のどれか。計測の基準は、測る対象と数を文に書く。human のものは、人が確認する手順（どこを開いて何を見るか）を文に添える。公開の後でないと確認できないもの（店のネットワークの中からだけ開ける、など）は `after_release: true` を付ける（Gate 2 では、公開のチケットまでは畳んだ「公開の後に確認すること」に並び、公開のチケットで人の判断に出る）。tool のものは、どんな道具で何を調べるかを文に書く（001 で、確認する検証のコマンドに結ぶ）

層ごとか縦切りかの問いの例：
> 作ったものを確認するとき、どちらの進め方がよいですか
> ○ 1 つの操作ごとに、画面まで作って確認する（提案）　どのチケットも、終わったときに画面で実際に動かして確認できます。そのかわり、1 つのチケットで作るものが多くなります
> ○ 先に裏側の仕組みを作り、画面は後でまとめて作る　裏側のチケットでは「この入力ならこの結果」の一覧で確認します。画面と裏側を別の人が作るときに向いています

問いは、定義（specification.md）の「問いの書き方」のとおりに書く。人は下書きのページを見ずにチャットで答えるので、どの範囲の話か、選んだら何が変わるかを、問いの文と選択肢の effect に入れる。

レビューの指摘を直すときは、spec-hearing の「レビューの指摘を直すとき」に従う（場合を足す前に考える 3 つと、同じ形を同じ回に直すこと）。

## しないこと
- 技術の選択（001 で決める）。リリースの単位は作らない
- 業務で実際に起きない極端な場合の要件
- 操作の中の細部を、共通の要件や問いにすること（後半で、該当するチケットの範囲に回す）

## 終わったとき
報告に、書いたファイルと、書いた問いの数を書く。
