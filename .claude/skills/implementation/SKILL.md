# implementation

## 使う役
implementer

## 読むもの
- テスト（変えない）、`specs/<チケット>/plan/implementation-plan.md`、`plan/details.yaml`
- 変える領域の `specs/_current/<領域>/requirements.yaml`、`specs/_current/_tech/`（architecture.md、toolchain.yaml）
- 検証で落ちて戻ったときは、プロダクトリードが渡す失敗の出力
- `specs/_notes/` のうち、関係しそうなもの
- 画面のあるチケット（`specs/<チケット>/screen-changes.yaml` がある）では、載っている画面の `specs/_current/<領域>/mock/project/<SCR の ID>.dc.html`、それが読む画面の CSS（`<SCR の ID>.css`）とモックの共通部品（`<dc-import>` の名前の `.dc.html` と `.css`。`parts` に載った共通部品は、このチケットで変えたもの）、`_tech/design.yaml`、デザインシステムの土台の CSS（`_tech/ds/<フォルダ>/base.css`）

## 手順
1. テストを通す最小のコードを書く。テストを流して確認する（toolchain.yaml のテストのコマンド）
2. 通ったまま整える
3. 計画の案内（方針と、作る順番）に従う。外れたほうがよいと分かったら、計画に戻さずに外れてよい。外れた点と理由を報告に書く（コードレビューが判断する）
4. 作りながら細部を決めたら、`plan/details.yaml` に test: false の決め事として足す（by: implementer、plain を書く）。テストが要ると思う細部なら、足さずに止まる（計画への異議）
5. 検証で落ちて戻ったときは、まず実装の不備とみなして直す
6. 最後に `node .claude/aidd/bin/verify.mjs <チケット>` を流す（e2e を含めて長いので、裏に回ることが多い。CLAUDE.md の「サブエージェントの決まり」の長く流れるコマンド）。落ちたら直して流し直す。同じ失敗が limits.same_failure 回（`.claude/aidd/defaults.yaml` と `specs/_current/_tech/harness.yaml` の limits）続いたら、止まって返す（報告に失敗の出力と試したこと）。コマンドがすべて通り、画面のスクリーンショットだけが無くて落ちたときは、直さずに完了で返す（スクリーンショットのテストはテストを書く役が直す）。出力（`results/verify.json`、`results/examples.json`、`results/visual/`、差し替えた見た目の基準）は成果物に含める。流した後にコードを直したら、流し直す（コミットの検査が、verify.json がほかのファイルより後に書かれたかを確認する）。この検証は計測のコマンド（toolchain.yaml の measurement）を流さず、前の計測の結果を残す（計測は 8 で流す）
7. 画面のあるチケットでは、検証が通った後に、このチケットで変えた画面（screen-changes.yaml に載っている artboard。モックだけの画面を除く）の作ったものとモックを見比べる。作ったもの（検証が差し替えた見た目の基準 `specs/_current/<領域>/screenshots/<名前>-<OS>.png`）とモック（`specs/<チケット>/results/mock/<名前>.png`）を、同じ名前（同じ幅）の組で Read で開く。1 回の応答で 2〜3 組ずつ、Read を並べてまとめて開く（1 枚ずつ開くと、手数の上限に届く）。見るのは、主の幅（領域の `mock/canvas.yaml` の widths の先頭）では、画面の元と、このチケットで足すか変えた具体例（`results/spec-diff.json`）の画面例の組、もう一方の幅では、画面の元の組だけにする（前のチケットの画面例を描き直しただけの組は、コードレビューが見比べる）。画面の元に最初の 1 画面の画像（モックの `<名前>--top.png`。画面の下に固定した部品のある背の高い画面）があれば、作ったもの（`specs/_current/<領域>/screenshots/<名前>--top-<OS>.png`）との組も比較する（検証は、最初の 1 画面の画像を変化の並びに入れない）。並び、文言、間隔、色、折り返しのずれを直し、6 の検証を流し直してから 8 に進む。見比べて直すのは 2 回までにし、残ったずれは報告に書く（コードレビューも見比べる）
8. 完了で返す直前に、`node .claude/aidd/bin/verify.mjs <チケット> --measure` を 1 回だけ流す（6 の検証が通り、画面のあるチケットでは 7 も済んだ後。コマンドがすべて通り、スクリーンショットだけが無くて返すときも流す）。計測のコマンドだけを流し、verify.json の計測の結果を書き換える（どの検証が最後になるかは前もって分からないので、返す直前にだけ流す）。計測が基準を満たさずに落ちたら、6 と同じに直し、6 から流し直す

## 書ける範囲
書けるのは、案件の `specs/_current/_tech/write-scopes.json` の implementer の範囲と、コアが決める置き場所（`.claude/aidd/lib/scopes.mjs` の CORE）を足し合わせたものである（write-scopes.json の deny は、どちらにも効く）。作る役のコアの置き場所は次のとおりで、write-scopes.json に無くても書ける。write-scopes.json には足さない（同じ許しが 2 か所になる）。
- `specs/<チケット>/plan/details.yaml`（作りながら決めた test: false の決め事）
- `.gitignore`
- 画面文の一覧 `specs/_current/*/texts.yaml`（行を足す）
- 検証の出力（`specs/<チケット>/results/verify.json`、`results/examples.json`、`results/visual/`）と、検証が差し替えた見た目の基準（`specs/_current/*/screenshots/`）
- `specs/_notes/`（どの役も書ける）

ほかに書きたいものが範囲の外なら、書かずに止まる（CLAUDE.md の「止まるとき」）。

## 判断の決まり
- 要らない場合分け、防御のコード、仕様に無い一般化、使われない作り込みを書かない
- 依存を足すのは、承認した技術の選択（`_tech/tech.yaml`）にあるものだけ。版の範囲（architecture.md）の中の更新はしてよい
- 検証で脆弱性が見つかり、版の範囲の中の更新で直るなら、更新して既存のテストがすべて通ることを確認する。範囲を超える更新や入れ替えが要るなら止まる
- 技術を入れ替えるチケットでは、計画が挙げた `_notes` の事実を確認し、当てはまらなければ廃止する
- 画面の文は、画面文の一覧（`specs/_current/<領域>/texts.yaml` と `_tech/texts.yaml`）から ID で取り、コードに直に書かない。要る文が一覧に無ければ（具体例の無い通信の失敗の文など）、行を足す。今ある行の文は変えない（文を決めるのは Designer と人）。足した行は報告に書く
- 値の入る画面の文は、すべて architecture.md の画面の文を出す部品で出し、値を `<span data-value>` で包む（文字列を返す関数で文を組み立てて出さない。値が包まれず、名前などが行の途中で割れるため）。属性の値（aria-label、placeholder、alt、title など）は除く
- 計画の案内が seed にデータを足すよう書いていたら、toolchain.yaml の `start.seed` のコマンドが入れるデータに、このチケットの画面を開いて試せる架空のデータを足す（テストの準備の関数を使い回してよい。実データは使わない）
- 画面は、並びと文言をモックに合わせ、色、文字、間隔、角の丸みは共通の値（CSS の変数）だけで指定する。値を直接書かない。日本語の折り返し、操作の応答と動き、入力の部品の形は、土台の CSS（base.css の写し）に任せ、画面ごとに書き直さない。振る舞いは要件と具体例に従う。モックと要件と具体例が食い違えば止まる（計画への異議）

## 基盤づくりのとき
雛形（振る舞いを持たず、ライブラリの既定のまま動くもの）、開発環境の定義（toolchain.yaml の setup.files）、CI（architecture.md と foundation-hearing の決まりのとおり）、書き方の決まりの道具の設定を作る（テストの設定とテストの支えは、テストを書く役が書く）。画面のあるシステムでは、`_tech/design.yaml` の値を見た目の共通の値（CSS の変数のファイル）に写し、デザインシステムの土台の CSS（`_tech/ds/<フォルダ>/base.css`）を、architecture.md の置き場所の土台の CSS のファイルに中身のまま写す（基盤の検査の design-base が、中身の一致を確認する）。文節の区切りの手当てと、値の入る所の値を `<span data-value>` で包む画面の文を出す部品（architecture.md）も入れる。マシン全体へのインストールはしない。準備が要るところまで書いたら止まる（開発環境の準備が要る）。

## 止まるとき
- テストが呼ぶ形が成り立たない（計画への異議）
- テストの設定かテストの支えの直しが要る（計画への異議。作る役は変えられないので、テストを書く役に直してもらう）。報告に、直すファイルと、作ったものに合わせて何をどう直すか（例：webServer の起動のコマンドを `npm run dev` に、ポートを 5173 に）を書く。作ったものに合わせてテストの設定だけを直すなら、プロダクトリードは計画に戻さず、実装中のままテストを書く役に直させる
- テストか仕様が誤っているのでは、と思う（テストを変えずに、テストの名前と、具体例と食い違う点を書く）
- 原因は main にマージ済みの別のチケットのコードだと思う
- 環境が原因だと思う（データベースが起動していない、依存が壊れている など）
