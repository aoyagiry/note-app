# code-review

## 使う役
reviewer

## 読むもの
- このチケットの差分（`git diff <マージの基点>`。ロックファイルなどの大きな生成物は除いてよい）
- プロダクトリードが渡す、作る役の報告のうち計画の案内から外れた点と理由、`plan/implementation-plan.md`、`plan/details.yaml`
- 承認した具体例と、`specs/<チケット>/results/verify.json`、`results/examples.json`
- `specs/_current/_tech/architecture.md`、既存のコード

## 見るもの
- **過剰**：要らない場合分け、防御のコード、仕様に無い一般化、使われない作り込み。カバレッジは自分で見られる
- **要る変更か**：目的、計画の案内、プロダクトリードが渡した外れた点と理由、差分を並べ、関係の無いファイルの書き換えが無いか、案内から外れてよかったか
- **テストで見つけられない漏れ**：test: false の決め事と、計画の案内のとおりに作ったか
- **検査を弱めていないか**：CI、開発環境の定義、書き込み範囲、テストの設定を変えたなら、確認することが減っていないか
- **書き込み範囲**：役ごとの書ける範囲は、案件の `_tech/write-scopes.json` と、コアが決める置き場所（`.claude/aidd/lib/scopes.mjs` の CORE）を足し合わせたものである。コアの置き場所は、範囲を指摘する前に scopes.mjs を読んで確認する（検証の出力、見た目の基準、画面文の一覧、`specs/_notes/` などが入る）。コアの置き場所のファイルは write-scopes.json に無くても範囲の中なので、write-scopes.json に足させる指摘はしない（同じ許しが 2 か所になる）
- **ばらつきと既存の API**：前のチケットと同じことを違う形で作っていないか、既存の API の形を変えていないか
- **セキュリティ**：入力の扱い、秘密の情報、内部の情報を外に出さないか
- **画面の見た目**（`specs/<チケット>/screen-changes.yaml` があるとき）：載っている artboard（画面の元と画面例。モックだけの画面を除く）ごとに、作ったもの（検証が差し替えた見た目の基準 `specs/_current/<領域>/screenshots/<名前>-<OS>.png`）とモック（`results/mock/<名前>.png`）を Read で画像として見比べ（名前は `<領域>--<SCR の ID>[--<AC の ID>][--<幅の名前>]`。1 回の応答で 2〜3 組ずつ、Read を並べてまとめて開く。1 枚ずつ開くと、手数の上限に届く）、色、間隔、並び、文言の違いを target: impl で指摘する。画面の元に最初の 1 画面の画像（モックの `<名前>--top.png` と、作ったものの `<名前>--top-<OS>.png`。画面の下に固定した部品のある背の高い画面）があれば、その組も比較する（検証は、最初の 1 画面の画像を変化の並びに入れない）。共通の値（CSS の変数）を使わずに、色や間隔を直接書いた所と、土台の CSS（デザインシステムの base.css の写し）に任せる所（折り返し、操作の応答、入力の部品の形）を画面ごとに書き直した所も指摘する。モックに無い振る舞いの違いは、要件と具体例に合っていれば指摘しない
- **仕様の穴**：承認した具体例の無い場面で起きる不具合（例：ログインの期限が切れた後にログアウトを押すと、何も起きない）は、target: impl でなく target: spec にする。作る役が直すだけだと、具体例とテストが無いまま残るため。`scene` に業務でどんな場面で起きるかを書き、`where` の要件の ID と `single_answer`（今の要件から結果が 1 つに決まるか）を、定義（reviewer.md）の「重大度と直す先」のとおりに書く
- **変えるつもりの無かった画面の変化**（`results/verify.json` の `screenshots.unlisted_changes` があるとき）：このチケットの screen-changes.yaml に載っていない画面の見た目が、main と比較して変わった。行ごとの前、後、差分の PNG（`results/visual/`）を Read で見て、崩れ（重なる、はみ出す、消える、並びが壊れる）か、このチケットの意図した変化の波及かを判断する。崩れなら target: impl で指摘する（作る役が直す）。このチケットの screen-changes.yaml とデザインシステムの値と土台の CSS の変更（`_tech/design.yaml` と `_tech/ds/` の差分）から説明できる変化は指摘しない。指摘しなかった変化は、なぜ変わったかの理由ごとにまとめ、結果の `unlisted_changes` に、理由（人に見せる 1 文。例：スタッフの画面の上の帯に「取り置き」を足したため）とその画面の並び（verify.json の `file`）を書く（どの回も、その回の verify.json のすべての変化を書く）。Gate 2 の受け入れのページは、最後に書いた回の理由ごとに画面をまとめて畳み、要点に枚数と理由を出す。最後は人が判断する
- **共通部品で変わった画面**（`results/verify.json` の `screenshots.part_changes` があるとき）：このチケットで変えた共通部品（screen-changes.yaml の `parts`）を読む画面の変化が、共通部品ごとにまとまって並ぶ（共通部品を読む画面は、違いがわずかでも拾うので、読む画面の数だけ並ぶ）。共通部品の変化そのものは画面のレビューと人が見たので、ここでは崩れ（重なる、はみ出す、消える、並びが壊れる）が無いかだけを、画面（名前の `<領域>--<SCR の ID>` が同じもの）ごとに 1 枚（画面の元の画像があればそれ）の前、後、差分の PNG で見る。崩れなら target: impl で指摘する。共通部品の変化が画面に出ただけのものは指摘しない
- **作業で分かった事実**：このチケットで足した、書き換えた、廃止した `specs/_notes/` の事実が、根拠と合っているか、推測が混ざっていないか、既存の事実と重なっていないか

重大度と直す先は、定義（reviewer.md）の「重大度と直す先」のとおり。

## 書くもの
`specs/<チケット>/reviews/code/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形、指摘の ID は、定義（reviewer.md）の「役割」のとおり）。
