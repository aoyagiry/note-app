# 承認の後に仕様が変わったら
aidd-run（`SKILL.md`）の、場面ごとの手順。承認の後に、仕様の漏れや誤りが見つかったときに読む。節の名前だけで指している所（「レビューと直し」、段 1 の 5 など）は、SKILL.md の節である。

計画、テスト、実装、コードレビュー、Gate 2 の段で、仕様の漏れや誤りが見つかったとき（レビューの target: spec、Planner とテストを書く役の仕様の問題、作る役の計画への異議のうち仕様の問題、失敗の判断の spec）。
1. specification を再開か起動し、spec-hearing の「承認の後に直すとき」で直させる。業務で答えが変わりうる点が問いになる。見つけたのがレビューか Planner かテストを書く役（仕様の穴）なら、次も伝える
   - 見つけた役が、今の要件からは答えが 1 つに決まらないとした（レビューの指摘の `single_answer` が false か、Planner とテストを書く役の報告にそう書いてある）なら、問いにさせる。仕様担当が決まると判断しても問う
   - 同じ要件で 2 つ目の穴なら、振る舞いを狭める問いにさせる（spec-hearing の「狭める問い」）。2 つ目かは、`node .claude/aidd/bin/spec-diff.mjs $0 --after-approval`（承認のコミットから今までに変わった項目。承認の後に取り込んだ main の、ほかのチケットの変更は除く）の changes に、その要件（指摘の where か報告にある要件の ID）か、その下の具体例があるかで決める。同じ回に同じ要件の穴が 2 つ以上届いたときも 2 つ目とみなす
   どちらでもなければ、仕様担当の判断に任せる（業務で答えが変わりうる点だけが問いになり、ほかは問わずに具体例を足す）。問いにする穴の場面が、人が話していない所なら、仕様担当は「後で切り出す範囲に回す」案も選択肢に入れる
2. spec-diff と traceability-check（before-approval）を流し、reviewer に spec-review を見させる。画面のあるシステムの機能のチケットでは、続けて designer に screen-mock で（作る回）画面を直させ（作る回は、描く前にキャンバスの人の直しを写しに取り込む）、mock-render を流し、描き直した画面の画面のレビューを動かす（screens.md）。きっかけがモックと要件や具体例の食い違い（作る役の計画への異議、Planner の仕様の問題）なら、仕様を直さないときも、designer を直す回で起動し、食い違いの中身を渡す。Gate 2 の受け入れのページに「承認の後にモックが変わった」画面として出る（承認はやり直さない）。designer が「仕様の不足」で止まったら、1 に戻る
   コードレビューが、具体例の無い場面の不具合を target: spec で出したときは、仕様担当に具体例を足させ（問いがあれば 3 の答えを反映させ）、4 で状態をテスト作成中に戻して test-writer に落ちるテストを書かせ（red-run.json は、足した具体例の Red として上書きしてよい。前の Red は git の履歴に残る）、test-review をもう一度通してから implementer に直させる。Gate 2 の受け入れのページに「承認の後に変わった具体例」として出る。そのうち、承認の後に答えた問いの about に ID の無い具体例は、問わずに決めた振る舞いとして「あなたが見て判断すること」にも出る
3. 問いがあれば、変わった要件と具体例をチャットで示し、判断に要る事情を問いの文に入れて、AskUserQuestion でまとめて 1 回で問う（全体の承認はやり直さない）。今ある具体例の結果が変わる点は、影響の一覧が空でも問う。2 の仕様のレビューが上限に達して直す指摘が残ったら、段 1 の 5 の「上限で残った指摘」と同じ問いを束の最後に足し、答えも段 1 の 6 と同じに扱う（承認の後は Gate 1 の承認のページを作らないので、「ここで打ち切る」で残った指摘は、その場で業務の言葉で示して先へ進む）。答えを記録して反映させる
4. 元の状態に戻る。直した仕様に合わせて、計画、テスト、実装を直す必要があれば、その状態から進め直す
