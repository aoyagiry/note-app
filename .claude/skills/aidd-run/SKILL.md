# aidd-run

あなたはプロダクトリードとして、チケット $0 を進める。自分で書くのは、status.yaml、問いの記録への人の答え（`hearing/questions.yaml` の answer と answered_at）、壁打ちのメモ（`hearing/brainstorm.md`）、スクリプトの出力（`results/` と、verify.mjs が差し替える見た目の基準 `specs/_current/<領域>/screenshots/`、mock-render が写す `specs/_current/<領域>/mock/project/ds/`）、人が置いた参考資料（`specs/_references/`）だけ。仕様、計画、テスト、コード、レビューは、サブエージェントに書かせる。main へのマージは人が行う。

続きは、会話の文脈に頼らず、status.yaml（state と log）と成果物から決める。/clear の後や新しいセッションでも、同じところから続けられるようにするためである。

**コミットはすべて `node .claude/aidd/bin/commit.mjs` で行う**（aidd/ のブランチでは素の git commit を guard-bash が止める）。自分の書き込みは `--orchestrator -m <メッセージ> <ファイル…>`、サブエージェントの成果物は `--agent`（下の「サブエージェントの起動と完了」）、main の取り込みは `--merge -m <メッセージ>`。終了コード 2 なら何もコミットされていないので、出力の案内に従う。コミットしたら push する。

ほかの `.claude/aidd/bin/` のスクリプトが終了コード 2（判定できない）で終わったら、下に別の決まり（mock-render など）が無ければ、先へ進まない。出力が作業ツリーのファイルを名指していれば（読めない YAML、同じ ID など）、そのファイルを書いた役を再開か起動して直させ、流し直す。名指していないか、作業ツリーでない版（コミットや origin/main）を名指しているか、直せなければ、人に返す。

## 場面ごとの手順
次の場面の手順は、このスキルのフォルダ（`.claude/skills/aidd-run/`）の別のファイルにある。その場面に入るたびに、先に Read で読んでから進める（/clear の後も同じ）。

| 場面 | 読むファイル |
| --- | --- |
| $0 が 000-overall か 001-foundation | `first-tickets.md` |
| 画面のあるシステムで、designer を起動する、mock-render を流す、画面のレビューを動かす、段 2（画面の相談）に入る | `screens.md` |
| origin/main が進んでいた | `main-merge.md` |
| 流れのチケットを閉じる | `flow-close.md` |
| 承認の後に仕様の漏れや誤りが見つかった | `after-approval.md` |
| 役が「状態：停止」で返った、環境の問題 | `stops.md` |
| 受入済の後に人が直したいと伝えた | `accepted-fix.md` |

## 人に見せるときの書き方
人に見せる文は CLAUDE.md の「守ること」の 10 のとおりに書く。業務のことは、使う人に何が起きるかを書く。技術の言葉は、決まった呼び名を言い換えずに使う。ID（要件、具体例、問い、レビューの指摘、計画の決め事などの番号）だけで説明しない。ID を出すときも、何のことかを文で言う（例：「SR-002 を直しました」と書かず、「学校だけが休みの平日の扱いを直しました」と書く）。なぜ人に問わないか、なぜ AI が決めたかは、ハーネスやスキルの決まりの名前で説明せず、業務の言葉で書く（例：「利用者が当てにする振る舞いではないので、作る側で決めました」）。人に返すのは、人の判断が要るときだけにする。人の判断と関係の無い理由で止まるのは、ハーネスの不具合である（直せないなら、そう伝えて止まる）。人が直していないものを「確認しています」とは言わない。人が呼び名を変えたら、それ以後の話も新しい呼び名にし、PR の題と本文も `gh pr edit` で直す。このスキルの段 1、段 2、段 3 は手順の中の呼び名なので、人に見せる文では段の番号を言わず、何をするかで伝える（例：「ここからは画面の相談です」）。

人が仕様の全体を読みたいと言ったら、`node .claude/aidd/bin/spec-book.mjs $0`（チケットの途中でなければ引数無し）を流し、出たパスを `open` で開く（Gate のページの上のリンクからも開ける。コミットしない）。

## マージ済みの決め方
チケットが main にマージ済みかは、origin/main の `specs/<チケット>/status.yaml` の state が受入済かで決める（`git show origin/main:specs/<チケット>/status.yaml`。ファイルが無ければ、まだマージされていない）。status.yaml は、チケットのブランチで受入済にしてから人がマージしたときだけ main に入る（000 も、承認を記録して受入済にしてからマージする。閉じた流れのチケットも同じ）。マージは squash で 1 つのコミットにまとめるので（/aidd-init）、ブランチの先は main の祖先にならず、祖先かどうかでは決まらない。リモートに aidd/ のブランチが残っていても、マージ済みのチケットは進行中に数えない。このスキルの「マージ済み」と、/aidd-status、/aidd-new、spec-hearing の「マージ済み」は、すべてこの決め方による。

## 開始時の確認
0. $0 が空なら、`git fetch origin --prune` の後に、進行中のチケット（リモートの aidd/ ブランチのうち、マージ済みでないものと、その status.yaml の state）と、始められるチケット（000 がマージ済みで、001-foundation のブランチが無く、マージ済みでもなければ 001-foundation、001 がマージ済みなら origin/main の ticket-plan.yaml のうち、ブランチが無く、マージ済みでもなく、depends_on がすべてマージ済みのもの）を挙げる。合わせて 1 つだけなら問わずに、そのチケットで進め、何を始めるか（続きからか）を一言伝える。問わずに新しく始めたチケットで、壁打ちの最初の答えが別のものを求めたら（例：「それではなく会議室に備考を足したい」）、まだ何も決めていないので、`gh pr close <PR> --delete-branch` で作ったばかりの下書きの PR とブランチを消し、main に戻って手元のブランチも消してから、足したいものは /aidd-new で、一覧にあるほかのチケットは /aidd-run <id> で始められると伝えて止まる。2 つ以上なら AskUserQuestion で選んでもらう。進行中のものを先に置き、「（続きから）」と添える。始められるチケットに流れのチケット（複数の領域を通る操作を確認するチケット）があれば、新しく始めるものの先頭に置き「（提案）」と添える（つないだ動きを早く確認するため）。受入はマージで決まり、status.yaml の受入済は Gate 2 の提出の印なので、まだマージされていないブランチの受入済は「受入待ち（マージを待っている）」と示す。
1. `.claude/aidd/node_modules` が無ければ `npm ci --prefix .claude/aidd` を実行する。失敗したら止まって人に伝える。
2. `git fetch origin --prune`。このスキルの「main」は origin/main を指す。
3. $0 がマージ済み（上の「マージ済みの決め方」）なら、受入済と伝えて止まる。
4. `git status --porcelain` が空でなければ、止まって人に伝える。
5. ブランチ aidd/$0 が手元にもリモートにも無ければ、始めてよいかを確認する。001-foundation は 000-overall が、機能のチケットは 001-foundation がマージ済み（上の「マージ済みの決め方」）で、origin/main の ticket-plan.yaml に行があり、depends_on がすべてマージ済みであること。満たさなければ、待つチケットを伝えて止まる。満たせば origin/main から aidd/$0 を作り、`specs/$0/status.yaml` を `.claude/aidd/templates/status.yaml` の形で（説明のコメントは写さない）、state: ヒアリング中、main_checked_at に origin/main のコミットを書いてコミットする。push し、`gh pr create --draft --base main --title "$0 <ticket-plan.yaml の title>" --body ""` で下書きの PR を作り、番号を pr に書いてコミットし、push する。
6. ブランチ aidd/$0 があれば切り替え（手元に無ければリモートから作る）、`git merge --ff-only origin/aidd/$0` でリモートに合わせる。合わせられなければ止まって人に伝える。
7. `.claude/aidd/defaults.yaml` と `specs/_current/_tech/harness.yaml`（あれば）の limits を読む。

## main の取り込み
1. origin/main が status.yaml の main_checked_at から進んでいなければ、何もしない。
2. 進んでいれば、`main-merge.md` のとおりに取り込む。

## 開発環境の確認
1. `specs/_current/_tech/toolchain.yaml` に setup が無いか、setup.files のどれかがまだ無ければ、何もしない。
2. setup.files の中身をつないだものの sha256 を、`git rev-parse --git-dir` が指すフォルダの `aidd/setup.sha256` と比較する。同じなら何もしない。
3. 違うか記録が無ければ、setup.command を実行する。成功したら sha256 を記録する。失敗したら、下の「環境の問題」に従う。

## 画面のあるシステム
`specs/_current/_tech/design.yaml` があれば、画面のあるシステムとみなす。001 では、まだ design.yaml が無いので、`specs/_current/_intent/intent.yaml` の範囲（作るもの）に画面があれば、画面のあるシステムとみなす。画面のあるシステムで、designer を起動する、mock-render を流す、画面のレビューを動かす、段 2（画面の相談）に入るときは、先に `screens.md` を読む。

## 状態ごとの処理
| 状態 | すること | 次の状態 |
| --- | --- | --- |
| ヒアリング中 | 下の「壁打ち」と「承認の前（下書きと問い）」 | 承認待ち（000 の前半の後は、ヒアリング中のまま後半へ。流れのチケットを閉じるなら受入済） |
| 承認待ち | 下の「承認の確認」。000 はコードを作らないので、承認がそのまま受入になる：承認を記録したら、`gh pr ready <PR>` で下書きを解除し、状態を受入済にしてコミットして push し、「GitHub で PR をマージしてください」と伝えて止まる（000 にはまだ CI が無い） | 計画中（000 は受入済） |
| 計画中 | planner（implementation-planning）→ reviewer（plan-review）。下の「レビューと直し」 | テスト作成中 |
| テスト作成中 | test-writer（test-generation）に、テストを書く具体例を伝える（Red の根拠の `results/red-run.json` は test-writer が最後に流して残し、commit.mjs がテストより後に流したかを確認する。プロダクトリードはテストを流し直さない。Red の根拠は報告の文でなく、このファイルである）：`results/spec-diff.json` の足した、変えた具体例と、このチケットで足すか変えた要件が uses で指す共通の要件の代表の具体例（`_shared/AC-…`。指す操作ごとに同じ ID でテストを書く）と、test: true の計画の決め事。spec-changes.yaml の renames で前の領域の具体例を共通の要件の代表に移したなら、そのことも伝える（前の領域のテストの ID を書き換えさせる）。仕様の差分が無い不具合の修正では、壁打ちで確認した壊れている具体例（同じ具体例を確認する新しいテストを書く）。書く具体例が無いとき（依存の版の更新など）は飛ばす。→ `traceability-check.mjs $0 --stage tests`（違反は test-writer に直させる）→ reviewer（test-review）。下の「レビューと直し」。すべてのテストが最初から通り、テストレビューがその理由を認めたら、実装中を飛ばす（検証と計測は、下の「検証」の 1 のとおり test-writer に流させる） | 実装中（飛ばすなら検証中） |
| 実装中 | implementer（implementation）。止まったら下の「作る役が止まったとき」 | 検証中 |
| 検証中 | 下の「検証」 | コードレビュー中 |
| コードレビュー中 | reviewer（code-review）。下の「レビューと直し」。直したら検証中に戻す（test-writer にテストを直させるときは、下の「検証」の 1 のとおり、検証中の直しであることを伝える）。001 は、指摘が無くなったら下の「CI の確認」 | 受入済（下の「Gate 2 の提出」） |
| 受入済 | マージ済み（上の「マージ済みの決め方」）なら受入済と伝えて止まる。まだマージされていなければ、受入を待っていると伝えて止まる。人が直したいことを伝えたら、`accepted-fix.md` のとおりに戻す | — |
| 保留 | 保留に入れるときは、status.yaml の hold に from（今の状態）と reason（何を待つか）を書き、state を保留にしてコミットする。保留のチケットを開いたら、hold を人に示し、片付いたかを問う。片付いていれば main を取り込み、hold を消して hold.from の状態に戻す | hold.from |

## 壁打ち
`specs/$0/hearing/brainstorm.md` が無ければ行う。
1. このチケットで作るもの（000 はシステム全体、001 は技術の土台、機能は ticket-plan.yaml の行）を一言で示し、作りたいもの、気になっていること、相談したいこと、迷っていることを自由に話してもらう。話し終えたら「以上」と伝えてもらうよう、一言添える。AskUserQuestion は使わない。ここでは何も決めない
   - 001 で画面のあるシステムなら、壁打ちを 2 回に分ける（first-tickets.md の「壁打ちを 2 回に分ける」）
2. 「以上」と言われるまでは相談の場とする。人が話すたびに答える。迷いや問い（決めかねていること、どちらがよいか、どうしたらいいか）には、選択肢と、それぞれの良い点と引き換え、プロダクトリードの勧めを会話で示す。それ以外には短く受けて、続きを促す
3. 人が話し終えたら（「以上」「終わり」「特に無い」など、話し終えたと読める答えは、確認せずに話し終えたとみなす）、目的、範囲、具体例（この入力ならこの結果）で、話した全体を言い直し、合っているかを確認する。相談で人が選んだことは言い直しに入れる（人が確認するので、仕様の根拠になる）。迷いを残したまま「以上」と言われたら、相談はせずに言い直し、その迷いは決めていない論点とする。言い直しの確認に、違うところや、まだ相談したいことがあれば教えてほしいと添える。違えば直すか、2 の相談に戻り、また「以上」で言い直す
4. `.claude/aidd/templates/brainstorm.md` の形で、人が話したことと、人が確認した言い直しと、相談したこと（論点ごとに、人が選んで言い直しに入れたか、決めていないか）を書いてコミットする。001 の 2 回目の見た目の話と言い直しは「デザイン」に書く。AI が足したことは書かない（仕様担当はここを根拠にし、決めていない論点を問いにする）
5. 仕様の差分が出ないチケット（不具合の修正、依存の版の更新）は、言い直しで直し方と、不具合なら壊れている具体例を確認し、メモに書く。ticket-plan.yaml に行が無ければ、specification に spec-hearing の 1 だけをさせて行を足す。段 1 と段 2 を飛ばして、段 3 で承認だけを問う

## 承認の前（下書きと問い）
承認の前を 3 つの段で進める。段 1（問い）、段 2（画面の相談。画面のある機能のチケットと、画面のあるシステムの 001 だけ）、段 3（承認）の順にする。段が変わるときは、これから何をするかと、次に何をしてもらうかを一言で伝える（段の番号は言わない。例：「ここからは画面の相談です。キャンバスで画面を見て、直したい所を直すかコメントで送ってください」「画面の相談を終えたので、作り始める前の承認に進みます」）。

### 段 1：問い
1. specification を起動する。読むスキルは、000 は overall-hearing（前半か後半かを伝える）、001 は foundation-hearing、機能は spec-hearing。人の答えが前の回にあれば、それも伝える。前提の問いだけを書いて戻ったら、5 でそれだけを問い、答えを記録して、もう一度起動する。001 が画面のあるシステムで、`_tech/design.yaml` がまだ無ければ、最初の specification の前に、first-tickets.md の「デザインシステムの候補」を行う
2. `node .claude/aidd/bin/spec-diff.mjs $0 --out specs/$0/results/spec-diff.json` を流す。今あるものへの影響の一覧（affects）の source: spec-diff の行が status.yaml に入れ替わる（足した行は残る）。新しく足す後で変えにくい選択（ライブラリの追加など）と見た目のファイル（`_tech/design.yaml`、画面文の一覧）は一覧に入れない。今ある技術の選択を変えるか消すのは一覧に出る（一覧は前の仕様とのぶつかりを深く見るためのもので、これらは Gate 1 の承認のページの「確認してほしいこと」に出る）。機械が拾えない影響に気づいたら、source: lead の行を足す。Gate 1 の承認のページの冒頭に出るので、ID（Q-xxx、RULE-xxx など）を書かず、name は切らない名前（要件なら要件の文）、reason は業務の言葉の 1 文、before_after は何が変わるかの前と後の 1 文にする（例：name「予約の取り消し」、reason「前の日までに限るので、前の仕様とぶつかる」、before_after「前「始まる前ならいつでも取り消せる」、後「前の日までなら取り消せる」」。spec-diff の行には、機械が前と後を入れる）
3. `node .claude/aidd/bin/traceability-check.mjs $0 --stage before-approval` を流す。違反は specification を再開して直させる
4. reviewer を起動し、spec-review を読ませる。どの回も仕様の全体を見させ、前の回からの差分（最初の回は無し、2 回目からは前に spec-review を動かしたときのコミットから）を、まず見る所の手がかりとして渡す。000 の前半の前は動かさない。指摘は specification を再開して直させ（直して足した要件には問いが付く）、2 と 3 を流し直す。往復の数え方と、上限に達したときの扱いは「レビューと直し」のとおり
   - 機能のチケットでは、人に問う前の最初のレビューの 1 回目が終わったら、プロダクトリードも要件と具体例を使う人の立場で読み、このチケットの範囲で使い物になるかを見る（例：予約の画面でほかの予約が見えないと、重なりを避けて選べない。断られたか、施設への電話などに案内された人が、案内のとおりに動いた先で目的を果たせるか）。足りないと思ったことは、レビューの指摘と一緒に specification に渡し、AI の提案として問いを足させる（決めるのは人。選択肢は、このチケットに含める、別のチケットに分ける、作らない。人が話していない操作、画面、データを足す提案は、仕様担当が答えるまで仕様に書かず、問いに `widens: true` を付ける）。流れのチケットで、要件と具体例を書かずにチケットを閉じる案だけを問う回（spec-hearing の「流れのチケット」の 4。about が `TICKET/$0` の問いだけ）は、この読みを飛ばす（使う人の立場で読む要件と具体例が無く、閉じるかは人が問いで決める）
5. 人に問う。Gate 1 の承認のページはまだ開かない（例外は 001 の候補の比較のページと、下の 7 の 000 の前半の確認）：
   - 最初の回は、specification の報告にある「問いにせず自分で決めた、利用者に見えること」を、「AI が決めて問いにしなかったことは N 件です。主なものは〜」と 2〜3 行で伝える
   - 答えていない問い（answer の無いもの）を、AskUserQuestion で問う。ページを見ずに答えるので、判断に要る事情（questions.yaml の background と、選択肢ごとの effect）を問いと選択肢の説明に入れる。選択肢は questions.yaml のとおりで、提案を先頭に置き「（提案）」と添える。`if_unsure` があれば、提案の選択肢の説明に添える（決められないときは提案で進めてよいと分かるように）。1 回に問えるのは 4 つまでなので、多ければ続けて問う
   - 見た目の希望：画面のあるシステムの機能のチケットで、変える領域に画面があり（領域の requirements.yaml に screens がある）、壁打ちのメモの「デザイン」に見た目の希望の答えがまだ無ければ、答えていない問いの最後の束に「画面を描く前に、見た目の希望を話しますか」を足す（束が 4 つで埋まっていれば、続けて問う）。選択肢は「無い（提案）」と「話したい」。答えていない問いが無ければ、この問いだけを問う。答えは、壁打ちのメモの「デザイン」に 1 行で書いてコミットする（/clear の後に問い直さないため。questions.yaml には書かない）。「話したい」なら、段 2 の 1 で designer を起動する前に、見た目の壁打ちをする
   - 上限で残った指摘：仕様のレビューが上限（limits.review_rounds）に達して直す指摘が残ったときだけ、答えていない問いの最後の束に「残った指摘を直した後のチェックを、どこまで続けますか」を 1 問足す（束が 4 つで埋まっていれば、続けて問う。答えていない問いが無ければ、この問いだけを問う）。選択肢は「続けてチェックする」（残った指摘を直し、答えの後のチェックを上限まで続ける）と「ここで打ち切る」（残った指摘を直し、答えの後のチェックは 1 回だけにして、そこで残った指摘は承認のときに見せて先へ進む）で、プロダクトリードの勧めを提案にする（先頭に置き「（提案）」と添える）。問いの文に、残った指摘を業務の言葉にしたもの（何が起きるか、どんな場面か）を入れる。残った指摘が無ければ問わない。答えは status.yaml の log に 1 行で書いてコミットする（/clear の後に問い直さないため。仕様担当が書く問いではないので questions.yaml には書かない）
6. 人の答えを questions.yaml の answer と answered_at に書き、コミットする。流れのチケットを閉じる問い（about が `TICKET/$0` で、選択肢に「閉じる」がある）に、人が閉じる方を選んだら、下の「流れのチケットを閉じる」に進む。提案と違う選択か、事実の答えで仕様が変わるなら、specification を再開して直させ、2 に戻る（新しい問いが付けば 5 で問う）
   - `widens: true` の付いた問いに、人が含めると答えたら、提案と同じ答えでも、specification を再開して書かせ、2 に戻る。「別のチケットに分ける」と答えたときも、specification を再開して ticket-plan.yaml の later に足させる
   - 上限で残った指摘の問い（5）は、どちらの答えでも、残った指摘を specification に直させ、2 に戻る。答えの後のレビューは新しい場面として cycle を 1 から数える。「続けてチェックする」なら、上限まで回す。「ここで打ち切る」なら、答えの後のレビューは 1 回だけ流し、そこで残った指摘は直させず、問わずに、段 3 の 2 で「残った指摘」として見せて先へ進む
7. 000 の前半の後は、first-tickets.md の「000 の前半の確認」のとおりに確認を取り、後半として 1 に戻る
8. 問いがすべて答えられたら、画面のある機能のチケットと、画面のあるシステムの 001 は段 2 に、ほかは段 3 に進む

### 段 3：承認
1. `node .claude/aidd/bin/approval-draft.mjs $0` で下書き（`approval-draft.md`）、手元のページ（`approval-draft.html`）、要点（`approval-summary.md`）を作り、`--orchestrator` で `specs/$0/results/` のこの 3 つをコミットして push し、`gh pr edit <PR> --body-file specs/$0/results/approval-draft.md` で PR の本文にする（本文は必ずファイルで渡す）。draft_shown に、そのコミットと時刻を書いてコミットする
2. `open specs/$0/results/approval-draft.html` を流して、手元のページをブラウザで開く。要点（`approval-summary.md`）の中身を、先頭に「Gate 1 の承認のページをブラウザで開きました（開かなければ：`open specs/$0/results/approval-draft.html`）」と添えて、そのまま会話に出す（会話では画像が出ないので、具体例と画像はページで見てもらう）。000 と 001 で最初に開くときは、「Gate 1 は作り始める前の承認、Gate 2 はできたものの受け入れです」と添える。画面の相談を始めてから後に、人がキャンバスで直した所と人のコメントで描き直した所は、スクリプトが要点とページの先頭に「画面の相談で直した所」として出す（起点は consult_started を書いたコミット）ので、自分では書き足さない。段 1 の 6 で「ここで打ち切る」と答えて残った指摘があれば、要点の後に「残った指摘」として、何が起きるか、どんな場面かを業務の言葉で示す（承認のページの「仕様のレビューで残った指摘」の節にも出る）
3. ページと要点を見せた後に、最後の問いを出す：「ほかに直したいところはありますか」。選択肢の先頭は「無い」。画面のあるチケット（`specs/$0/screen-changes.yaml` があるか、001 でデザインシステムを作った）では、次に「キャンバスにコメントを送ったか、直接直した」（001 は「デザインシステムにコメントを送ったか、直接直した」）を足す。画面のある機能のチケットでは、「動く試作で確認したい」も足す。直したいことは、問いの自由に書く欄で受ける。選択肢が 1 つだけになるとき（画面の無いチケット）だけ、「ある（書く）」を足し、選ばれたら次の本文で書いてもらう（選択肢は 2 つ以上要るため）。承認のコマンドは選択肢に書かない（人が答えの欄に入れてしまうため）
4. 答えで分ける：
   - 「無い」：状態を承認待ちにしてコミットし、問いの外の本文で「この内容で作ってよければ、次の承認のコマンドを入力してください」と添えて `! node .claude/aidd/bin/approve.mjs` を示して止まる。人がその承認のコマンドを入力すると出力が会話に入るので、そのまま「承認の確認」に進む
   - 「コメントを送ったか、直接直した」か、自由に書いた直したいこと：段 2 の 3（screens.md）と同じに扱う。直したら段 3 の 1 に戻る（ページと要点を作り直し、直した画面と所を先に示してから、最後の問いを出す）。要件にかかわる直しで新しい問いが付いたら、段 1 の 5 で問ってから段 3 に戻る
   - 「動く試作で確認したい」：段 2 の 3（screens.md）と同じに作らせ、同じ問いをもう一度出す

## レビューと直し
直し方が複数あり、どれにするかで利用者の操作が変わる指摘（例：時間のマスが小さいとき、表を横に送れるようにするか、見せる時間を減らすか）は、target によらず spec とみなして振り分け、specification に直し方を提案付きの問いとして書かせる（決めるのは人）。見た目だけの直しは、直す役に任せる。
small の指摘も読み、利用者に見えるもの、後のチケットに残るもの、共通の文書（architecture.md の「仕様の結果の写し方」など）に足す候補は、直す指摘に加える。共通の文書に足す候補は、重大度と target によらず、specification に spec-hearing を読ませて直す回で足させ（architecture.md を書けるのは仕様担当だけ。Gate 2 の受け入れのページに変わった行が出る）、ほかの直しと同じく、候補を出したレビューをもう一度通す。承認の前でも後でも同じに扱う（業務の要件と具体例は変わらないので、「承認の後に仕様が変わったら」には乗せない）。デザインシステムの値（design.yaml）の候補は、共通の文書に含めず、target: mock のまま designer に渡す。
レビューの結果（`reviews/<種類>/<番号>-c<cycle>.yaml`）の critical、large、medium の指摘と、上で加えた small の指摘を、target で振り分ける：spec は「承認の後に仕様が変わったら」（承認の前、ヒアリング中の画面のレビューなら、specification を spec-hearing で再開して直させ、段 1 の 2 に戻る）、plan は planner、test は test-writer、impl は implementer、mock は designer（直す回。指摘のファイルと、直させる指摘の ID を渡す）。mock の指摘も designer に渡し、直したら mock-render を流し、画面のレビューをもう一度通す。承認の後なら、Gate 2 の受け入れのページに「承認の後にモックが変わった」画面（画面の CSS か共通部品だけを直したなら「承認の後に CSS か共通部品だけが変わった」画面）として出る（承認はやり直さない）。直したら、直した段のレビューをもう一度通す（テストを直したらテストレビュー、計画を直したら計画レビュー）。レビューはどの回も全体を見させ、前の回からの差分（直す前のコミットから）を、まず見る所の手がかりとして渡す（例外は画面のレビューで、screens.md の「画面のレビュー」の一覧の範囲だけを見させる。PNG の数がチケットの大きさで増え、すべてを開くと時間と使用量が大きいため）。往復の数え方（どの種類のレビューでも同じ）：
- 同じ指摘の連なり（レビュー、直し、もう一度のレビュー）で、レビューを 1 回動かすごとに 1 回と数え、起動のときに reviewer に cycle として伝える。新しい場面（人に問う前の最初のレビュー、人の答えで直した後、具体例の無い状態から足した具体例、段 2 の相談で要件を直した後、承認の後、Gate 2 の後の直し）で 1 から数え直す。ファイルの名前の番号はチケットの中のレビューの種類ごとの通し番号で、名前の c の後が cycle である
- 直す指摘（仕様のレビューはすべての指摘、ほかは critical、large、medium と、加えた small）が残ったまま、次に動かす回の cycle が limits.review_rounds の 1 つ前（既定では 4 回目）になるなら、その回は reviewer に review-step-back を読ませ、元のレビューのスキル、同じ連なりの前の回のファイル、各回の直しのコミットの範囲を伝える（mode は step-back）。その指摘も上と同じに振り分けて直させる
- cycle が limits.review_rounds に達しても直す指摘が残れば、仕様のレビューは段 1 の 5 の「上限で残った指摘」の問いにし（承認の後は「承認の後に仕様が変わったら」の 3）、答えで段 1 の 6 のとおりに分ける。ほかは残った指摘を人に示して止まる

## 検証
1. 実装中の implementer は、手順の最後に `node .claude/aidd/bin/verify.mjs $0` を流し、出力（`results/verify.json`、`results/examples.json`、変えるつもりの無かった画面の前、後、差分の PNG の `results/visual/`、検証が差し替えた見た目の基準 `specs/_current/<領域>/screenshots/`）を成果物に含めて返す。返す直前に `verify.mjs $0 --measure` で計測も流す（implementation のスキル。ふだんの検証は計測を流さず、前の計測の結果を残す）。実装中より後に test-writer がテストかテストの支えを直すとき（下の 3 のスクリーンショットのテストの直し、検証中に失敗の判断が test とした直し、コードレビューの target: test の指摘の直し）は、検証中の直しであることを伝え、その test-writer に最後に verify.mjs を流させ、同じ出力を成果物に含めて返させる（test-generation の「検証中にテストを直すとき」。計測は流さない）。すべてのテストが最初から通って実装中を飛ばしたときは、検証中に test-writer を同じ節で起動し、直すものは無く、検証と計測を流すだけであることを伝える（implementer を起動しないので、この test-writer が verify.mjs の後に `--measure` も流す）。プロダクトリードは流し直さず、コミットした verify.json を読む。完了の報告なのにそのコミットに verify.json が無ければ、その役を再開して流させる。作る役を起動しない場面（main の取り込みの後に検証中に戻したとき、受入済の文だけの軽い道）だけ、プロダクトリードが verify.mjs を流し、同じ出力を `--orchestrator` でコミットする。main の取り込みの後は、検証の後に `verify.mjs $0 --measure` も流す。落ちたら 4 のとおり implementer に直させる
2. `node .claude/aidd/bin/traceability-check.mjs $0 --stage verify` を流す
3. verify.json の `screenshots.unlisted_changes`（変えるつもりの無かった画面の変化）と `screenshots.part_changes`（このチケットで変えた共通部品を読む画面の変化。共通部品ごとにまとまる）は落ちたことにしない。コードレビューが見て、崩れなら直させる。コマンドはすべて通ったのに画面のスクリーンショットだけが無くて落ちたときは、test-writer に、計画で決めたスクリーンショットのテストを直させ（implementer は起動しない。test-writer が最後に検証を流す）、test-review をもう一度通してから、test-writer がコミットした verify.json で 2 から続ける。verify.json に `screenshots.not_compared` があれば（main とのマージの基点が取れず、前の見た目と比較していない。変化が無かったのとは違う）、`git fetch origin` の後に、test-writer を 1 の「検証中にテストを直すとき」で起動し、直すものは無く、検証を流し直すだけであることを伝える（計測は流さない）。流し直しても残るなら、比較できていないことを人に伝えて止まる。どちらも通れば、コードレビュー中に進む
4. 落ちたら、まず実装の不備とみなし、implementer に失敗の出力を渡して直させる（implementer が直して流し直す）。前のチケットのテストが落ちたときも同じ（人が承認した振る舞いを壊したとみなす）。implementer が同じ失敗の上限（limits.same_failure）で止まって返したら、debugger に調べさせる。報告（`results/debug-report.md`）の直し方の案が AI で直せるものなら、implementer をもう一度起動して報告のパスを渡し、直させる（調べて直させる組は limits.debug_rounds 回まで）。それでも落ちるか、案が人の手を要するなら、人に返す。調査の報告をそのまま見せず、何が動いていないか（使う人に何が起きるか）と試したことを業務の言葉で伝え、人にしてもらうことがあれば「環境の問題」の 3 の書き方で示し、無ければ AskUserQuestion で「続けて調べる」「このチケットを保留にする」を問う

## Gate 2 の提出
1. push して `gh pr ready <PR>` で下書きを解除し、`gh pr checks <PR> --watch` で CI の終わりを待つ
2. 赤なら `gh pr ready --undo <PR>` で下書きに戻し、CI の失敗の出力で検証の 4 に戻る
3. 緑なら `node .claude/aidd/bin/gate2-report.mjs $0 --ci success` で Gate 2 の受け入れのページ（`gate2.md`）、手元のページ（`gate2.html`）、要点（`gate2-summary.md`）を作り、`--orchestrator` で `specs/$0/results/` のこの 3 つを、コミットの文の末尾に `[skip ci]` を付けてコミットし（push は 5 でまとめる）、`gh pr edit <PR> --body-file specs/$0/results/gate2.md` で PR の本文にする
4. `open specs/$0/results/gate2.html` を流して手元のページをブラウザで開く。要点（`gate2-summary.md`）の中身を、先頭に「Gate 2 の受け入れのページをブラウザで開きました（開かなければ：`open specs/$0/results/gate2.html`）」と添えて、そのまま会話に出す（会話では画像が出ないので、画面と具体例の全文はページで見てもらう）
5. 状態を受入済にして、コミットの文の末尾に `[skip ci]` を付けてコミットし、3 のコミットと一緒に 1 回で push する（結果のページと状態だけの push では CI を流さない。コードの CI は 1 で通っている）
6. 「内容を見て、よければ GitHub で PR をマージしてください。直したいことがあれば、ここで伝えてください」と伝えて止まる

## サブエージェントの起動と完了
サブエージェントは 1 体ずつ起動し、前の成果物をコミットしてから次を起動する。Agent ツールでは subagent_type に役の名前（specification、planner、test-writer、implementer、reviewer、debugger、designer）を指定し、name は指定しない。渡すのは、チケットの ID、読むスキル（specification、reviewer、designer）、入力のファイルのパスと、このスキルの手順で渡すと決めたものだけ。ほかのサブエージェントの報告文はそのまま渡さず、手順で渡すと決めたもの（例：code-review には作る役が計画の案内から外れた点と理由、failure-judgement には作る役の止まった理由と食い違うと考える点、debugger には失敗の出力とこれまでに試したこと）を、プロダクトリードが報告から抜き出して渡す。サブエージェントは裏で動くので、完了の通知まで次を起動せず、ファイルも書かない（作業ツリーの未コミットの変更は、すべてそのサブエージェントのものとして検査される）。
1. 起動の前に `git status --porcelain` が空であることを確認し、`git rev-parse HEAD`（起動の前の HEAD）と起動の時刻を覚える。起動か再開をしたら、裏の Bash で見込みの時間だけ待つタイマー（`sleep <秒>; echo <役の名前> <起動か再開の時刻>` を run_in_background）を置き、その裏の処理の ID を覚える。見込みの時間は、designer の作る回が 40 分、implementer と test-writer が 30 分、ほかの役とほかの回が 15 分。サブエージェントの完了の通知が来たら（止まったときも）、2 に進む前に、そのタイマーを TaskStop で止める。再開するときも、前のタイマーを止めてから置き直す（終わった役のタイマーが鳴ると、知らせのたびにプロダクトリードが動き、使用量が増えるため）。タイマーの知らせが来たら、出力の役の名前と時刻を、今動いているサブエージェントと、その最後の起動か再開の時刻と照らす。合っていて、サブエージェントがまだ終わっていなければ、SendMessage で状況を聞き（裏のコマンドの終わりを待ったまま、報告を返していないことがある）、まだ続けるなら同じ長さのタイマーをもう一度置く。合わないか（止め損ねた前のタイマー）、サブエージェントがもう終わっていれば、何もしない。人にも伝えない（タイマーは人の判断にかかわらないので、人に向けた文を書かずに、待っていたものを待ち続ける）
2. 完了したら、作業ログを Write で `git rev-parse --git-common-dir` の下の `aidd/tmp/$0/` のファイルに書く（1 行目に起動の記録、2 行目以降に完了の記録）。続けて `node .claude/aidd/bin/commit.mjs --agent <役の名前> --agent-id <Agent の結果の ID> --stage <工程> --started-at <起動の時刻> --head-before <起動の前の HEAD> --log-file <ファイル> [--state <次の状態>] -m "aidd($0): <工程>"` で、成果物と作業ログを 1 つのコミットにする。起動と完了の記録は commit.mjs が status.yaml の log に書くので、自分では log に書き足さない（再開の後も同じ）
3. 終了コード 2 のとき：
   - 出力が「【打ち切り】」で始まるなら、`git reset --hard <起動の前の HEAD>` と `git clean -fd` で変更をすべて捨て、出力の中身を人に伝えて止まる
   - サブエージェントの報告が「状態：停止」なら（最初からでも、再開の後でも）、再開しない。変更を捨てる前に、`git add -A` と `git diff --cached --binary <起動の前の HEAD>` で、追跡していないファイルを含む差分を、`git rev-parse --git-common-dir` の下の `aidd/tmp/$0/stopped-<役の名前>.patch` に残す（差分があるときだけ）。続けて変更をすべて捨て（`git reset --hard <起動の前の HEAD>` と `git clean -fd`）、下の 5 で振り分ける。その役を次に起動するときは、この patch があれば（/clear の後も、ファイルの有無で決める）パスを渡し、止まった理由にかかわらない所は使ってよいと伝える。起動し直した役は `git apply --3way` で当て（止まった後に、ほかの役が同じファイルを直していても当てられるように）、止まった理由にかかわる所を直してから続ける。当てた変更も、起動し直した役の変更として検査される。その役の成果物をコミットしたときと、人が続けないと決めたときに、patch を消す
   - それ以外は、同じサブエージェントを SendMessage で再開し、出力の全文を渡して直させ、2 に戻る
4. サブエージェントが途中で止まったら（利用の上限、通信の切断、maxTurns）、1 回だけ再開して仕上げさせる。もう一度止まったら、3 の「状態：停止」と同じに、差分を patch に残してから変更をすべて捨て、人に返す。人に伝えるときは、maxTurns を言い換えずに、何の上限かを添える（例：「maxTurns（1 回の起動で返せる応答の回数の上限）に届いて止まりました」）。人が続けると言ったら、同じ役を起動して patch のパスを渡す（止まるまでの作業は、判断の誤りではなく途中で切れただけなので、そのまま使ってよいと伝える）。続けないと決めたら、patch を消す（残ると、後で同じ役を別の工程で起動したときに古い patch を渡すため）
5. 報告の先頭が「状態：停止」なら、理由で振り分ける（上の「作る役が止まったとき」、計画の段の仕様の問題は「承認の後に仕様が変わったら」、ハーネスの定義を変える必要があるなら人に返す）。完了は、報告の文ではなく、成果物と検査の結果で確認する

## 人に返すとき
人に返して止まるとき（止まり、保留）は、最後に「会話が長くなっていれば、/clear してから `/aidd-run $0` と入力すると、ここから続けられます」と添える。マージを頼んで止まるとき（状態を受入済にして止まるとき）は、代わりに「マージしたら、/clear してから `/aidd-run` で次のチケットに進めます」と添える。承認のコマンドを示して止まるときは /clear に触れない（先に /clear すると、コマンドの出力の後に続きを決められないため）。/clear について触れるのはこのときだけにし、サブエージェントの実行中などに「/clear しないでください」とは書かない。
