# 役が止まったとき、環境の問題
aidd-run（`SKILL.md`）の、場面ごとの手順。役が「状態：停止」で返ったとき、準備のコマンドが落ちたときに読む。節の名前だけで指している所（「レビューと直し」、段 1 の 5 など）は、SKILL.md の節である。

## 作る役が止まったとき
テストを書く役と Planner が止まったときも、同じ理由ならここに従う。
- 計画への異議：planner に直させ、plan-review をもう一度通す。テストが呼ぶ形か、テストを書く役の分担（Red の前に要るテストの設定など）が変わったら、テスト作成中に戻す。同じ計画への異議が limits.review_rounds に達したら人に返す
- 計画への異議のうち、モックと要件や具体例の食い違い：「承認の後に仕様が変わったら」
- 計画への異議のうち、作ったものに合わせてテストの設定だけを直すもの（webServer の起動のコマンドとポート、カバレッジから外すファイルなど。テストが呼ぶ形、テストのファイル、テストの支えは変えない）：planner を通さず、テスト作成中にも戻さない（作りかけのまま Red を取り直さないため）。状態を実装中のまま、test-writer を test-generation で起動し、テストの設定だけの直しであることと、直す設定のファイルと中身（implementer の止まった理由から、プロダクトリードが書く）を伝える。Red の根拠（red-run.json）は流し直させない（commit.mjs は、テスト作成中のコミットでだけ求める）。続けて reviewer に test-review を読ませ（cycle は 1 から）、テストの設定だけの直しであることと、test-writer を起動する前のコミットからの差分を渡し、その差分だけを見させる（全体を見るレビューの例外）。指摘が無くなったら、implementer をもう一度起動する。テストのファイルかテストの支えも直すなら、上の計画への異議の道にする
- テストか仕様が誤っているのでは、原因は main にマージ済みの別のチケットのコード：reviewer に failure-judgement で判断させる。impl なら implementer を、判断の根拠を添えてもう一度起動する。test なら、状態は変えずに test-writer に直させ、test-review をもう一度通す。実装中に出たなら、失敗の判断が test とした直しであることを伝え（Red も検証も流させない）、指摘が無くなったら implementer をもう一度起動する。検証中に出たなら、SKILL.md の「検証」の 1 のとおり、検証中の直しであることを伝える。spec なら「承認の後に仕様が変わったら」。upstream なら、AskUserQuestion で「このチケットで直す（影響の一覧に足す）」「別のチケットで直す（このチケットは保留にする）」「今は直さない（理由を書いてリスクを引き受ける）」を問う
- 環境が原因：下の「環境の問題」
- 開発環境の準備が要る（001 で定義ファイルを書き終えた）：SKILL.md の「開発環境の確認」を行い、同じ役をもう一度起動する
- テストを書く役と Planner の、仕様の問題：「承認の後に仕様が変わったら」

## 環境の問題
作る役が「環境が原因」と止まったとき、準備のコマンドが落ちたとき。
1. 原因を見立て、AI で直せる直し方を試す（依存の入れ直し、setup.command の流し直し、キャッシュの削除など）。マシン全体を変える操作はしない
2. 同じ失敗が limits.same_failure 回続いたら、debugger に調べさせ、報告（`results/debug-report.md`）の案のうち AI で直せるものを試す（環境の直しは 1 と同じに自分で行い、コードの直しは implementer を起動して報告のパスを渡す。limits.debug_rounds 回まで）
3. 人の手が要るとき（管理者の権限が要るインストール、Docker などのアプリが起動していない、ネットワーク、クラウドへのログイン）だけ、人にしてもらうことを 1 つずつ具体的に示して止まる。例：「Docker Desktop を開いてから『続けて』と伝えてください」「次の 1 行を、先頭に ! を付けて入力してください：`! brew install postgresql@16`」。認証情報は受け取らない
