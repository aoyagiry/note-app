# 画面のあるシステム
aidd-run（`SKILL.md`）の、場面ごとの手順。画面のあるシステムで、designer を起動する、mock-render を流す、画面のレビューを動かす、段 2（画面の相談）に入るときに読む。節の名前だけで指している所（「レビューと直し」、段 1 の 5 など）は、SKILL.md の節である（段 2 だけは、このファイルの下の「段 2：画面の相談」）。

- **Designer**：画面のモックとデザインシステムは designer が Claude Design（Artifact）で作る。001 は design-system、機能のチケットは screen-mock を読ませ、回（候補、作る、直す、写しを取る、読み直す、動く試作）を伝える。designer は描いた画面を自分で撮って確認する。報告に、コマンド（ランタイムの写し、mock-render）を止められたとあれば、代わりに流して結果を渡し、再開させる
- **見張りを止める**：designer の報告に公開した URL があれば、そのたびに ArtifactComments（遅れて読み込む道具なら ToolSearch で読み込む）の watch に url と on: false を渡して、そのキャンバス（001 はデザインシステム）の見張りを止める。見張ったままだと、送られたコメントに自動で返事をし、要件にかかわるかを分ける前に約束してしまう。途中で届いたコメントの知らせには応じない
- **モックの PNG**：designer が画面を足すか直したら（`specs/$0/screen-changes.yaml` がある）、`node .claude/aidd/bin/mock-render.mjs $0` を流し（変えた共通部品があれば、共通部品の artboard と、それを読む代表の画面の元も撮る）、`specs/$0/results/mock/` と `results/mock-check.json`（文字が枠に収まっているかを測った結果）と、mock-render が写した各領域の `mock/project/ds/`（変わったときだけ）を `--orchestrator` でコミットして push する（このスキルで「mock-render を流す」と書いた所は、このコミットと push までを含む）。Gate 1 の承認のページと Gate 2 の受け入れのページは、HEAD にコミットした PNG を指すので、mock-render → PNG をコミットして push → approval-draft か gate2-report の順に流す。mock-render が止まったら（モックの元、デザインシステムの tokens.css か base.css、ランタイムの写しが無い、仕様に無い具体例を指している、同じ名前の共通部品の中身が領域で違う）、出力を渡して designer を再開して直させる
- **具体例の無い画面の状態**：designer の成果物をコミットした後、`git diff <起動の前の HEAD> HEAD -- specs/$0/screen-changes.yaml` で `unexampled` に足された行があれば（報告の文には頼らない）、specification を spec-hearing で再開し、足された行を渡して具体例にさせる。続けて spec-diff と traceability-check（before-approval）を流し、reviewer に spec-review でもう一度見させ（新しい場面なので、cycle は 1 から数える）、designer を作る回でもう一度起動して、足した画面例を描かせる。このとき、前に designer を起動した時点のコミットからの `specs/_current/` の差分を、`git rev-parse --git-common-dir` の下の `aidd/tmp/$0/` にファイルで書き出してパスを渡す（designer に起動の前のコミットを探させないため）。承認の後も同じに扱う（「承認の後に仕様が変わったら」の流れに乗る）。一度挙げた状態は designer がもう挙げないので、往復は止まる
- **画面のレビュー**：機能のチケットで、designer が作る回で画面を描き、mock-render を流した後（具体例の無い画面の状態の往復があれば、その最後の作る回の後）、段 2 で人に相談を始める前に、reviewer に screen-review を読ませ、描いた画面（PNG と mock-check.json）を見させる。承認の後に仕様が変わって描き直したときも動かす。写しを取る回、人のコメントか人の答えがきっかけの描き直し、動く試作の回では動かさない（人の意図による変更で、人がその場でキャンバスを見ている。段 2 の 3）。指摘の振り分けと往復は「レビューと直し」のとおり。すべての PNG は見させず、見る PNG の一覧を作って渡す
  1. 起動の前に `node .claude/aidd/bin/screen-review-list.mjs $0` で一覧を作る。1 回目（新しい場面の最初）は引数を足さない（足すか変える画面例はすべて主の幅で、もう一方の幅は画面の元と長い値の画面だけ。変えた共通部品の artboard と代表も入る）。承認の後に描き直したときは `--since <描き直す前のコミット>` を足す（描き直した画面例だけ）。2 回目からは `--since <直す前のコミット> --after <前の回の結果のファイル>`（組に分けたなら、カンマでつなぐ）を足す（前の回の指摘が指した画面例と、直した画面例と、画面の CSS を直した画面の画面例だけ）。主の幅は、領域の `mock/canvas.yaml` の widths の先頭である。「見る PNG がありません」なら、その回は動かさない
  2. 一覧は `<git の共通の場所>/aidd/tmp/$0/screen-review-list.json` に書かれる。見る PNG が 30 枚を超えると、画面ごとの組に分かれる（ほかの組の画面の元を、画面をまたぐ一貫を見るために添え、添えた分も含めて 1 組 30 枚までにする。reviewer が maxTurns（1 回の起動で返せる応答の回数の上限）の中で、ほかの読みものと結果を書くことも済ませるため）。組ごとに reviewer を 1 体ずつ順に起動し、一覧のファイルのパスと組の番号を渡す。cycle は組によらず同じで、結果のファイルは起動ごとに次の番号になる
  3. reviewer が返したら、`node .claude/aidd/bin/screen-review-list.mjs $0 --check <結果のファイル> --group <組の番号>` で、一覧の PNG をすべて開いたかを確認する。終了コード 1 なら、開いていない PNG を伝えて同じ reviewer を再開する。指摘は、すべての組が返ってから「レビューと直し」で振り分ける
- **お手本を撮る**：壁打ちのメモの「デザイン」に好きなサイトや製品の URL があり、`git rev-parse --git-common-dir` の下の `aidd/references/design/` にまだその PNG が無ければ、designer を作る回で起動する前に、`node .claude/aidd/bin/ref-capture.mjs <URL> ...` を流す（案件の Playwright で撮り、git の管理の外に置く）。001 のメモの URL は、001 より後の最初の機能のチケットの始めに撮る（001 の間は、案件の Playwright がまだ無い）。機能のチケットの見た目の壁打ち（段 2 の 1）で出た URL は、その話をメモに書いた後、designer を起動する前に撮る。撮れなかった URL は人に伝え、画像を置いてもらうか、無しで進む。この機械に Google Chrome が無くて終了コード 2 で終わったときも同じにする（外のサイトはサンドボックスを効かせた Chrome で開くため）
- **画像は会話に出ない**：Gate 1 の承認のページは手元のページ（`results/approval-draft.html`）を、Gate 2 の受け入れのページは手元のページ（`results/gate2.html`。作ったものとモックを並べる）を、ブラウザで開いて見てもらう。会話には、スクリプトが作る要点だけを出す

## 段 2：画面の相談
1. 描く：機能のチケットでは、designer に screen-mock で（作る回）画面を足すか直させ（壁打ちのメモの「デザイン」に見た目の希望があれば、それを読むよう伝える。spec-changes.yaml の renames に、前の領域の具体例を共通の要件の代表（`_shared`）に移したものがあれば、名前を付け替える画面例を伝える）、mock-render を流し、具体例の無い画面の状態の往復と画面のレビューを済ませる（上の「具体例の無い画面の状態」と「画面のレビュー」）。「状態：変える画面なし」なら段 3 に進む。「状態：停止（仕様の不足）」なら、足りないものを伝えて specification を再開して直させ、段 1 の 2 に戻る。001 では、designer に design-system で（作る回）選んだ案をデザインシステムにさせる
   - 見た目の壁打ち：機能のチケットで、壁打ちのメモの見た目の希望の答えが「話したい」で、「デザイン」にまだ見た目の話の言い直しが無ければ、designer を起動する前に行う。「画面を描く前に、見た目の希望を聞きます。話し終えたら『以上』と伝えてください」と伝え、壁打ちの 2 と 3 のとおり「以上」まで相談して言い直し、話したことと言い直しを壁打ちのメモの「デザイン」に書き足してコミットする。好きなサイトや製品の URL が出たら、上の「お手本を撮る」のとおり、designer を起動する前に撮る。項目、操作、知らせの文など要件にかかわる希望が出たら、3 の要件にかかわる直しと同じに扱い、仕様を直して段 1 の 2 から 4 を流してから描かせる（designer は要件と具体例に無い振る舞いを描かないため）
2. status.yaml に consult_started（at に今の時刻）を書いてコミットし、キャンバス（001 はデザインシステム）の URL を示して、「ここからは画面の相談です。キャンバスを直接直しても、コメントを『Send to Claude』で送ってもかまいません。終わったら『相談終わり』と伝えてください」と伝える（001 では、「画面の相談」を「デザインシステムの相談」、「キャンバス」を「デザインシステム」にする）
3. 人の番ごとに（人がチャットに何か書いたら）：
   - キャンバス（001 はデザインシステム、機能のチケットは screen-changes.yaml の screens と parts に載る領域のキャンバス。共通部品だけを変える領域も入る）のコメントを ArtifactComments で読む（URL は `_tech/design.yaml` と、領域の `mock/canvas.yaml`）。扱うのは、consult_started.at より後に「Send to Claude」で送られ、閉じていなくて、最後の発言が人のもののスレッドだけ。送られていないものは件数だけを伝える（人どうしのやり取りとみなす）。人が「コメントを送った」と書いたのに 1 件も無ければ、「Send to Claude」で送れているかを確認してもらう
   - 見た目や文だけの直し（チャットに書いたものも）は、designer に（直す回）中身を渡して直させる（designer は描く前にキャンバスを読んで人の直しを写し、texts-sync も流す）。mock-render を流す。画面のレビューは動かさない（人の意図による直しで、人がその場でキャンバスを見ている）
   - 要件にかかわる直し（項目、操作、メッセージを変える）は、specification に spec-hearing で直させ、段 1 の 2 から 4（spec-diff、traceability、spec-review）を流してから、designer に（直す回）描き直させる。画面のレビューは動かさない。コメントを入れるのに新しい要件（新しい画面、新しく扱うデータ、新しい操作）が要るときは、先に AskUserQuestion で「このチケットに含める」「別のチケットに分ける（後で切り出す範囲に足す）」「作らない」を問い、問いの文に、何が増えるかと、おおよその重さ（増える画面の数、ほかの画面への影響）を入れる。見た目や文の直しと、今ある要件の具体例を変えるだけの直しは問わずに直す。境目に迷ったら問う
   - 画面を見て出た、業務で答えが変わりうる問いは、specification に問いを書かせて AskUserQuestion で問う
   - 人がキャンバスを直接直しただけ（直すものを渡さない番）なら、designer に（写しを取る回。001 は読み直す回）今の中身を写させる。見た目だけでない人の直しを報告したら、要件にかかわる直しと同じに扱う
   - 「動く試作で確認したい」なら、designer に screen-mock で（動く試作の回）作らせ、キャンバスの URL を示し、「動きは AI が確認していないので、動かないところがあれば教えてください」と添える
   - 直したら、直した画面を先に示し、反映したコメントのスレッドへ ArtifactComments の reply で何をしたかを 1 文で返し、resolve で閉じる。反映しなかったもの（仕様担当が要らないと判断した）は、理由を返事して閉じない。送られていないコメントには触れない。続けて、次の番を待つ
4. 人が「相談終わり」と言ったら（「終わりです」「相談は以上」など、相談を終えたと読める言い方も同じに受ける）、designer に（写しを取る回。001 は読み直す回）キャンバスの今の中身を写させてコミットする。写しで画面が変わったら、mock-render を流す。designer が見た目だけでない人の直しを報告したら、3 の要件にかかわる直しと同じに扱う。続けて段 3 に進む
