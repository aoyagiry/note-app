# 000 と 001 だけの手順
aidd-run（`SKILL.md`）の、場面ごとの手順。$0 が 000-overall か 001-foundation のときに読む。節の名前だけで指している所（「レビューと直し」、段 1 の 5 など）は、SKILL.md の節である。

## 壁打ちを 2 回に分ける（001 で画面のあるシステム）
1 回目は技術の前提の話で、「壁打ち」の 2 と 3 のとおり「以上」まで相談して言い直す。続けて 2 回目に見た目の話をする。「次は見た目の話です。話し終えたら『以上』と伝えてください」と伝え、きっかけを示す：使う人にどう感じてほしいか、好きなサイトや製品のページ（URL）と、どこが好きか、嫌いなものとその理由、競合とどう違って見せたいか、使う場面、ブランドの性格、渡せる素材（ロゴ、写真）、ブランドや社内の色の決まり。好きなページの画像を見せたいときは、`git rev-parse --git-common-dir` の下の `aidd/references/design/` に置いてもらう（git の管理の外。他社のページの画像はリポジトリに入れない）。2 回目も、「壁打ち」の 2 と 3 のとおり「以上」まで相談して言い直す（2 つに分けると、技術の話に見た目の話が埋もれず、人がどちらも話し切れる）

## デザインシステムの候補（001 で画面のあるシステム）
段 1 の 1 で、`_tech/design.yaml` がまだ無いとき。
- 最初の specification の前に、designer に design-system で（候補の回）候補を描かせてコミットし、`node .claude/aidd/bin/ds-compare.mjs $0` で比較のページ（`results/ds-compare.html`）を作って `--orchestrator` でコミットし、`open specs/$0/results/ds-compare.html` で開く（段 1 で開くページの例外。見て選ぶこと自体が問いなので）。開くときに「デザインシステムは、色、文字、角の丸み、雰囲気など、すべての画面に共通する見た目を決めます。画面ごとの並びや配置は、それぞれのチケットで画面を描くときに決めます」と添える。続けて specification を前提の問いの回で起動する（どの案にするかの問いを書く）
- 人が選んだら、答えの記録と一緒に、選んだ案と理由、選ばなかった案を壁打ちのメモの「デザイン」に書き足す。人が直させたいと答えたか、前提の問いの答え（素材、色の決まり）が候補とぶつかるなら、designer を候補の回でもう一度起動し、直す中身を渡す

## 000 の前半の確認
000 の前半の後は、approval-draft を流して下書き、ページ、要点（results/ の 3 つ）を作ってコミットし、ページを開いて要点を会話に出し、「この内容でチケットの一覧を作ってよいですか」を問う（選択肢は「作ってよい」と「直したい（書く）」。承認ではない）。「作ってよい」なら、status.yaml の log に「前半を確認した」と書いて一緒にコミットし、後半として段 1 の 1 に戻る（/clear の後に前半を見せ直さないため）。「直したい」なら、specification を再開して直させ、段 1 の 2 に戻る

## CI の確認（001 だけ）
コードレビューの後、Gate 2 の提出の前に行う。
1. `ci-check/001-foundation` のブランチに、何も壊さない小さな変更を置いて PR を作り（向け先は aidd/001-foundation、下書きにしない。ブランチの切り替えとコミットは別のコマンドで行う。1 つにつなぐと、guard-bash が切り替える前の aidd/ のブランチの上のコミットとして止める）、`gh pr checks <PR> --watch` で CI が緑になることを確認する
2. 同じブランチに、失敗するテストを 1 つ足して push し、CI が赤くなることを確認する
3. PR を閉じてブランチを消し、aidd/001-foundation に戻る。`specs/001-foundation/results/ci-check.yaml` に green と red の { commit, result, url } を書いてコミットする。result は、CI が通ったら success、落ちたら failure と書く
