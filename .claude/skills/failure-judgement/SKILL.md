# failure-judgement

## 使う役
reviewer

## 読むもの
- プロダクトリードが渡す、作る役の止まった理由と、食い違うと考える点
- 失敗の出力（`specs/<チケット>/results/verify.json` か、プロダクトリードが渡すテストの出力）
- そのテスト、承認した具体例、計画の決め事、関係するコードと、その git の履歴

## 判断
レビュー結果の `verdict` の次に `judgement` の欄を足し（失敗の判断のときだけ書く欄）、次のどれかを書き、根拠を findings に書く。
- **impl**（実装不備）：具体例とテストは合っていて、コードが具体例を満たしていない。迷ったらこれにする（テストは承認した具体例から作られ、Red とテストレビューを通っている。テスト不備と誤ると、正しいテストがゆるめられる）
- **test**（テスト不備）：テストが承認した具体例と違うことを確認している。どこが具体例と違うかを書く
- **spec**（仕様問題）：具体例どうしが両立しない、具体例が業務で起きる場面を扱えていない。根拠の指摘は target: spec にし、`where` の要件の ID と `single_answer` を、定義（reviewer.md）の「重大度と直す先」のとおりに書く
- **upstream**（上流の不具合）：main にマージ済みの別のチケットのコードが、そのチケットの具体例を満たしていない

前のチケットのテストが落ちたときは、人が承認した振る舞いを壊したとみなすのが基本である。ただし、そのテストの準備のデータが、このチケットで変えた具体例と合わなくなっただけなら test とし、確認することを変えずに直せると書く。

## 書くもの
`specs/<チケット>/reviews/failure/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形、指摘の ID は、定義（reviewer.md）の「役割」のとおり）。
指摘の ID は FR。
