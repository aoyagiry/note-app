# test-review

## 使う役
reviewer

## 読むもの
- テストのファイルの差分（`git diff <マージの基点>` で自分で見る）
- 承認した具体例（変える領域の `specs/_current/<領域>/requirements.yaml`）と、`plan/details.yaml` の test: true の決め事、`plan/implementation-plan.md` の約束（テストが呼ぶ形）
- `specs/<チケット>/results/red-run.json`（テストを書く役が最後に流したテストの出力。Red の根拠）、`results/red-result.md`。Red の e2e は、Red の印（環境変数 `AIDD_RED=1`）でパソコンの幅の project だけで流れる（ほかの幅の e2e は red-run.json に出ない。architecture.md のテストの節）
- テストを直して戻ったときも全体を見る。プロダクトリードが伝える直す前のコミットからの差分は、まず見る所の手がかりにする。例外は、実装中にテストの設定だけを直して戻ったとき（下の「見るもの」の該当の行）で、プロダクトリードが渡す差分だけを見る

## 見るもの
- どの具体例も、テストがその具体例のとおりに確認しているか（期待する結果が、具体例と仕様の結果の写し方（architecture.md）と計画の決め事から出ているか）。uses で共通の要件（`_shared/rules.yaml`）を指す操作ごとに、その共通の要件の代表の具体例の ID（`_shared/AC-…`）のテストがあるか
- 既存のテストの期待する結果を変えたなら、そのテストが確認する具体例、仕様の結果の写し方、計画の決め事のどれかが変わっているか。前の領域の具体例を共通の要件の代表に移した（spec-changes.yaml の renames）ために、テストの名前の ID だけを書き換えたのは、確認することを変えていなければよい。変わっていないのに期待する結果を変えた、ゆるめた、消したら critical。ファイルの移動や準備のデータの直しは、確認することを変えていないか
- Red が正しい理由で落ちているか（期待する結果の不一致、受け口が無いための 404 など、まだ無い画面の要素を待つ e2e の期限切れ。要素の待ちや操作の待ちの上限で落ちるのは正しい）。import のエラー、テスト 1 件の待ちの上限での失敗、それ以外のタイムアウト（画面を開けない、サーバーが起動しない）、環境のエラーは誤った Red。ただし基盤づくりでは、これから作る雛形のファイル（package.json など）が無いための失敗は正しい Red。操作の前の前提の確認（test-generation の 1）で、前提の値が違って落ちたものは誤った Red（準備の誤り）。このチケットで作るデータの関数がまだ無くて落ちるのは正しい Red。前からある e2e が Red の印で操作か expect の待ちの上限で落ちたものは、誤った Red とせず、待ちの短さとして verdict に書く（red-result.md に、そのファイルを Red の印なしで流し直して通ったことが書いてあるかを見る）
- 最初から通るテストに、red-result.md の「最初から通ってよいテスト」の理由があり、成り立つか
- 画面のあるチケット（`specs/<チケット>/screen-changes.yaml` がある）では、載っている artboard ごとに撮るテストがあるか。名前（`e2e-screenshots/<領域>--<SCR の ID>[--<AC の ID>][--<幅の名前>].png`）と撮る幅が、計画で決めたとおりか。モックだけの画面（`variant`）を撮っていないか。テストの中で見た目を比較していないか（比較はハーネスの検証が行う）。画面例は、その具体例の then を確認した後に撮っているか（画面例が具体例の途中の場面を描いているときは、その場面を確認した直後に撮っているか。test-generation の 4）
- 「見つからない」「ログインしていない」を期待する否定の具体例は、受け口を置いたうえで落ちているか（フレームワークの既定の応答で通っていないか）
- テストを直して戻ったときは、直したテストが承認した具体例のとおりか（通すためにゆるめていないか）
- 実装中にテストの設定だけを直して戻ったとき（プロダクトリードが伝える）は、渡された差分だけを見て、設定の直しが作ったもの（起動のコマンド、ポート、ファイルの置き場所）に合わせたものか、テストが確認することを減らしていないか（待ちの上限を延ばして落ちるテストを通す、振る舞いを持つコードをカバレッジから外す、テストのファイルを流す対象から外す）。Red は見直さない（red-run.json は、テスト作成中に流したもののまま）
- 仕様の穴（具体例どうしが両立しない、具体例が足りずテストの期待する結果が決まらない）は target: spec で指摘する。`where` の要件の ID と `single_answer` は、定義（reviewer.md）の「重大度と直す先」のとおりに書く

重大度と直す先は、定義（reviewer.md）の「重大度と直す先」のとおり。

## 書くもの
`specs/<チケット>/reviews/test/<番号>-c<cycle>.yaml` に書く（ファイルの名前と形、指摘の ID は、定義（reviewer.md）の「役割」のとおり）。
