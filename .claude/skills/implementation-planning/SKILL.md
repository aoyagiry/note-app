# implementation-planning

## 使う役
planner

## 読むもの
- `specs/<チケット>/results/spec-diff.json`（承認した仕様の差分、uses でたどった影響）、`specs/<チケット>/status.yaml` の affects（今あるものへの影響の一覧）と、変える領域と uses で指す領域の `specs/_current/<領域>/requirements.yaml`
- `specs/_current/_tech/`（architecture.md、tech.yaml、write-scopes.json）、今のコード
- `specs/_notes/` のうち、名前と「当てはまる」から関係しそうなもの
- 仕様の差分が無いチケット（不具合の修正、依存の版の更新）では、壁打ちのメモ（`hearing/brainstorm.md`）の直し方と壊れている具体例
- 前のチケットの `plan/details.yaml`（同じ決め事があれば same_as で、変える決め事があれば replaces で指すため）

## 書くもの
`specs/<チケット>/plan/implementation-plan.md`（`.claude/aidd/templates/implementation-plan.md` の見出しのまま）と `plan/details.yaml`（`.claude/aidd/templates/details.yaml` の形）を書く。
- **テストが呼ぶ形（約束）**：テストが呼ぶ形。API なら、メソッドとパス、受け取る欄、返す欄。関数を直接呼ぶなら、名前と引数と戻り値。仕様の結果の写し方と基盤の構成（architecture.md）に沿わせる。テストを書く役と作る役の両方がこれに従う
- **details（計画の決め事）**：誰も当てにしない細部（名前の前後の空白を除く、など）。plain に、何を決めたかを CLAUDE.md の「守ること」の 10 のとおりに 1 行で書く（Gate 2 で畳んで見せる）。仕様の結果の写し方やライブラリの既定から外れるなら、reason に理由を書く。テストで確認するなら test: true（業務で効く細部だけ）、確認しないなら test: false と no_test_reason。前のチケットと同じ決め事は same_as で指す。前のチケットの決め事を変えたら、変えた決め事の replaces にその ID（例：`005/PD-005`）を書く（仕様の全体のページで、変えられた古い決め事が「後のチケットで変わった」として畳まれる。書かないと、古い決め事が今のもののように並ぶ）
- **変え方の方針（案内）**：既存のどこをどう変えるか、新しく何を作るか。既存の関数やコンポーネントを使えるなら使う。関係する `_notes` の事実を反映し、「反映した _notes」にその名前を挙げる
- **作る順番と触るつもりのファイル（案内）**：作る順番と触るつもりのファイル。ID は付けず、文章でよい。ファイルごとに、テストを書く役と作る役のどちらが書くかを分け、各ファイルがその役の書き込み範囲（`_tech/write-scopes.json` と、コアが決める置き場所（`.claude/aidd/lib/scopes.mjs` の CORE。作る役の `.gitignore` や画面文の一覧など）の和）に入っているかを確認する。Red の前に要るもの（e2e の設定、止めた時刻の表など）と、作りに合わせて変わるテストの設定の直し（webServer の起動のコマンドとポート、カバレッジから外すファイルなど）は、前もってテストを書く役の分担に入れる（作る役はテストの設定とテストの支えを変えられない）

## 画面のあるチケット
`specs/<チケット>/screen-changes.yaml` があれば、そこに載っている artboard（画面の元 `specs/_current/<領域>/mock/project/<SCR の ID>.dc.html` と、画面例 `<SCR の ID>--<AC の ID>.dc.html`。それらが読む画面の CSS `<SCR の ID>.css` と、`<dc-import>` で読むモックの共通部品も）と `_tech/design.yaml` も読み、計画に次を書く。
- どの具体例を e2e で確認するか（画面で起きることだけ。要件の細部は API のテストやユニットテストで確認する）。このチケットの要件が uses で指す共通の要件の代表の具体例（`_shared/AC-…`）も入れる（指す操作ごとに確認する）。screen-changes.yaml の `examples` に載った具体例は、`also` の具体例も含めて、すべて e2e で確認する（then が画面に見えるため。撮るのは代表の `ac` だけ）。modified の具体例（前のチケットの画面例を描き直しただけ）は、前のチケットの撮るテストをそのまま使い、新しく決めない
- `_tech/design.yaml` がこのチケットで変わったら（Designer がデザインシステムの値を足すか変えた）、変え方の方針に「共通の値（CSS の変数のファイル）を design.yaml に合わせる」と書く（基盤の検査の design-tokens が、作る前は落ちる）
- `_tech/ds/<フォルダ>/base.css` がこのチケットで変わったら（Designer がデザインシステムの土台の CSS を足すか変えた）、変え方の方針に「土台の CSS のファイルを base.css の中身に写し直す」と書く（基盤の検査の design-base が、作る前は落ちる）
- screen-changes.yaml の `parts` に共通部品が載っていたら（Designer が共通部品を足すか変えた）、変え方の方針に、作るものの対応する共通の部品（ヘッダー、ナビゲーションなど）を合わせることを書く。それを読む画面は screens に載らないが、作ると e2e の見た目が変わる（検証が「共通部品で変わった画面」として並べ、コードレビューが崩れを見る）。読む画面の撮るテストは新しく決めない
- 撮るテスト：画面の元（screen-changes.yaml の画面の `change` が unchanged でないもの）は、画面を開いたときを撮るテストを 1 つ（`e2e-screenshots/<領域>--<SCR の ID>.png`）。画面の元が modified でも、その領域に仕様の変更が無ければ（spec-diff に無い。デザインシステムの値を変えて、見た目だけが変わった画面）、前のチケットの撮るテストをそのまま使い、新しく決めない（確認する見える要素が無く、Red にできないため。前のチケットの撮るテストが、毎回の e2e で同じ名前の画面を撮り直す）。画面例は、その具体例の e2e のテストの終わり（then を確認した後）に撮る（`e2e-screenshots/<領域>--<SCR の ID>--<AC の ID>.png`）。画面例が具体例の途中の場面を描いているときは、その場面を確認した直後に撮る（test-generation の 4）。画面の幅（`_tech/design.yaml` の breakpoint）を決めた案件では、名前の末尾に `--<幅の名前>` を付け、領域の `mock/canvas.yaml` の screens の widths（無ければ breakpoint の最初の幅）の幅ごとに撮る（例：`rooms--SCR-list--phone.png`）。モックだけの画面（`variant`）は撮らない
- 画面の要素の見つけ方（ラベルや役割。モックの文言に合わせる）
- 動き（`_tech/design.yaml` の motion を使う画面）があれば、動きごとに CSS で作るか JS で作るかを約束に書く（テストを書く役が、どう確認するかを決めるため）
- 撮るテストの準備のデータ（モックの一覧の行などに書いた値にそろえる。画面例は、その具体例の given の値で描かれている。違うと、見比べで違いとして出る）
- 画面の道：`plan/details.yaml` の `screen_paths` に、このチケットで足すか変える画面（screen-changes.yaml の画面）ごとの道（`/rooms/new` など）を書く（Gate 2 の受け入れのページに、人が開く URL として出る）
- 試す日時：日付か時刻で中身が変わる画面（今日の名簿、締め切りの前と後で変わる画面など）を足すか変えるチケットだけ、`plan/details.yaml` の `try_at` に、画面を試す日時を 1 つ書く（ISO 8601。例：`2027-05-12T16:00`。具体例の前提の日時から、このチケットの画面が中身を持って見える日時を選ぶ）。toolchain.yaml の `start.clock` の `{at}` に入り、Gate 2 の受け入れのページの「画面を開く」に、開く日によって試せないときの道として出る
- 試すデータ：toolchain.yaml の `start.seed` があれば、作る順番の案内に「seed に、このチケットの画面を開いて試せるデータを足す」と書く（作る役が足す。テストの準備の関数を使い回してよい。人が Gate 2 で画面を開いたとき、空の画面にならないように）
振る舞いは要件と具体例に従い、モックからは見た目（並び、文言、値）だけを取る。モックが要件と具体例と食い違えば、計画で埋めずに止まる（仕様の問題）。

## 判断の決まり
- よい設計を渡す。テストを書く役と作る役は Sonnet で、この計画に従う。ただし、使われない一般化や先回りの作り込みはしない
- 一覧に無い業務の結果（architecture.md の「仕様の結果の写し方」に無い語）が要れば、計画の決め事で技術の形を決める
- テストごとの Red の理由（どのテストが何で落ちるか）の見込みは書かない。Red の理由はテストを書く役が red-result.md に書き、テストのレビューが見る
- 技術を入れ替えるチケットでは、当てはまらなくなりそうな `_notes` の事実を方針に挙げる（作る役が確認して廃止する）
- 影響の一覧が空でないときは、方針に、一覧の各行への影響（既存の振る舞いとほかの領域）を書く
- 仕様に、業務で答えが変わりうる漏れや誤りを見つけたら、計画で埋めずに止まる（仕様の問題）。報告には、かかわる要件の ID（領域を付ける）と、今の要件から答えが 1 つに決まるか（決まらないなら答えの候補）を書く（決まらないとした穴は、必ず人に問われる）。細部の漏れは計画の決め事で決める
- 自信の無い難しい実装（決まった手順のある処理、標準の仕様、セキュリティにかかわるもの）は、自分で作り方を考える前に、広く使われている OSS の実装かライブラリを調べ、計画の決め事に、参照した実装（名前と URL）と選んだ理由を書く。今の依存で作れるなら、その実装を参考に方針を書く。新しいライブラリが要ると分かったら、後で変えにくい選択なので自分では決めず、止まる（仕様の問題。仕様担当が技術の選択に書き、人に見せる）

## 終わったとき
報告に、書いたファイルと、仕様の問題（あれば）を書く。
