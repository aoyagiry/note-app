# foundation-hearing

## 使う役
specification

## 読むもの
- `specs/001-foundation/hearing/brainstorm.md`、`specs/_current/_intent/`、`specs/_current/_shared/`（非機能要件は、選ぶ技術で満たせて確認できなければならない）、`specs/ticket-plan.yaml`、`specs/_references/`
- プロダクトリードが伝える回（前提の問いの回か、下書きの回か）と、前の回の答え

## 1. 前提の問い
次のうち、壁打ちのメモで分からないものだけを問う。事実を答えるだけなので、短く問う。
- 社内の標準（使ってよい言語やクラウド、決まった道具）
- 動かす環境（どこで動かすか。今はローカルだけでもよい）
- マシンに入れてよいもの（Docker などを入れてよいか）
- リリースとデプロイ：環境、デプロイのきっかけ、本番へ反映する人、切り戻しの方法。「今はローカルだけで開発し、デプロイは後で決める」も選べる。後で決めるなら、`specs/ticket-plan.yaml` の later に「デプロイ」を置く。デプロイを決めて、作ったものを公開して使い始めるチケット（公開のチケット。later の「デプロイ」を切り出したものなど）の行には `release: true` を付ける（公開の後でないと確認できない非機能要件（after_release）が、そのチケットの Gate 2 で人の判断に出る）
- 画面のあるシステムなら、デザインシステムの候補（`specs/001-foundation/ds-candidates/` の案ごとの `about.md`）からどの案にするか。案ごとに方向の名前と引き換えを選択肢にし、推奨と理由を書く（比較のページを見てもらう）。理由には、パソコンの幅とスマホの幅での見え方も書く。ほかに前提の問いが無くても、この回はこの問いのために開く。雰囲気や参考のサイトは壁打ちで聞いているので問わない。候補を作るのに要る事実（渡せる素材、ロゴやブランドの決まり、社内の色の決まり）が壁打ちで出ていなければ、それも問う

## 2. 技術の土台の下書き
書くファイルの形は、それぞれのテンプレート（`.claude/aidd/templates/tech.yaml`、`.claude/aidd/templates/architecture.md`、`.claude/aidd/templates/toolchain.yaml`）のとおりにする。
前提の答えから、技術を自分で決めて書く。選択肢はほとんど標準に沿って決まる。
- `_tech/tech.yaml`：技術の選択。開いて見せるのは、後から変えると作り直しが大きいか使う側に影響し、その影響を業務の言葉で説明できるものだけ（言語と動かす仕組み、Web のフレームワーク、データの持ち方、エラーの返し方の 4 件ほど）。これには background、alternatives、if_changed を書く。alternatives の effect は、選ばなかった理由の一言（30 字ほど）にする。詳しい比較が要るなら architecture.md に書く。ほかは summary を 1〜2 行で書いて畳む（データをメモリに持つので再起動で消える、のように、畳まれると困ることは開く）。summary の技術の言葉は CLAUDE.md の「守ること」の 10 のとおり、決まった呼び名（アクセシビリティの検査、カバレッジ、lint など）を言い換えずに使う（「見やすさの検査」のように、言い換えで意味が変わると、人が違うものを承認する）
- `_tech/architecture.md`：技術スタック、構成とレイヤ、標準のファイル構成、仕様の結果の写し方、テスト、開発環境と人が行う準備、CI、リリースとデプロイ、依存の版の範囲。仕様の結果の写し方には、具体例で使う結果の語（受け付ける、見つからない、断られる（要件に反する）、ほかと重なる、権限が無い、ログインしていない、など）ごとに、技術の形（状態コード、エラーの形）を広く使われている標準に沿って決める。「エラーの返し方」として tech.yaml の開いて見せる選択にも入れる。テストの節には、テストの設定とテストの支えの置き場所（テストを書く役が書き、作る役は変えない）を書く。また、準備のデータを入れるときは、その領域のデータの読み書きの関数か、開発する人のコマンドと同じ関数で入れ、テストに SQL を直に書かないと書く（後片付けの削除は除く。前の領域のコードが書く形と準備がずれないように）
- `_tech/toolchain.yaml`：準備のコマンドと定義ファイル（setup）、依存の定義（dependencies）、検証のコマンド（テストのレベルごと、型、書き方、ビルド、起動の確認、脆弱性の検査、カバレッジ）。テストのコマンドの名前は `test` で始める（`test-unit`、`test-e2e`、基盤の検査は `test-foundation`。テストを書く役が Red でこれだけを流す）。ほかのコマンドの名前は `test` で始めない。テストの結果、カバレッジ、ビルドの出力は .gitignore に入れる（流した後に作業ツリーに残らないように）。テストのファイルの名前は `*.test.*` か `*.spec.*` にする（ハーネスはこの名前でテストを見つける）、計測のコマンド（measurement の非機能要件ごと）、道具で確認する非機能要件（check: tool）ごとに確認する検証のコマンドの名前（`nfr_commands`。非機能要件の ID と commands の名前。例：アクセシビリティの非機能要件と、axe で検査するコマンド。Gate 2 の受け入れのページに、そのコマンドの結果と並んで出る）、テストの結果の置き場所（test_reports）。テストのコマンドはテストが 0 件でも成功し、結果を JUnit XML で test_reports に出す設定にする。テストのコマンドは、末尾にテストのファイルを渡すと、そのファイルだけを流せる形にする（基盤の検査が見本のテストだけを流すため）。カバレッジは具体例から到達しないもの（起動処理、設定）を除く。脆弱性の検査のコマンドは、000 で決めた深刻度の線で落ちるようにする
- `_tech/write-scopes.json`：形は `{ "test-writer": { "allow": ["tests/**", …], "deny": […] }, "implementer": { "allow": […], "deny": […] } }`（キーは役の名前、allow と deny はパスの glob の並びで、deny は省ける。allow に `specs/`、`.claude/`、`CLAUDE.md` で始まるものは書けない）。テストを書く役は、テストのファイル、テストの設定（playwright.config.ts、vitest.config.ts など）、テストの支え（テストだけが読む準備の関数、時刻の表など）と、実装のファイル（受け口を置くため）を書ける。作る役は、実装と、テストの設定を除く設定と、CI のファイルを書け、テストのファイル、テストの設定、テストの支えは書けない（作る役の deny に入れる。テストを実装の隣に置くなら、テストのファイルの形も入れる）。テストの設定は、アプリの設定と分けたファイルに置く（Vitest の設定を vite.config.ts に混ぜない）。001 でも、テストの設定はテストを書く役が書く
- CI：PR（向け先が main と `aidd/**`）と main への push で、検証のコマンドと `node .claude/aidd/bin/traceability-check.mjs --stage baseline` を流す。ハーネスのライブラリが要るので、その前に `npm ci --prefix .claude/aidd` を流す。下書きの PR では流さない。コミットの文に `[skip ci]` のある push では流れない（GitHub の決まり。Gate 2 の提出の、結果のページと状態だけのコミットに使う）。ジョブに時間の上限（`timeout-minutes: 20` ほど）を置く（止まったときに、GitHub の既定の 6 時間まで待たないように）。npm のキャッシュを付ける（actions/setup-node の cache）。単体と API のテストはカバレッジのコマンドの回で流し、別に流さない（同じテストを 2 回流さない）。画面のあるシステムでは、ジョブを Playwright の公式のコンテナのイメージ（案件の Playwright と同じ版）で流し、OS のパッケージを毎回入れない（OS のパッケージを入れる段は、外のミラーにつながらずに止まることがある）。e2e は matrix と Playwright の `--shard` で 2 つのジョブに分け、データベースを使うならジョブごとにデータベースのサービスを置く。`traceability-check.mjs --stage baseline` と e2e でない検証のコマンドは、分けない側のジョブで 1 回だけ流す（traceability-check はテストのファイルの中の名前を見るので、ジョブを分けても流せる）。main への push の CI も、同じ形で残す。非公開のリポジトリでは無料の実行時間に月ごとの上限があるので、畳んだ説明に、無料の範囲で足りる見込みかを添える
- 書き方の決まりは道具（ESLint など）で確認し、git の hook は使わない
- 画面のあるシステム（`_intent/intent.yaml` の範囲の作るものに画面がある）では、先にこのスキルのフォルダの `screens.md`（`.claude/skills/foundation-hearing/screens.md`）を読み、そこにあるものも決める（e2e と Playwright、スクリーンショット、画面の文、見た目の共通の値、土台の CSS、作った画面を人が開く手順）

## 3. 基盤の受入条件
`_tech/acceptance.yaml` に、`.claude/aidd/templates/tech-acceptance.yaml` の形で、観点ごとに書く。
テストの道具を確認する観点（test-levels、visual-regression、test-report）は、検査がその場で置く見本のテスト（必ず通るものと必ず落ちるもの。テストの置き場所の下の一時のフォルダ（`e2e/zztmp/` など）に置き、終わったら消す）のファイルだけを、テストのコマンドに渡して流す形で書く。プロジェクトの本物のテスト全体は流さない（基盤の検査は検証、Red、CI のたびに流れるので、本物のテストを流すと、テストが増えるほど重くなる）。見本のテストを流す子のプロセスの環境からは、Red の印（`AIDD_RED`）を除く（除かないと、Red の記録の回に見本の e2e がパソコンの幅だけで流れ、基盤の検査が落ちる）。検証のコマンドが全部通るかを確認する観点は置かない（チケットごとの検証が同じコマンドを流すので重なる）。
| 観点 | 中身 | checked_by |
| --- | --- | --- |
| test-levels | テストのレベルごとに、見本の成功するテストが成功し、見本の失敗するテストが失敗する。e2e は一時的な画面で確認し、スクリーンショットが決めた名前で出ることも確認する | test |
| visual-regression | 見た目の回帰テストが変化を見つける：一時的な画面の見た目を変えて撮ると、`.claude/aidd/lib/visual.mjs` の `comparePng` で、基準との違いが visual_threshold を超える（画面のあるシステムだけ） | test |
| design-tokens | コードの共通の値（CSS の変数）が、`_tech/design.yaml` の値（breakpoint を除く。色、文字、間隔、角の丸みと、あれば size、border、shadow、motion、effect）と一致する（画面のあるシステムだけ） | test |
| design-base | コードの土台の CSS のファイルの中身が、`_tech/ds/<フォルダ>/base.css` と同じ（画面のあるシステムだけ） | test |
| test-report | 見本のテストを流すと、テストの結果を JUnit XML で test_reports に出す | test |
| errors | 想定外の例外が起きても、決めたエラーの返し方で返し、例外の文やスタックトレースを外に出さない | test |
| structure | 標準のファイル構成と、設定が決めた技術どおり | test |
| dev-env | 開発環境を作れる | test |
| write-scopes | 作る役がテストのファイルかテストの設定を変えると、コミットの検査（scope-check）が止める | test（最初から合格してよい） |
| ci | PR で検証が走り、失敗するテストがあれば赤くなる | ci |
| deploy | デプロイの仕組みが動く（デプロイを決めたときだけ） | human |

## 4. 決める項目の確認の一覧
下書きを渡す前に、次がそろっているかを自分で確認する。言語と実行環境、Web のフレームワーク、データの持ち方、エラーの返し方と写し方、構成とレイヤ、テストのレベルと道具、テストの設定と支えの置き場所、検証のコマンド、開発環境の準備、書き込み範囲、CI、リリースとデプロイ（後で決めるなら later）、依存の版の範囲。テストの準備のデータの入れ方。画面のあるシステムでは、e2e の道具とブラウザの置き場所、e2e が自分のサーバーを相手にすること、動きのテストの設定、画面の幅の名前と大きさ（breakpoint）、時計の固定と動きを止める設定、visual_threshold、スクリーンショットの出し方、見た目の共通の値のファイル、土台の CSS のファイル、文節の区切りの手当て、画面を開く手順と試すデータの入れ方（start。データベースを起こす所から含めた seed と、日時を決めて起こすコマンド clock も）。道具で確認する非機能要件があれば、その検査のコマンドと nfr_commands。

問いは、定義（specification.md）の「問いの書き方」のとおりに書く。

レビューの指摘を直すときは、spec-hearing の「レビューの指摘を直すとき」に従う（場合を足す前に考える 3 つと、同じ形を同じ回に直すこと）。

## しないこと
- 技術の選択を人に問うこと（後で変えにくい選択として Gate 1 の承認のページで見せる）
- 回数の上限やハーネスの都合の数を問うこと（変えたいときは `_tech/harness.yaml` を変えるチケットで直す）

## 終わったとき
報告に、書いたファイル、開いて見せる技術の選択、書いた問いの数を書く。
