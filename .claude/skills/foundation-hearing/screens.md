# 画面のあるシステムで決めること
foundation-hearing（`SKILL.md`）の「2. 技術の土台の下書き」の続き。画面のあるシステムのときだけ読む。

画面のあるシステム（`_intent/intent.yaml` の範囲の作るものに画面がある）では、次も決める（デザインシステムは Designer が同じ時点で作り、値を `_tech/design.yaml` に書く）
- テストのレベルに e2e を置き、道具は Playwright にする（ハーネスも、モックの PNG を撮るのに案件の Playwright を使う）。自分のサーバーがあるときは、e2e はビルドしたサーバーを起こして相手にし、その API を差し替えない（差し替えてよいのは外のサービスだけ。画面とサーバーのつなぎ目を e2e が確認するため）。e2e のテストは、画面ごとと画面例ごとにスクリーンショットを `e2e-screenshots/<領域>--<SCR の ID>.png`（例：`rooms--SCR-list.png`）と `e2e-screenshots/<領域>--<SCR の ID>--<AC の ID>.png` に出し（画面の幅（`_tech/design.yaml` の breakpoint）を決めた案件では、名前の末尾に `--<幅の名前>` を付け、領域の `mock/canvas.yaml` の screens の widths（無ければ breakpoint の最初の幅）の幅ごとに撮る（例：`rooms--SCR-list--phone.png`））、ほかのテストと同じく結果を JUnit XML で出す。`e2e-screenshots/` は .gitignore に入れ、Playwright の出力先（`test-results/`）の下に置かない（Playwright は実行のたびに出力先を空にするので、後に流れるテストに消される）。基盤の検査も `e2e-screenshots/` を消さない。Playwright の設定で `locale: "ja-JP"` を使い、ブラウザの起動に `--lang=ja-JP` を渡す（`launchOptions.args`。ページの locale だけでは日付の入力欄の並びが変わらない。モックの PNG と、日付などの書き方をそろえる）。画面のビルドとサーバーの起動を待つ長さは webServer の timeout に置き、テスト 1 件の待ち時間は道具の既定のままにする（テスト 1 件の待ち時間を延ばすと、まだ画面の無い e2e が 1 件ずつ待ち切ってから落ち、Red の確認が長くなる）。操作の待ち（actionTimeout）と移動の待ち（navigationTimeout）は数秒（目安 5 秒）にし（上限が無いと、まだ画面の無い e2e が操作ごとにテスト 1 件の待ちの上限まで待つ）、expect の待ちは道具の既定のままにする。ただし Red の印（環境変数 `AIDD_RED=1`。run-capture.mjs と、テストを書く役が Red を確認する回に付く）があるときだけ、操作の待ちと expect の待ちを 1.5 秒にし（移動の待ちは 5 秒のまま）、project をパソコンの幅のものだけにする（まだ画面の無い e2e を早く落とし、Red を速くするため）。パソコンの幅の project は、すべての e2e のファイルを流すようにする（Red の回にも、どの e2e のファイルも流れるように）。これらの待ちと Red の印のときの形を architecture.md に書く。画面の幅の名前と大きさ（例：desktop 1280×800、phone 390×844。最初の幅が、canvas.yaml に widths を書かない画面の既定になる）を決め、`_tech/design.yaml` の breakpoint（Designer が書く）と architecture.md に書く（e2e の viewport とモックの大きさになる）。e2e は振る舞いを確認し、スクリーンショットを撮るだけにする（見た目の比較はテストの中に書かない。ハーネスの検証が、受け入れた見た目の基準と比較する）。画面の下に固定した部品（bottom を指定した sticky と、下に近い fixed）があり、ページが画面より高い画面は、撮る支えの関数で `.claude/aidd/lib/pin-fixed.mjs` の関数（固定した部品を見つける `findPinned`、ページの下端に置く `pinToBottom`、元に戻す `unpin`。型は隣の `pin-fixed.d.mts`）を `page.evaluate` に渡し、部品をページの下端に置いてから全体を撮り、撮った後に戻す（そのまま撮ると、部品が全体の画像の途中に重なる）。画面の元は、その前に最初の 1 画面（画面の大きさの分だけ）を、名前の末尾に `--top` を付けて撮る（例：`rooms--SCR-list--phone--top.png`。開いたときの見え方を見る。モックの PNG も mock-render が同じ関数で同じに撮る）と architecture.md に書く。撮る前に揺れを止める：サーバーとブラウザの時計を具体例の「今日」に固定し、動画と時間で動く動きは、動きを減らす設定（`reducedMotion: "reduce"`）で止める。比較は手元の検証だけで行い、CI は撮るだけにする（基準は手元の OS で作るため）。違いとみなす画素の割合を toolchain.yaml の `visual_threshold` に書く（目安 0.001）
- 動きのテスト：動きのある画面（`_tech/design.yaml` の motion を使う画面）を確認する e2e は、`page.emulateMedia({ reducedMotion: "no-preference" })` で動きを減らす設定を外す。JS で作る動きは Playwright の時計（`page.clock.install()`。requestAnimationFrame と performance も差し替える）で確認するので、install はほかの時計の呼び出しより先に呼び、その時刻を具体例の今日にする（時計の固定とぶつけないため）と architecture.md に書く
- ブラウザは、プロジェクトの中の `.browsers/` に入れ、.gitignore に入れる。`node_modules` の中（`PLAYWRIGHT_BROWSERS_PATH=0`）には置かない（`npm ci` で消え、Mac では起動直後に落ちることがある）。準備のコマンド（setup）、e2e のテストのコマンド、CI に、`PLAYWRIGHT_BROWSERS_PATH=<リポジトリ>/.browsers` を渡す。準備のコマンドと CI で `npx playwright install chromium` で入れる（CI の OS のパッケージはコンテナのイメージに入っているので、`--with-deps` は付けない）
- 画面の文：画面の文は画面文の一覧（`specs/_current/<領域>/texts.yaml` と `_tech/texts.yaml`。Designer が書く）から ID で取り、コードに直に書かないと architecture.md に書く。API は文を返さず理由の符号を返し、画面が符号に当たる文を画面文の一覧から引く（architecture.md の「仕様の結果の写し方」のエラーの形に書く）。画面と API のサーバーが分かれているときの、画面文の一覧の取り込み方（ビルドのときに読み込む、など）と、値の入る所（`{名前}`）の埋め方も決める
- 見た目の共通の値：`_tech/design.yaml` の値（色、文字、間隔、角の丸み）を、コードの共通の値（CSS の変数のファイル）に写す決まりと、そのファイルの置き場所を architecture.md に書く。変数の名前は、デザインシステムの tokens.css と同じにする（design.yaml の欄の道筋を kebab にしてつなぐ。例：`--color-surface-sunken`、`--spacing-5`。作る役が、モックの `var(--…)` をそのまま当てられるように）。そろえるのは名前だけで、暗い表示への切り替え方はコードの側で決める。画面は、色、文字、間隔、角の丸みと、design.yaml にあれば size、border、shadow、motion、effect を、この変数だけで指定する。breakpoint は CSS の変数にしないので、design.yaml の値を architecture.md に写す。書体は、デザインシステムの tokens.css の `@import` を使わず、npm のパッケージなどで同じ書体を入れる。e2e は、撮る前に書体の読み込みを待つ（`document.fonts.ready`）と architecture.md に書く（外の読み込みの揺れを、見た目の違いにしない）
- 土台の CSS：デザインシステムの土台の CSS（`_tech/ds/<フォルダ>/base.css`。日本語の折り返し、操作の応答と動き、入力の部品の形。Designer が同じ時点で作る）を、作るものの土台の CSS のファイルに中身のまま写す決まりと、そのファイルの置き場所（ほかのどの CSS より先に、すべての画面で読む）を architecture.md に書く。base.css は要素、状態、data 属性のセレクタと、tokens.css と同じ名前の変数だけで書かれるので、そのまま効く。画面は、これらを画面ごとに書き直さない
- 日本語の文節の区切り：base.css の `word-break: auto-phrase` は Chromium（Chrome、Edge）だけで効き、Safari（iPhone を含む）と Firefox では捨てられて `word-break: keep-all` が残る（keep-all だけでは、文節の区切りの無い長い文が折り返せず、はみ出すことがある）。作るものには、文節の区切り（`<wbr>`）を入れる手当て（BudouX など）を決め、技術の選択（tech.yaml。畳んでよい）に入れる。architecture.md に、どこで区切りを入れるか（画面文の一覧の文を出す所、など）と、その道具が勧める CSS を、道具の説明で確認してから書く（Designer が base.css に入れる）。あわせて、画面の文を出す部品は、値の入る所（`{名前}`）に入れる値を `<span data-value>` で包む（base.css がこの印の値に `display: inline-block` を当て、名前などの値を行の途中で割らない）と書く。値の入る画面の文は、すべてこの部品で出す（文字列を返す関数で文を組み立てて出すと、値が包まれない）。属性の値（aria-label、placeholder、alt、title など）は除く。1 行で切る欄（`text-overflow: ellipsis`）は、base.css の印 `data-truncate` を付ける（その中では値を包む span を inline に戻すので、値が丸ごと「…」にならない）とも書く
- 作った画面を人が開く手順：toolchain.yaml の `start` に、ビルドと起動のコマンド（command）と開く URL（url）と、画面を開いて試せる架空のデータを入れるコマンド（seed。開発用のデータの置き場所に入れ、テストの準備の関数を使い回してよい。実データは使わない）を書く（受入の画面に、人が自分のブラウザで開く手順として出る。001 では入れるデータが無くてよく、機能のチケットの作る役が、そのチケットの画面のデータを足す）。データベースを使うなら、seed のコマンドは、データベースを起こす所から含める（受入の画面には seed、command の順に出るので、データベースを起こす、データを入れる、ビルドと起動、ブラウザで開く、の順になる）。日時を決めて起こすコマンド（clock）も必ず書く：seed と command をつなぎ、日時の所を `{at}` と書いたコマンドで、e2e のためにある、サーバーの時計を決める仕組みを使う（例：`npm run db:up && npm run seed && npm run build && APP_CLOCK={at} npm start`。受入の画面では seed と command の代わりに流すので、ビルドも含める）。開く日によって画面を試せないとき（休みの日で名簿が空になる、など）の道として、計画担当が書いた試す日時を `{at}` に入れて受入の画面に出る。そのため、画面の「今日」（日付や時刻で中身が変わる所）はサーバーから受け取る、と architecture.md に書く（ブラウザの時計で決めると、clock で起こしても画面の今日が変わらない）。ログインのある画面では、試すためのログインの情報（login。架空の利用者を作るコマンドか、その名前とパスワード。実データは使わない）も書く。001 の時点でログインが無ければ書かず、ログインを入れた機能のチケットの仕様担当が、この節を使って足す
