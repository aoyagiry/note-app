## 確認してほしいこと（後で変えにくいもの）

### アプリは Rust と Tauri 2 で作り、画面は Web の技術（HTML と CSS）で、OS の WebView（Windows は WebView2、Mac は WKWebView）に描く。ページの保存、検索、同期などの処理は Rust で書く（AI の提案。問い 4 の答えで決まった）

- なぜ決めるか：人は「アプリは Rust で作る（速さを大事にするため）」と指定しました（FACT-rust）。この選択では、処理とデータは Rust で作りますが、画面は Web の技術（TypeScript）で描くので、指定から外れる所があります。Mac の画面は Safari と同じ仕組み（WebKit）、Windows の画面は Edge と同じ仕組み（Chromium）で描かれるので、両方で見え方と速さを確かめます
- 選んだ理由：問い Q-004 の答えで決めた。速さ（NFR-response-time）に照らすと、遅くなりやすいのは、1 万件のページの保存、読み出し、検索と、起動の処理で、これらはすべて Rust で行う。文字を打ってから出るまでは、WebView の中の本文の編集の部品が、処理とやり取りせずに次の描画（1 コマ 16 ミリ秒）で出す（Notion、VS Code、Obsidian も同じ形）。ページを開く、検索の結果を出すは、Rust の処理に 1 回聞いて、出す分だけを描くので、100 ミリ秒の中に収まる見込み。Tauri のアプリは、OS の WebView を使うので、起動が 1 秒より短い見込み。選んだ見た目（ひだまりの遊び）は CSS の変数と土台の CSS（base.css）で描かれていて、そのまま写せる。本文の編集は、Web の技術に成熟した部品がある
- 選ばなかった案：画面も Rust で描く（GPUI、egui、Slint など）（描画は最も速いが、見た目の土台と本文の編集を一から作る）
- 選ばなかった案：Rust で画面を書き、WebView で描く（Dioxus、Leptos）（速さは同じで、本文の編集の部品が乏しい）
- 選ばなかった案：Electron（Rust で作る指定に合わず、重く起動も遅い）
- 後から変えるとき：画面をすべて作り直します。画面も Rust で描く形に変えるときは、見た目の土台（CSS）と、画面の e2e とスクリーンショットの確かめ方も作り直します。Rust の処理（crates/core）はそのまま使えます

### 画面は React と TypeScript で書き、Vite でビルドする。見た目は CSS Modules と、デザインシステムと同じ名前の CSS の変数だけで指定する

- なぜ決めるか：画面を組み立てる道具の選び方で、作れる部品と、作る役が迷わずに書けるかが変わります。すべての画面がこの道具の上に乗ります
- 選んだ理由：本文の編集、木の形の並び、長い一覧を少しずつ描く部品など、作るものに要る部品と情報がいちばん揃っているため。文字を打つ処理は本文の編集の部品が React の外で行うので、キーを打ってから文字が出るまでの速さ（NFR-response-time）に React は効かない
- 選ばなかった案：Svelte（本文の編集と木の部品の選択肢が少ない）
- 選ばなかった案：SolidJS（速いが部品と情報が少なく、作る量が増える）
- 選ばなかった案：Vue（本文の編集と Yjs の組み合わせの例が少ない）
- 後から変えるとき：すべての画面と、画面の単体テストを書き直します。e2e のテストと Rust の処理はそのまま使えます

### ページはパソコンの中の SQLite に保存し、ページの中身と並びは Yjs の形（CRDT。Rust では yrs）で持つ。ネットにつながっていなくても、すべての操作はパソコンの中のデータに対して行う

- なぜ決めるか：ページをどんな形で保存するかで、つながっていない間に書いたものの合わせ方と、同期の仕組みが決まります。000 で、両方の書き換えを行や文字の単位で自動で合わせると決めました
- 選んだ理由：2 台で同じページを書き換えたとき、両方の書き換えを行や文字の単位で自動で合わせる（RULE-merge-edits）には、書き換えを差分として持ち、どの順に届いても同じ結果になる仕組み（CRDT）が要るため。Yjs は本文の編集の部品との組み合わせ（y-prosemirror）があり、Rust の yrs と同じ形でやり取りできる。パソコンの中に保存するので、つながっていなくても読み書きできる（RULE-works-offline）
- 選ばなかった案：ふつうの表に保存し、後から書いた方を残す（文字の単位で合わせられない）
- 選ばなかった案：Automerge（本文の編集の部品との組み合わせが少ない）
- 選ばなかった案：Loro（新しく、長く使った実績が少ない）
- 後から変えるとき：保存したページを新しい形に移し替える処理と、同期の仕組みと、本文の編集のつなぎを作り直します

### データを預かるサーバーは Supabase（データベース、ログイン、変更の知らせを運用まで任せられるサービス）を使う。サーバーはページの書き換えの差分を預かって相手のパソコンに知らせるだけで、合わせるのは各パソコンが行う。手元では Supabase の CLI で Docker の上に同じものを起こす。使い始めるのは 005 から

- なぜ決めるか：壁打ちで「どのフルマネージドのサービスにするか（2 台の書き換えを文字の単位で合わせる仕組みとの相性も含めて）」を決めていませんでした。ログイン（005）と同期（006）の作りが、このサービスの上に乗ります
- 選んだ理由：Supabase の公式のクライアントは JavaScript、Flutter、Swift、Python、C# だけで、Rust は公式にもコミュニティの一覧にも無い。Rust の処理からやり取りすると、ログインとトークンの更新（Auth の REST）、表への出し入れ（PostgREST）、Realtime の手順（WebSocket の上の join、25 秒ごとの heartbeat、トークンの入れ替え、つなぎ直し）を自前で書いて保守することになる。画面の側の supabase-js なら、これらは Supabase が保守するので自前で書くのは差分の受け渡しだけで済み、合わせる仕組みは Rust（yrs）に残せる。2 台の書き換えを文字の単位で合わせるのは CRDT（Yjs）が各パソコンで行い、差分はどの順に届いても同じ結果になるので、サーバーは差分を積んで知らせるだけでよい（RULE-merge-edits）。積んだ差分は消えないので、つながっていない間の書き換えも後から届く（RULE-works-offline）。データベースから送る Broadcast の遅れは、Supabase の計測で中央値 46 ミリ秒、遅い方の 5% でも 132 ミリ秒で、3 秒以内に出す（NFR-sync-delay）に十分な余裕がある。1 回に送れる大きさ（無料の枠で 256 KB）は、打った分の差分なら収まり、大きな初めの同期は知らせでなく表から取る。フルマネージドの希望に合い、データベース、ログイン、変更の知らせが 1 つのサービスにまとまっていて、手元でも Docker で同じものを動かせる。費用は、無料の枠（データベース 500 MB、プロジェクト 2 つ、使う人 5 万人まで）で、自分一人で使う間は足りる見込み。無料の枠のプロジェクトは 1 週間使わないと止まるので、使い始める 008 で、止まらない有料の枠（月 25 ドルから）にするかを決める
- 選ばなかった案：Cloudflare（Durable Objects、D1）（Yjs の中継に向くが、ログインとパスワードの保存を自分で作る）
- 選ばなかった案：Supabase と Rust の処理が直にやり取りする（公式の Rust のクライアントが無く、Auth と Realtime を自前で書く）
- 選ばなかった案：Firebase（差分を積んで知らせられるが、手元で Docker で動かせない）
- 選ばなかった案：AWS（Cognito、AppSync、DynamoDB など）（差分を知らせる部品の組み合わせが多く、手元で動かしにくい）
- 選ばなかった案：GCP（Cloud Run、Cloud SQL など）（差分を中継する処理を自分で動かし、常に課金される）
- 後から変えるとき：ログインと同期のサーバー側とアプリの同期の処理を作り直し、預けたページを新しいサービスへ移します。パソコンの中のデータの形（TECH-local-data）と、合わせる仕組み（Yjs）はそのまま使えます

### 失敗は、決まった種類（見つからない、断られる、ほかと重なる、権限が無い、ログインしていない、想定外）と理由の符号だけで返し、画面が符号に当たる文を画面文の一覧から引いて出す。想定外の失敗では、中身を一切返さず、記録だけに残す

- なぜ決めるか：失敗をどう返し、どう画面に出すかを、すべての操作で揃えます。後から変えると、すべての操作の失敗の扱いと、そのテストを直すことになります
- 選んだ理由：失敗の理由ごとに画面の文を分けられ、文の直しがコードに及ばない。サーバーの内部の情報を返さない（NFR-error-details）
- 選ばなかった案：例外の文をそのまま返す（内部の情報が画面に出る（NFR-error-details））
- 選ばなかった案：画面に出す文をサーバーが返す（文の直しのたびに処理を直すことになる）
- 後から変えるとき：すべての操作の失敗の返し方と、画面の失敗の出し方と、そのテストを直します

- 道具をそろえた環境（手元は準備のコマンド npm run setup の後、CI はジョブの準備の段の後）を見る → .browsers/ に Chromium と WebKit があり、cargo nextest、cargo llvm-cov、cargo audit が動き、rust-toolchain.toml の部品（clippy、rustfmt、llvm-tools-preview）が入り、Node.js の版が .node-version のメジャー版と同じ

**作る役がテストを変えられない**

- 作る役として、e2e/ の下のテストのファイル、apps/desktop/src の下の *.test.ts、playwright.config.ts、vitest.config.ts のどれかを変えて、コミットの検査（scope-check）を流す → 範囲外の変更として止められる。apps/desktop/src の下の実装のファイルだけを変えたときは止められない

## AI の提案と問い

### 問い 1：比較のページで見た 3 つの案のうち、どの見た目でアプリを作りますか

**答え**：やわらかな遊びを元に遊びを足した「ひだまりの遊び」（sunlit-play。押すと沈む厚み、時刻で変わる背景のにじみ、線を引くように描かれる印、極太の見出し）。最初の答えは「やわらかな遊びが一番いいが、もっと遊びがあってもいい」で、遊びの強さを 3 段に分けた案を見比べて選んだ

- やわらかな遊び（砂色の地に浮かぶ丸い紙。押すと少し沈み、チェックやつまみが小さく弾む。背景に淡いにじみがゆっくり漂う）（提案）：「動かすだけで楽しく、思わず開きたくなる」にいちばん近く、押したときの手応えがはっきりあります。色は砂色と白に素焼きの橙を一点だけで、ぎらぎらしません。そのかわり、余白と丸みで一度に見える量は 3 案の中で最も少なく、弾む動きと漂う背景は長く使うと甘く感じることがあります。動きは 180〜260ms で 3 案の中で長めなので、ページを開くなどよく使う操作は短く詰めて作ります
- くっきりした道具（白と灰を 1px の線で区切った作業の道具らしい画面。信号の緑を一点だけ使う）：動きは 60〜180ms で、押した瞬間に返り、3 案の中でいちばん速く感じます。保存した時刻や文字数、並びの子の数が常に見え、キーボードだけで探して開けます。そのかわり、情報と線が多く、ゆったり書く気分は出にくく、楽しさは見た目より速さと正確さから出す方向になります
- 静かな紙（生成りの紙に墨で書くような面。見出しは明朝、藍を一点だけ使う）：長い文を落ち着いて書いて読み返すのに向き、夜に暗い画面で使っても目が疲れにくいです。そのかわり、一度に見える行とページの数が少なく、ボタンの形が控えめなので押せる所が分かりにくいことがあり、楽しさは手応えより静けさの側に寄ります

提案の理由：壁打ちで話された「動かすだけで楽しく、思わず開きたくなる」「手応えで楽しさを出す」「背景の動きは場面によってあってよい」に、3 案の中でいちばん合うためです。パソコンの幅では、左の並びと本文が浮いた 2 枚の面になり、余白が多めでも本文は十分な幅で読めます。スマホの幅（スマホは後で足す予定ですが、パソコンでウィンドウを細くしたときも同じ形になります）では、左の並びを隠して丸いメニューのボタンから開き、本文の面だけが残るので、どの案でも同じように使えます。ただ、3 案の中で一度に見える量がいちばん少ないので、ページが増えて一覧で見渡したくなったら、くっきりした道具が合います

### 問い 2：新しい版のアプリを自分の Mac と Windows に入れるとき、どうしたいですか

- 自分の 2 台では、ビルドされたアプリを手で入れ直す。自動のアップデートは一般に配るときに足す（提案）（答え）：使い始めるまでに作るものが少なく済みます。そのかわり、新しい版を出すたびに、Mac と Windows の両方でダウンロードして入れ直す手間がかかります
- 使い始めるとき（008）から、アプリが新しい版を見つけて自分で入れ替わるようにする：版の印を付けた後は、2 台とも次に開いたときに新しい版になり、入れ直す手間がありません。そのかわり、008 で署名の鍵と新しい版を置く場所の準備が足され、使い始めるまでが少し延びます

提案の理由：最初に使うのはご自身一人で、版を出すタイミングもご自身で決めるので、入れ直す手間は小さいためです。配り方（無料、買い切り、月額）を決めるときに、新しい版の届け方も一緒に決められます

### 問い 3：PR を出したときと main にマージしたときに、Mac と Windows の両方ですべてのテストを流す確認（CI）を、どの機械で流しますか

**答え**：リポジトリを公開にして、GitHub の Mac と Windows の機械で毎回流す（公開のリポジトリは無料で使えるため）。最初の答えは「今回 CI はやめる」で、CI を置かないと受け入れの確かめと「両方で流して通す」を自動で確かめられなくなることと、費用を抑える案（Windows だけ CI、リポジトリを公開、自分の 2 台を CI の機械に、置かない）を示して選んでもらった

- GitHub の機械で毎回流し、無料の分を超えたら払う（提案）：手元のパソコンの状態によらず、いつでも同じきれいな環境で確認が流れます。作業の多い月は 20〜40 ドルほどかかる見込みです。GitHub に支払いの方法を登録し、使ってよい額の上限を決めておく準備が要ります。005 から、CI では Supabase の試し用のプロジェクトを使います
- 自分の Mac と Windows を、CI を流す機械として GitHub につなぐ：費用はかかりません。Docker も使えるので、005 からも手元の開発と同じ形でサーバーのテストを流せます。そのかわり、2 台の電源が入っていて、待ち受けの仕組みが動いている間だけ確認が流れ、どちらかが止まっていると PR の確認がそのまま待ちます。流している間は、そのパソコンが重くなります
- GitHub の機械で、Windows は毎回、Mac は main にマージしたときだけ流す：Mac の分の費用がおよそ半分になります。そのかわり、Mac でだけ壊れたことは、マージした後に分かります（「両方で流して通す」を「Mac はマージの後に確かめる」に書き換えます）
- 無料の分だけで流し、使い切ったら翌月まで待つ：費用はかかりません。そのかわり、使い切った月は CI が流れず、PR の確認とチケットの受け入れが翌月まで止まります

提案の理由：費用の上限は無く、安い方がよいとのお話でした。2 台のパソコンの電源や状態に左右されず、いつでも確認が流れるのはこの案だけで、かかる額は作業の多い月でも数十ドルに収まる見込みです

### 問い 4：「アプリは Rust で作る（速さのため）」について、画面の部分をどう作りますか

- 処理は Rust で作り、画面は Web の技術で描く（Tauri。Mac と Windows に入っている画面を描く仕組みを使う）（提案）（答え）：「ひだまりの遊び」の CSS の土台が、そのまま画面に使えます。Notion のような本文の編集の部品が揃っていて、作る量が少なく済みます。画面の作りも、ブラウザで自動で確かめられます。サーバーとのログインと同期のやり取りは、画面の側で Supabase の公式の部品を使えるので、自前で書くのはデータの受け渡しだけです。文字を打つ処理は画面の中で行うので 16 ミリ秒に収まる見込みで、ページを開く、探すは Rust の処理に 1 回聞いて出す分だけを描くので 100 ミリ秒に収まる見込みです。そのかわり、画面の部分は Rust ではなく TypeScript で書きます。Mac と Windows で画面を描く仕組みが違う（Mac は Safari と同じ、Windows は Edge と同じ）ので、両方で見え方と速さを確かめます
- 画面も Rust で描く（GPUI、Slint などで、画面を Rust から直に描く）：すべてを Rust で書けて、画面を描く速さは最も速くできます。そのかわり、「ひだまりの遊び」の CSS の土台は使えず、色や間隔の値だけを写して、押したときの沈み、弾む動き、背景、日本語の折り返しを Rust で作り直します。本文の編集（見出し、箇条書き、チェックボックス、日本語の入力）も一から作るので、003 が大きく延びます。画面をブラウザで自動で確かめる仕組みとスクリーンショットでの見比べも使えず、画面の確かめは、触って見る確認が中心になります。さらに、Supabase には Rust の公式の部品が無いので、ログイン、データの出し入れ、変更の知らせを受ける手順を自前で書いて保守するか、Rust から使いやすい別のサーバーの仕組みを選び直すことになり、ログイン（005）と同期（006）も延びます

提案の理由：速さが効く処理（1 万件の保存、検索、起動、同期）はすべて Rust が受け持つので、Rust を選んだ理由の速さは保てます。画面の部分は、基準の 16 ミリ秒と 100 ミリ秒に収まる見込みで、選んだ見た目と本文の編集をそのまま作れるからです。速さは、チケットごとに計測のコマンドで Mac に近い仕組みと Windows と同じ仕組みの両方で測り、基準を超えたら分かるようにします

<details><summary>ほかの技術の選択（13 件。後から変えても手間が小さいものです）</summary>

- アプリ、試す場、サーバーの定義、両方が使うデータの形を、このリポジトリ 1 つにまとめる（モノレポ）。Rust は Cargo の workspace、JavaScript の依存はリポジトリの直下の package.json 1 つで持つ
- 試す場（devhost）を Rust で作る。アプリと同じコマンドの処理を HTTP で受け、ビルドした画面を配る。e2e、API のテスト、人がブラウザで画面を開くときに使う
- テストは、画面の部品の単体テストと API のテストを Vitest、e2e を Playwright（Chromium のパソコンの幅とスマホの幅、Mac の画面に近い WebKit のパソコンの幅）、Rust の中のテストを cargo-nextest で流す。結果はすべて JUnit XML で reports/junit/ に出す
- カバレッジは、TypeScript を Vitest（v8）で、Rust を cargo-llvm-cov で測る。Rust は、API のテストが呼んだ試す場の処理も含めて測る
- 書き方の決まりは lint の道具（ESLint、Prettier、rustfmt、clippy）で確かめる。git の hook は使わない
- 脆弱性の検査は npm audit（High 以上で落とす）と cargo audit（既知の脆弱性があれば深刻度によらず落とす）で行う
- 書体は、デザインシステムと同じものを Fontsource の npm パッケージでアプリに同梱する（今の案では Zen Maru Gothic と Nunito）。ネットにつながっていなくても同じ書体で出る
- 日本語の文の折り返しは、BudouX で文節の区切り（<wbr>）を入れて、Mac の画面（WebKit）でも文節で折り返す
- アプリの「今」（日付、時刻、時刻で変わる空の色）は、画面ではなく Rust の処理から受け取る。試す場では、起動のときの指定で時計を決められる
- 想定外の失敗の詳細は、パソコンの中の記録のファイルにだけ書き、画面には出さない
- アプリと試す場とサーバーがやり取りするデータの形は Rust で定義し、TypeScript の型を生成して使う
- CI は GitHub Actions で、PR（向け先が main と aidd/**、下書きを除く）と main への push のたびに、Mac と Windows の GitHub の機械で、すべての検証と e2e を流す（NFR-platforms）。リポジトリは公開にするので、GitHub の機械は無料で使え、回数の上限を気にせず毎回流せる（問い Q-003 の答え）。公開なので、認証情報はリポジトリに置かず、CI の秘密の値は GitHub の secrets にだけ置く（AI の提案。問い 3 の答えで決まった）
- 版の印（v で始まるタグ）を付けて送ったときだけ、Mac と Windows のアプリをビルドし、GitHub の下書きのリリースに置く。main へのマージでは何も起きない。署名はせず、新しい版は自分で入れ直す（自動のアップデートは一般に配るときに足す）
